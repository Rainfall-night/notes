# C# 并发与线程

> **系列**：C# 学习笔记（并发专题）｜ **上级**：[[02-C#高阶]] 第 7 课
> **说明**：结合 `STWebsiteBackEnd_V2` 项目与 ASP.NET Core 实际场景讲解。

## 1. 并发 vs 并行


|      | 并发（Concurrency）      | 并行（Parallelism）  |
| ------ | -------------------------- | ---------------------- |
| 含义 | 多个任务**交替**执行     | 多个任务**同时**执行 |
| 硬件 | 单核也能（靠时间片切换） | 需要多核             |
| 类比 | 一个人来回切换做几件事   | 多个人同时做几件事   |

**关键**：并发是"结构"（任务可以交错），并行是"执行"（真的同时跑）。ASP.NET Core 同时处理大量请求，就是并发（甚至单核也能并发）。

## 2. 线程（Thread）

- 线程是操作系统调度的**最小执行单元**
- 一个进程可以包含多个线程

**C# 创建线程的方式（从底层到高层）**：


| 方式                                | 层次                | 用途             | 现代推荐度           |
| ------------------------------------- | --------------------- | ------------------ | ---------------------- |
| `new Thread(...).Start()`           | 最底层              | 手动管理线程     | ❌ 几乎不用          |
| `ThreadPool.QueueUserWorkItem(...)` | 线程池              | 短任务           | 少用（被 Task 取代） |
| `Task.Run(...)`                     | 线程池（Task 封装） | 后台任务         | ✅ 最常用            |
| `Task.Factory.StartNew(...)`        | 线程池（更多选项）  | 长任务等特殊场景 | 特定场景             |
| `Parallel.For` / `ForEach`          | 并行循环            | CPU 密集并行     | 特定场景             |
| `async/await`                       | 异步（不阻塞线程）  | IO 密集          | ✅ 最推荐            |

```csharp
// ① 最原始：new Thread
var t = new Thread(() => Console.WriteLine("线程"));
t.Start();

// ② 线程池：不 new 线程，交给线程池调度
ThreadPool.QueueUserWorkItem(_ => Console.WriteLine("线程池任务"));

// ③ Task.Run：现代最常用，底层也是线程池
Task.Run(() => Console.WriteLine("Task"));

// ④ Task.Factory.StartNew：更多控制选项
Task.Factory.StartNew(() => { }, TaskCreationOptions.LongRunning);

// ⑤ 并行循环：自动拆成多线程并行执行
Parallel.For(0, 100, i => { });
Parallel.ForEach(items, item => { });

// ⑥ async/await：异步，等待时线程被释放
await SomeIoAsync();
```

**为什么现代代码不 new Thread**：

- `new Thread` 直接创建 OS 线程，开销大（约 1MB 栈），创建销毁慢
- `Task.Run`/线程池复用线程，开销小得多
- `async/await` 等 IO 时根本不用线程，线程被释放去干别的

**对比 Java**：


| Java 开线程                       | C# 对应                   |
| ----------------------------------- | --------------------------- |
| `new Thread(...).start()`         | `new Thread(...).Start()` |
| `Runnable` 接口                   | `Action` / 委托           |
| `Callable` + `Future`             | `Task<T>`                 |
| `ExecutorService`（线程池）       | `ThreadPool` / `Task.Run` |
| `CompletableFuture`               | `Task`                    |
| `parallelStream()` / ForkJoinPool | `Parallel.ForEach`        |

## 3. 线程安全：竞态条件（Race Condition）

### 3.1 为什么需要并发

1. **充分利用 CPU**：多核并行计算，加速处理
2. **避免阻塞**：等 IO 时线程去做别的（呼应 async/await）

### 3.2 竞态条件的根源

多个线程同时读写**共享数据**，结果不确定：

```csharp
private static int counter = 0;

void Increment() {
    for (int i = 0; i < 100000; i++) {
        counter++;   // ⚠️ 不是原子操作！
    }
}

// 两个线程各跑 10 万次
// 期望 200000，实际可能 150000 左右
```

**为什么 `counter++` 不是原子的**：分三步：

```
1. 读 counter 的值
2. 值 + 1
3. 写回 counter
```

两个线程交错，就"丢"一次加：

```
线程A：读 counter=100         线程B：读 counter=100
线程A：100+1=101              线程B：100+1=101
线程A：写回 101               线程B：写回 101   ← 两次 ++ 只加了 1！
```

**竞态条件 = 多线程 + 共享可变数据 + 非原子操作**，三者缺一不可。

### 3.3 解决方案总览


| 方案               | 适用                   |
| -------------------- | ------------------------ |
| `lock` / `Monitor` | 互斥锁，保护临界区     |
| `Interlocked`      | 原子操作（加减、交换） |
| `SemaphoreSlim`    | 限制并发数             |
| `Concurrent` 集合  | 线程安全集合           |
| `async/await`      | 异步 IO，不阻塞线程    |

## 4. lock 与 Monitor

### 4.1 lock：让临界区同时只进一个线程

```csharp
private static int counter = 0;
private static readonly object _lock = new();   // ① 专用锁对象

void Increment() {
    for (int i = 0; i < 100000; i++) {
        lock (_lock) {          // ② 同时只允许一个线程进入
            counter++;          // ③ 临界区
        }
    }
}
// 两个线程各跑 10 万次，结果 = 200000 ✅ 不再丢
```

语义：一个线程进入 lock 后，其他线程想进同一个 lock 会阻塞排队，等里面的出来才放行。

### 4.2 lock 的本质：Monitor 的语法糖

```csharp
lock (_lock) { /* 临界区 */ }

// 等价于 ↓
Monitor.Enter(_lock);
try { /* 临界区 */ }
finally { Monitor.Exit(_lock); }   // 异常也释放锁（finally 保证）
```

### 4.3 底层原理：对象头 + 同步块表 + 换锁

**锁存哪**：每个堆对象有对象头，含"同步块索引"，指向全局同步块表：

```
堆上的对象                    全局同步块表
┌──────────────┐            ┌─────────────────────────────┐
│ 对象头        │            │ SyncBlock 0                 │
│  ├ SyncBlockIndex ────────▶│ ├ 持有线程（Thread ID）      │
│  └ TypeHandle│            │  ├ 重入计数                   │
├──────────────┤            │  ├ 等待队列（阻塞的线程）       │
│ 对象数据       │           │ SyncBlock 1                  │
└──────────────┘            └─────────────────────────────┘
```

锁状态不存对象本身，而在全局同步块表里，对象头只存索引。

**Monitor.Enter 的换锁（锁膨胀）**：

```
① 快速路径：Interlocked.CompareExchange 原子获取 → 几纳秒，不碰内核
② 自旋：没抢到先原地转几圈，期望锁马上释放
③ 内核锁：自旋几次还拿不到 → 分配同步块条目，调用 OS 内核对象让线程阻塞
```

### 4.4 锁对象的选择（三个坑）

```csharp
private static readonly object _lock = new();   // ✅ 专用锁对象

lock (this)        // ❌ 外部也能拿到 this 并 lock，可能死锁
lock ("字符串")     // ❌ 字符串驻留，全进程共享同一把锁
lock (typeof(T))   // ❌ 类型对象全局共享
```

原则：锁对象必须是 private readonly 的专用 object，不暴露给外部。

**三个坑的底层原因**（由 4.3 的机制解释）：


| 坑                      | 原因                                         |
| ------------------------- | ---------------------------------------------- |
| 锁对象必须引用类型      | 值类型没对象头，装箱后每次是新对象，各锁各的 |
| 不能 lock 字符串        | 字符串驻留，多个 lock("x") 是同一个驻留对象  |
| 锁对象 private readonly | 防止外部拿同一对象 lock，造成意外竞争        |

### 4.5 可重入锁（Reentrant）：同一线程重复 lock 不死锁

```csharp
void A() {
    lock (_lock) {
        B();    // B 里又 lock 同一个锁
    }
}
void B() {
    lock (_lock) { ... }   // 同一线程再次 lock，不会死锁
}
```

原理：Monitor 内部记录"当前持有线程 + 重入计数"。同一线程重复进入只把计数 +1，退出 -1，归零才真正释放。Java 的 synchronized 同样可重入。

### 4.6 锁升级：无竞争快，有竞争慢

```
无竞争  →  轻量级自旋（Interlocked CAS），几纳秒搞定
有竞争  →  升级为内核锁，线程阻塞，代价变大（微秒级 + 上下文切换）
```

结论：低竞争时 lock 几乎无成本；高竞争（大量线程抢同一把锁）性能明显退化——所以要"临界区小、别用一把全局大锁"。

### 4.7 锁是线程相关的（thread-affine）

Monitor 记录"哪个线程持有锁"，只能由持有线程 Exit：

```csharp
// 线程 A Enter，线程 B Exit → 抛 SynchronizationLockException
```

这也是 lock 里不能 await 的原因——await 后可能换线程，Exit 的线程 ≠ Enter 的线程，直接异常。

### 4.8 lock 的代价和注意事项


| 注意点         | 说明                                                  |
| ---------------- | ------------------------------------------------------- |
| 降低并发度     | 临界区同时只有一个线程，其他都等                      |
| 临界区要小     | 只包住必须互斥的部分，别把慢操作（IO）放进去          |
| 别在锁里 await | lock 里不能 await（用 SemaphoreSlim 替代，见第 6 节） |

### 4.9 死锁（Deadlock）

```csharp
// 线程A：lock(a) → 想拿 b
// 线程B：lock(b) → 想拿 a
// 结果：A 等 b，B 等 a，永远卡死
```

避免死锁：多把锁时，所有线程按**相同顺序**加锁。

### 4.10 Monitor.TryEnter：带超时，拿不到就放弃

```csharp
if (Monitor.TryEnter(_lock, TimeSpan.FromMilliseconds(100))) {
    try { /* 拿到锁，干活 */ }
    finally { Monitor.Exit(_lock); }
} else {
    // 100ms 内没拿到锁，放弃，做别的（避免死等）
}
```

lock 是"无限等"，TryEnter 是"等一会儿，拿不到就走"。

### 4.11 Monitor.Wait / Pulse：条件变量（生产者-消费者）

```csharp
// 消费者：等队列有东西
lock (_lock) {
    while (queue.Count == 0) {
        Monitor.Wait(_lock);   // ① 释放锁 + 挂起，等通知
    }
    var item = queue.Dequeue();
}

// 生产者：放入后通知
lock (_lock) {
    queue.Enqueue(item);
    Monitor.Pulse(_lock);   // ② 唤醒一个等待线程
}
```

关键：Monitor.Wait 自动释放锁再挂起，被唤醒后重新拿锁——这是"等待-通知"的标准姿势。

### 4.12 对比 Java


|            | C#                                       | Java                           |
| ------------ | ------------------------------------------ | -------------------------------- |
| 锁状态存哪 | 对象头（索引）+ 全局同步块表（分离式）   | 对象头 Mark Word（内嵌）       |
| 升级路径   | CAS → 自旋 → 内核锁                    | 偏向锁 → 轻量级锁 → 重量级锁 |
| 共同点     | 都是"无竞争轻量、有竞争重量"的锁膨胀思路 |                                |

## 5. Interlocked 原子操作

### 5.1 Interlocked 是什么：counter++ 的更轻量解法

```csharp
private static int counter = 0;

void Increment() {
    for (int i = 0; i < 100000; i++) {
        Interlocked.Increment(ref counter);   // 原子 +1，一步完成
    }
}
// 两个线程各跑 10 万次，结果 = 200000 ✅
```

Interlocked.Increment 是硬件级原子操作（CPU 指令保证），一步完成"读-加-写"，不会交错。

### 5.2 为什么原子：CPU 硬件指令

Interlocked 之所以天然原子，因为最终落到 CPU 硬件原子指令：
- x86/x64：`LOCK` 前缀 + `CMPXCHG`（比较并交换）、`XADD`（交换加）
- `LOCK` 前缀锁住总线/缓存行，保证指令执行期间别的核心不能动这块内存

所以 Interlocked.Increment = 一条 `LOCK XADD` 指令，硬件层面不可分割。

### 5.3 常用方法

| 方法 | 作用 |
|------|------|
| Increment(ref int) | 原子 +1 |
| Decrement(ref int) | 原子 -1 |
| Add(ref int, int) | 原子加 N |
| Exchange(ref T, T) | 原子赋值/交换 |
| CompareExchange(ref T, newVal, cmp) | CAS：当前值==cmp 就改成 newVal |

### 5.4 CAS：CompareExchange（无锁编程的基础）

```csharp
// 语义：如果 counter 还是 100，就改成 101
int old = Interlocked.CompareExchange(ref counter, 101, 100);
// old == 100 → 成功改了；old != 100 → 中途被别人改了，需重试
```

基于 CAS 的"无锁读-改-写"（自旋）：

```csharp
int original, newValue;
do {
    original = counter;                 // 读当前值
    newValue = original + 1;            // 算新值
} while (Interlocked.CompareExchange(ref counter, newValue, original) != original);
// 中途被人改了 CompareExchange 失败，循环重试
```

### 5.5 ABA 问题（CAS 经典陷阱）

CAS 只比较值，若值 A → B → 又变回 A，CAS 误判"没变过"：

```csharp
// 线程1：读到 counter = 100，准备 CAS(counter, 101, 100)
// 线程2：counter 100 → 200 → 100（来回改又回到 100）
// 线程1：CAS 执行 → 100 == 100 → 成功改 101，但不知道中途被改过两次
```

**危害场景**：用 CAS 管理链表/栈节点时，节点可能被释放又复用，ABA 导致指针指向错误节点。

**解决**：加"版本号"一起比较（每次修改版本 +1，CAS 同时比较值+版本）。Java 有 AtomicStampedReference；C# 用 CompareExchange 组合 (值, 版本) 结构实现。

### 5.6 CAS 的应用：无锁栈

ConcurrentStack/ConcurrentQueue 内部用 CAS 实现"无锁"结构。简化版无锁栈 push：

```csharp
private Node? _head = null;

void Push(int value) {
    var node = new Node { Value = value };
    Node? original;
    do {
        original = _head;          // 读当前栈顶
        node.Next = original;      // 新节点指向旧栈顶
    } while (Interlocked.CompareExchange(ref _head, node, original) != original);
    // 中途 _head 被别人改了 CAS 失败，重试
}
```

无锁核心套路：读当前值 → 算新值 → CAS 尝试写回 → 失败重试（自旋）。

### 5.7 lock vs Interlocked

| | lock | Interlocked |
|---|---|---|
| 能做的事 | 任意复杂逻辑 | 只能简单原子加减/交换 |
| 开销 | 有锁膨胀、可能阻塞 | 极轻（一条硬件指令） |
| 适用 | 复杂临界区 | 计数器、标志位、状态切换 |

结论：能用 Interlocked 解决的（简单计数/标志），别用 lock——无阻塞、无锁膨胀，快一个量级。

### 5.8 对比 Java

| C# | Java |
|----|------|
| Interlocked.Increment | AtomicInteger.incrementAndGet() |
| Interlocked.CompareExchange | AtomicInteger.compareAndSet() |
| Interlocked 类 | java.util.concurrent.atomic 包 |

## 6. volatile：可见性 + 禁止重排

### 6.1 问题：多线程下的"可见性"

```csharp
private bool _stop = false;

// 线程 A：一直等停止信号
while (!_stop) { }

// 线程 B：发停止信号
_stop = true;    // ⚠️ 线程 A 可能"永远看不到"这个改动！
```

两个原因：
- **CPU 缓存**：每个核心有自己的缓存，B 写的是 B 的缓存，A 读的是 A 的缓存，没同步
- **指令重排/优化**：编译器假设没别的线程改 _stop，可能把 `while(!_stop)` 优化成"只读一次"

### 6.2 volatile 解决

```csharp
private volatile bool _stop = false;
while (!_stop) { ... }   // ✅ 每次循环重新读主内存最新值
_stop = true;            // ✅ 立即写回主内存，其他线程立即可见
```

| 保证 | 含义 |
|------|------|
| 可见性 | 对 volatile 字段的写，其他线程立刻能看到 |
| 禁止重排 | 编译器/CPU 不会重排对它的读写 |

### 6.3 底层：内存屏障（Memory Barrier）

volatile 底层就是插入内存屏障：

```
读 volatile 前 → 插"读屏障"（acquire），确保读到最新值
写 volatile 后 → 插"写屏障"（release），确保立即刷回主内存
```

### 6.4 局限：volatile 不保证原子性

```csharp
private volatile int counter = 0;
counter++;   // ⚠️ 依然不是原子的！还是"读-加-写"三步
```

### 6.5 三件套对比

| | volatile | Interlocked | lock |
|---|---|---|---|
| 可见性 | ✅ | ✅ | ✅ |
| 禁止重排 | ✅ | ✅ | ✅ |
| 原子性 | ❌ | ✅（简单操作） | ✅（复杂操作） |
| 适用 | 标志位 | 计数器 | 复杂临界区 |

记忆：volatile 管"看得到"，Interlocked/lock 管"改不乱"。

## 7. SemaphoreSlim 信号量

### 7.1 是什么：同时允许 N 个线程（lock 只允许 1 个）

```csharp
private static readonly SemaphoreSlim _sem = new(3, 3);   // 同时最多 3 个

async Task DoWork() {
    await _sem.WaitAsync();   // 拿一个"许可证"，拿不到就等
    try {
        // 同一时刻最多 3 个线程在这里
    }
    finally {
        _sem.Release();       // 还回许可证
    }
}
```

- `new(3, 3)`：初始 3 个许可证，上限 3 个
- `WaitAsync()`：拿许可证（计数 -1），拿不到（=0）就异步等待
- `Release()`：还许可证（计数 +1）

对比：lock = 信号量为 1 的特例；SemaphoreSlim(N, N) = 允许 N 个并发。

### 7.2 参数详解：initialCount 与 maxCount

`SemaphoreSlim(int initialCount, int maxCount)`：

| 参数 | 含义 |
|------|------|
| 第 1 个 initialCount | 初始有多少个许可证（一开始允许几个线程通过） |
| 第 2 个 maxCount | 上限，许可证最多能到多少（Release 不能超过它） |

常见组合：

```csharp
new(3, 3)   // 初始满额，一开始就有 3 个名额（限流，最常见）
new(1, 3)   // 初始 1 个，之后最多能涨到 3 个（"逐步放开"，少见）
new(0, 3)   // 初始 0 个，必须等别人 Release 才有名额（"等信号"）
new(1, 1)   // 异步版 lock
```

两个坑：

```csharp
new(5, 3)   // ❌ 初始数不能大于上限，抛 ArgumentOutOfRangeException
```

`SemaphoreFullException`：`Release` 让计数 +1，若计数已满（= maxCount）再 +1 就超上限抛异常：

```csharp
var sem = new SemaphoreSlim(1, 1);   // 计数 = 1（满）
sem.Release();   // ❌ 计数已满，再 Release 要变 2 > 1 → SemaphoreFullException
```

本质：Release 次数 > WaitAsync 次数（配对错）就超上限。

```
WaitAsync → 计数 -1（拿许可证）
Release   → 计数 +1（还许可证），但不能超过 maxCount
```

正常写代码时 WaitAsync 和 Release 用 try/finally 严格配对，就不会踩这个坑。

### 7.3 核心用途：SemaphoreSlim(1, 1) = 异步版 lock

```csharp
private static readonly SemaphoreSlim _gate = new(1, 1);

async Task DoAsync() {
    await _gate.WaitAsync();     // 异步等待（不阻塞线程）
    try {
        await SomeIoAsync();     // 临界区里可以 await！
    }
    finally {
        _gate.Release();
    }
}
```

lock 是线程相关的，await 后可能换线程导致异常；SemaphoreSlim 的 WaitAsync 是"异步互斥"的标准替代。

### 7.4 Semaphore vs SemaphoreSlim

| | Semaphore | SemaphoreSlim |
|---|---|---|
| 范围 | 跨进程（命名信号量） | 仅进程内 |
| 底层 | 内核对象 | 用户态优先（轻量） |
| 异步 | ❌ 不支持 | ✅ WaitAsync |

"Slim" = 瘦身版：砍掉跨进程，换来轻量 + 异步。

### 7.5 内部实现：快速路径 + 慢速路径

跟 lock 的锁膨胀类似：无竞争时自旋/CAS（快），有竞争才进内核等待（慢）。

### 7.6 典型场景：限流

```csharp
private static readonly SemaphoreSlim _limiter = new(5, 5);   // 同时最多 5 个请求

async Task Handle() {
    await _limiter.WaitAsync();      // 第 6 个请求会在这里等
    try { /* 处理请求 */ }
    finally { _limiter.Release(); }
}
```

- API 限流（同时最多 N 个并发请求）
- 连接池（同时最多 N 个连接）
- 保护有限资源（同时最多 N 个下载任务）

### 7.7 对比 Java

| C# | Java |
|----|------|
| SemaphoreSlim | java.util.concurrent.Semaphore |
| WaitAsync() | acquire() / tryAcquire() |
| Release() | release() |

## 8. Concurrent 集合

### 8.1 为什么普通集合多线程下会崩

```csharp
var list = new List<int>();

Parallel.For(0, 100000, i => list.Add(i));
// ❌ 可能抛异常 / 数据丢失 / 甚至死循环
```

List.Add 内部是"扩容 + 写数组"两步，多线程交错破坏内部状态。Dictionary 并发写可能死循环（哈希表结构被破坏）。

### 8.2 Concurrent 集合家族

| 集合 | 线程安全方式 | 场景 |
|------|-------------|------|
| ConcurrentDictionary<K,V> | 细粒度锁 + CAS | 缓存、计数 |
| ConcurrentQueue<T> | 无锁（CAS） | 生产者-消费者队列 |
| ConcurrentStack<T> | 无锁（CAS） | 栈 |
| ConcurrentBag<T> | 线程本地存储 | 无序集合、累积结果 |

### 8.3 常用方法

```csharp
// ConcurrentDictionary
var dict = new ConcurrentDictionary<string, int>();
dict.TryAdd("a", 1);                 // 尝试加（已存在则 false）
dict.GetOrAdd("a", _ => 0);          // 有就取，没有就加并返回
dict.AddOrUpdate("a", 1, (_, v) => v + 1);   // 有则更新，无则加

// ConcurrentQueue（生产者-消费者）
var queue = new ConcurrentQueue<int>();
queue.Enqueue(1);                    // 入队
if (queue.TryDequeue(out var item))  // 出队（空则 false）
{ /* 处理 item */ }
```

### 8.4 典型场景

| 场景 | 用什么 |
|------|--------|
| 线程安全缓存 | ConcurrentDictionary |
| 生产者-消费者队列 | ConcurrentQueue |
| 多线程累积结果 | ConcurrentBag |

### 8.5 lock 包普通集合 vs Concurrent 集合

| | lock + List | Concurrent 集合 |
|---|---|---|
| 性能 | 锁粒度大，竞争时慢 | 细粒度锁/无锁，快 |
| 使用 | 自己加锁，易错 | 开箱即用 |
| 复杂操作 | 灵活 | 可能不够（"检查后修改"要额外处理） |

结论：多线程共享集合，优先用 Concurrent 系列，别自己 lock 包 List——除非需要"多步原子操作"（Concurrent 提供不了时）。

## 9. ASP.NET Core 中的并发

### 9.1 并发模型

- 每个 HTTP 请求由线程池分配线程处理
- async/await：等 IO 时线程被释放去处理别的请求
- 几百个请求能"同时"（并发）处理，哪怕线程数远少于请求数

### 9.2 Scoped：每请求独立实例

```csharp
builder.Services.AddScoped<AuthService>();
builder.Services.AddScoped<WorkOrderService>();
builder.Services.AddDbContext<AppDbContext>(...);   // DbContext 默认 Scoped
```

Scoped = 每个 HTTP 请求创建独立实例。不同请求的 Service/DbContext 互相隔离，实例字段（_db 等）不会并发冲突——每个请求各用各的。

### 9.3 真正要小心：static 成员（跨请求共享）

```csharp
// ✅ 安全：无状态 static 方法（纯函数，不存可变数据）
public static ExecuteResult Ok(string message = "") => new() { ... };

// ⚠️ 危险：static 可变状态（所有请求共享，并发写会崩）
public static List<User> _cache = new();
public static int _counter = 0;   // counter++ 会丢（竞态条件）
```

判断标准：static 方法（无状态）→ 安全；static 可变字段 → 危险，需锁/并发集合。

### 9.4 项目并发安全盘点

| 成员 | 并发风险 | 原因 |
|------|---------|------|
| Controller/Service/Repository 实例字段 | ❌ 安全 | Scoped，每请求独立 |
| AppDbContext | ❌ 安全 | Scoped |
| ExecuteResult.Ok() 静态方法 | ❌ 安全 | 无状态纯函数 |
| EnumHelper.GetDescriptionByEnum | ❌ 安全 | 无状态 |
| PagedList.Create() | ❌ 安全 | 无状态 |

### 9.5 三个常见并发坑

| 坑 | 场景 | 解法 |
|----|------|------|
| static 可变字段 | 全局缓存、计数器 | ConcurrentDictionary / Interlocked / lock |
| 单例服务放实例字段 | AddSingleton 的类有可变字段 | 改 Scoped，或字段用并发集合 |
| static 缓存无锁 | 手动写缓存 | ConcurrentDictionary 或 IMemoryCache |

**一句话总结**：

```
Scoped（每请求独立）→ 实例字段随便用，天然安全
static（全局共享）  → 无状态方法安全，可变字段必须加锁/并发集合
```
