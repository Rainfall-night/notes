# 13 定时调度实战

> **系列**：web与后台服务 专题（HostedService 专属）｜ **上一篇**：[[12-生命周期与优雅关闭]] ｜ **下一篇**：[[14-异常与崩溃监控]]

### 背景

> 后台服务最常见的需求之一就是"到点干某事"。定时任务分两类：**固定间隔**（每 5 分钟跑一次）和**固定时刻**（每天 7:30 跑）。
>
> 日报项目是**固定时刻**：5 个任务、触发时刻各不相同（7:00、7:30、9:30、19:00、每 14 天），用 `ScheduleRunner` 统一调度。
>
> 本篇分两部分：**一**讲项目里已有的调度思想（附代码作示例）；**二**引申出项目里没有、但生产环境绕不开的调度知识。

## 一、项目已有的调度知识

### 1. 自写循环

> 思想：后台任务用 `while` 死循环 + `Task.Delay` 周期执行，`token` 取消时立即退出。

```csharp
while (!ct.IsCancellationRequested) {
    await Task.Delay(TimeSpan.FromMinutes(5), ct);   // 每 5 分钟
    DoWork();
}
```

局限：只适合**固定间隔**，日报的"每天固定时刻"做不到，需要算"距离下次触发还有多久"。

### 2. 多任务调度：接口 + 统一调度器

> 思想：多任务用**策略接口**（声明调度元数据）+ **统一调度器**（注入所有任务批量调度）。

```csharp
public interface IScheduledTask {
    TimeSpan[] Schedules { get; }                    // 触发时间点
    TimeSpan? Timeout { get; }                       // 超时
    Task ExecuteAsync(IServiceProvider sp, CancellationToken ct);
}
```

调度器注入 `IEnumerable<IScheduledTask>` 自动拿到全部任务，无需逐个处理。

### 3. 计算 delay

> 思想：把所有任务的所有时间点**摊平**，取"距现在最近"的那个作为休眠时长。

```csharp
var delay = _tasks.SelectMany(t => t.Schedules)
    .Select(ScheduleHelper.CalculateNextDelay)   // 每个时间点 → 距现在的时长
    .Min();                                      // 取最近 → 睡多久
```

### 4. 容错窗口

> 思想：`Task.Delay` 睡醒有误差，精确匹配会**错过**；用 ±2 分钟窗口"宁可多算不漏算"。

```csharp
.Where(x => Math.Abs((now - x.Sched).TotalMinutes) < 2)
```

睡到 7:29~7:31 都算 7:30 的任务到期。

### 5. 防重复触发

> 思想：任务执行时间长（日报 90 分钟），调度器期间多次醒来会**重复触发**；用 HashSet 记录"当天已触发"去重。

```csharp
triggeredTimes.Add((task.GetType().Name, sched));   // Add 返回 false = 已触发过
```

### 6. 跨天清空

> 思想：已触发记录只在**当天**有效，跨天必须清空，否则今天 7:30 永远被当成"已触发"而跳过。

```csharp
if (DateTime.Today != curDate) {
    curDate = DateTime.Today;
    triggeredTimes.Clear();
}
```

### 7. 并发执行

> 思想：多个到期任务**并发跑**（`Task.Run` 不 await），一个任务卡死不拖垮调度循环和其他任务。

```csharp
_ = Task.Run(() => task.ExecuteAsync(sp, token), ct);   // 不 await，丢弃 Task
```

### 8. 超时控制

> 思想：**倒计时 CTS** + **串联主 token**；合并 token 取消了但主 token 没取消 = 超时。

```csharp
using var timeoutCts = new CancellationTokenSource(task.Timeout.Value);
using var linkedCts = CancellationTokenSource.CreateLinkedTokenSource(ct, timeoutCts.Token);
```

### 9. 异常分级

> 思想：**单任务异常**记录继续（不拖垮调度器）；**主循环异常**设退出码触发崩溃监控——详细机制见 [[14-异常与崩溃监控]]。

## 二、项目里没有的调度知识

### 10. Cron 表达式

> 项目用 `TimeSpan[]` 硬编码时间点，**只能表达"每天固定时刻"**。生产上更常见的是用 Cron 表达式表达复杂调度。

Cron 格式（6 段）：**秒 分 时 日 月 周**

| 需求 | Cron | 说明 |
|---|---|---|
| 每天 7:30 | `0 30 7 * * ?` | `?` = 不指定周 |
| 每周一 9:00 | `0 0 9 ? * MON` | `MON` = 周一 |
| 每月 1 号 0 点 | `0 0 0 1 * ?` | `1` = 1 号 |
| 每 2 小时 | `0 0 */2 * * ?` | `*/2` = 每 2 |
| 工作日 8 点 | `0 0 8 ? * MON-FRI` | 区间 `MON-FRI` |

**项目 `TimeSpan` 做不到、Cron 能做的**：

- 项目只能"每天 7:30"，Cron 能"每周一"、"每月 1 号"、"工作日"、"每 2 小时"

**Cronos 库**（轻量解析）：

```csharp
var cron = CronExpression.Parse("0 30 7 * * ?");
DateTime? next = cron.GetNextOccurrence(DateTime.UtcNow);   // 下一次触发时间
```

把项目的 `CalculateNextDelay` 换成 Cronos，就能把 `TimeSpan[]` 升级成任意 Cron 表达式。

### 11. 分布式多实例：任务重复执行

> 项目是**单实例** Worker，天然没问题。但一旦部署 **N 个实例**（多台机器跑同一个 Worker），每个实例都有个 `ScheduleRunner`——**7:30 的任务会执行 N 次**，重复发邮件、重复入库。

```
实例 A：ScheduleRunner ┐
实例 B：ScheduleRunner ┼→ 7:30 任务各跑一遍 → 重复！
实例 C：ScheduleRunner ┘
```

**解法：分布式锁**——只有抢到锁的实例才执行任务。

- **Redis 锁（RedLock）**：`SET lock_key 1 NX EX 60`，抢到锁的执行，执行完释放
- **SQL 锁表**：`SELECT ... FOR UPDATE`，或原子更新锁行（谁改成功谁执行）

```csharp
// 伪代码：任务开头抢锁
using var lock = await _distributedLock.AcquireAsync("daily-report-task", TimeSpan.FromMinutes(30));
if (lock == null) return;   // 没抢到 → 别的实例在执行，跳过
await DoWork();
```

- **进阶**：Leader 选举（只有一个实例当调度器），Hangfire/Quartz 集群内置此能力

### 12. 任务错过补偿

> 项目宕机错过 7:30 就**永远错过**了。生产上可能需要"补跑"。

- 场景：7:30 服务宕机，7:45 恢复 → 7:30 的日报没发
- **方案**：记录"上次成功执行时间"，恢复后检测错过的任务，决定是否补

```csharp
// 思想：判断"上次执行"到"现在"之间，有没有该跑没跑的时间点
if (lastRunTime < today7_30) {
    // 错过 7:30 → 决定是否补跑
    RunMissedTask();
}
```

⚠️ **权衡**：补跑有风险——日报重复发邮件可能有害，财务统计则必须补。所以"补不补"要按任务语义决定，不能一刀切。

### 13. 统一重试策略

> 定时任务的重试和通用重试是同一套知识（指数退避、抖动、Polly），完整见 [[05-异常处理]]。
>
> 定时任务的特有要求是：**重试要配合幂等**——任务可重复执行而无副作用，重试才安全。

### 14. PeriodicTimer

> .NET 6+ 的周期循环替代品，解决 `while + Task.Delay` 的一个隐藏问题。

**`while + Task.Delay` 的问题**：实际周期 = delay + 任务执行时间（执行时间被**叠加**进周期）。

```csharp
// 任务跑 3 分钟 + delay 5 分钟 = 实际每 8 分钟一次！
while (!ct.IsCancellationRequested) {
    await Task.Delay(TimeSpan.FromMinutes(5), ct);
    DoWork();   // 假设耗时 3 分钟
}
```

**`PeriodicTimer` 保证固定周期**：从"上一次开始"算周期，任务耗时被排除在外。

```csharp
await using var timer = new PeriodicTimer(TimeSpan.FromMinutes(5));
while (await timer.WaitForNextTickAsync(ct)) {
    DoWork();   // 每 5 分钟一次（从上次开始算）
}
```

### 15. 手写 vs 调度库

> 项目手写了 `ScheduleRunner`（适合少量固定任务）。任务变多、要持久化/重试/监控时，该引库了。

| 方案 | 特点 | 适合 |
|---|---|---|
| **手写**（如项目） | 轻量、可控、零依赖 | 少量固定时刻任务 |
| **Cronos** | 轻量 Cron 解析 | 只要 Cron 语法 |
| **Hangfire** | 持久化、失败重试、可视化仪表盘、分布式协调 | 任务多、要监控和重试 |
| **Quartz.NET** | 企业级集群调度、Cron、持久化 | 复杂集群调度 |

**选型判断**：手写调度器出现"任务执行结果没记录、失败没重试、多实例会重复跑"这些问题时，就该上 Hangfire 这类库了。
