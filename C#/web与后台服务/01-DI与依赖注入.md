# 01 DI 与依赖注入

> **系列**：web与后台服务 专题（通用）｜ **下一篇**：[[02-配置系统]]

### 背景

> 依赖注入（DI）是 .NET 应用——无论 Web 还是后台服务——最核心的基础设施。Controller、Service、Repository、HostedService，全是通过 DI 容器创建和管理的。
>
> 本篇讲透 DI 容器的完整原理：它是什么、怎么解析依赖、底层组件、实例生命周期、Scope，以及最常见的陷阱（CaptiveDependency）和解法（CreateScope）。

### 1. DI 容器：自动对象工厂

没有容器时，你手动 `new`，依赖链多长就得写多长：

```csharp
// ❌ 手动 new：依赖链一长就爆炸
var conn = new SqlConnection(connStr);
var dbContext = new AppDbContext(conn);
var repo = new ProductionOutputRepository(dbContext);
var service = new ProductionOutputService(repo, logger);
var orchestrator = new OrchestratorService(service, ...);
```

有了 DI 容器，只需两步：

```csharp
// ① 注册：告诉容器"这些类型归你管"
builder.Services.AddScoped<ProductionOutputRepository>();
builder.Services.AddScoped<OrchestratorService>();

// ② 解析：说一声"给我个 OrchestratorService"
var orchestrator = provider.GetRequiredService<OrchestratorService>();
// 容器自动把依赖链 new 齐
```

- 容器 = **注册表**（存了哪些类型）+ **工厂**（自动 new）
- 你 `Program.cs` 里那一大串 `AddScoped` / `AddSingleton` 就是"注册"
- 构造函数里直接写参数拿对象，就是"解析"的成果

### 2. 解析机制：递归 new 依赖链

`GetRequiredService<OrchestratorService>()` 背后发生了什么：

```
要 OrchestratorService
   ↓ 看它的构造函数
构造函数要：ProductionOutputRepository、ILogger<OrchestratorService>
   ↓ 先解析 ProductionOutputRepository
      它的构造函数要：AppDbContext
        ↓ 先解析 AppDbContext
          它的构造函数要：DbContextOptions
            ↓ 注册时已配置好，直接给
          凑齐 → new AppDbContext ✅
      凑齐 → new ProductionOutputRepository ✅
   ↓ 解析 ILogger（框架内置，直接给）✅
   ↓
凑齐 → new OrchestratorService ✅
```

一个常见坑：

- **依赖没注册** → 抛 `InvalidOperationException: No service for type 'xxx' has been registered`

### 3. 依赖分析靠反射

容器"分析依赖"靠的是**反射**——读构造函数的签名。但和 Java Spring 的用法有本质区别：


|              | Java Spring                       | .NET 内置 DI                            |
| -------------- | ----------------------------------- | ----------------------------------------- |
| 找依赖的方式 | 注解扫描（`@Autowired` + 包扫描） | **显式注册**（`AddScoped<T>` 手动登记） |
| 反射用在哪   | 扫注解 + 注入字段                 | **读构造函数签名 + 实例化**             |

两步：

1. **分析阶段（反射）**：用 `type.GetConstructors()` 找到构造函数，读它的参数类型列表——这就是"依赖分析"
2. **实例化阶段**：对每个参数递归解析，再用反射（老版本 `ConstructorInfo.Invoke`）或**表达式树编译的委托**（新版本，有缓存）来 `new`

一句话：**.NET 内置 DI = 显式注册 + 反射分析构造函数 + 递归解析参数 + 编译委托实例化**。它不做 Java 那种"扫描注解自动装配"。

### 4. 循环依赖

.NET 内置 DI **不支持循环依赖**，检测到就直接抛：

```
InvalidOperationException: A circular dependency was detected
for the service of type 'A'.
```

A 的构造函数要 B，B 的构造函数又要 A，解析时容器发现绕回来了，立刻报错——**没有** Java Spring 那种字段注入延迟解决，也没有 Autofac 那种属性注入半成品的机制。

**解决办法**（按推荐度）：

1. **重构**：拆出公共接口，打破环
2. **`Lazy<T>` 延迟解析**：`public MyService(Lazy<OtherService> other)` —— 用到时才解析
3. **工厂**：注入 `Func<T>` 或自定义工厂，需要时再拿
4. 换第三方容器（Autofac 等支持属性注入）

### 5. 底层组件：IoC / DI / 容器 + CallSite

三个层次，别混：

```
IoC（控制反转）          ← 原则："对象不自己 new 依赖，交给外部"
   └── DI（依赖注入）    ← 手段：通过构造函数/属性把依赖传进去
          └── DI 容器    ← 工具：自动完成"分析 + 创建 + 管理生命周期"
```

.NET 内置容器（`Microsoft.Extensions.DependencyInjection`）的核心组件：


| 组件                 | 作用                                         |
| ---------------------- | ---------------------------------------------- |
| `IServiceCollection` | 注册表，存一堆`ServiceDescriptor`            |
| `ServiceDescriptor`  | 一条注册记录（服务类型、实现类型、生命周期） |
| `ServiceProvider`    | 容器本体，负责解析                           |
| `CallSiteFactory`    | 把注册记录编译成"调用站点"并缓存，加速解析   |

**底层流程**：

```
① 注册：AddScoped<T>() → 往 ServiceCollection 加一个 ServiceDescriptor
② 构建：BuildServiceProvider() → 把描述编译成 CallSite（构造指令树）
③ 解析：GetService<T>() → 查 CallSite → 执行指令树（递归解析依赖 → new 对象）
```

其中 **CallSite（调用站点）** 是精髓：一棵"怎么构造这个对象"的**指令树**，首次解析时构建、之后缓存复用——这就是 .NET DI 解析快的原因。

**ASP.NET Core 和 Worker Service 用的就是这同一个容器**（`Microsoft.Extensions.DependencyInjection`），前面讲的反射、循环依赖、生命周期、Scope，在 Web 和 Worker 里完全一致。想换容器可以 `builder.Host.UseServiceProviderFactory(new AutofacServiceProviderFactory())`，但 99% 的项目内置容器够用。

### 6. 实例生命周期

> ⚠️ 别和"服务生命周期"搞混：
>
> - **实例生命周期**（本节）：Singleton / Scoped / Transient，讲的是**对象实例** new 几次、活多久
> - **服务生命周期**（见 [[12-生命周期与优雅关闭]]）：HostedService 的 `StartAsync` / `StopAsync`，讲的是**后台服务的启动和停止**
>
> 一个管"对象"，一个管"服务"。

容器在 new 对象的时候要决定两件事：**new 几次、活多久**。

#### Singleton：整个应用只 new 一次

- 第一次解析时创建，之后每次解析都返回**同一个实例**
- 活到进程结束
- ⚠️ 全局唯一 = 共享状态，内部有可变字段时多线程访问要加锁（见 [[03-C#并发与线程]]）

#### Scoped：每个 Scope 一个

- 同一个 Scope 内，多次解析返回**同一个实例**
- Scope 结束，实例被 Dispose
- `DbContext` 默认就是 Scoped

#### Transient：每次解析都 new

- 没有共享，用完交给 GC

**为什么 DbContext 默认是 Scoped？** 两个原因：

1. DbContext 内部有"变更追踪"，要保证一个工作单元（一个请求/一个任务）内看到一致的数据快照
2. DbContext 不是线程安全的，一个请求一个实例正好隔离并发

### 7. Scope：一次工作单元

容器是**树形结构**：

```
根容器（Singleton 住这里）
   ├── Scope 1（HTTP 请求 1 的 Scoped 住这里）
   ├── Scope 2（HTTP 请求 2）
   └── Scope 3（后台任务手动建的）
```

- **Web**：框架自动给每个 HTTP 请求建一个 Scope，请求结束销毁
- **Worker**：没有请求概念，要手动 `CreateScope()`
- Scope 结束 → 里面所有 `IDisposable` 的 Scoped 服务被依次 Dispose

**注意**：从 Scope 里解析 Singleton，返回的还是根容器那个唯一实例（Singleton 不归 Scope 管）。

### 8. CaptiveDependency：长命不能持有短命

矛盾来自实例生命周期的错配：

- 全局缓存服务 = **Singleton**（长命）
- DbContext = **Scoped**（短命）

如果把 DbContext 存进 Singleton 字段：

```csharp
public class AppCacheService {   // Singleton
    private readonly AppDbContext _db;   // Scoped 被 Singleton 永久拽住
    public AppCacheService(AppDbContext db) => _db = db;
}
```

后果：

1. **DbContext 越滚越大**：所有数据的变更追踪堆在一个实例里
2. **线程不安全**：多任务并发用同一个 DbContext 会崩
3. **ValidateScopes**：开发环境（Development）默认开启，检测到 Singleton 依赖 Scoped 会报 CaptiveDependency 警告

**三种生命周期混用规则**：


| 注入方 ↓ / 依赖 → | Singleton | Scoped      | Transient   |
| --------------------- | ----------- | ------------- | ------------- |
| Singleton           | ✅        | ❌ 捕获依赖 | ⚠️ 不推荐 |
| Scoped              | ✅        | ✅          | ✅          |
| Transient           | ✅        | ✅          | ✅          |

### 9. CreateScope：手动拿 Scoped

Singleton 要用 Scoped，就临时开一个 Scope：

```csharp
public class MySingletonService {
    private readonly IServiceProvider _sp;   // 注入根容器

    public void DoWork() {
        using var scope = _sp.CreateScope();                    // ① 开工作单元
        var provider = scope.ServiceProvider;                   // ② 拿 Scope 解析器
        var db = provider.GetRequiredService<AppDbContext>();   // ③ 解析 Scoped
        // ④ using 结束 → scope.Dispose → db.Dispose
    }
}
```

两种拿法（等价）：

```csharp
// 方式 1：注入 IServiceProvider（根容器）
using var scope = _sp.CreateScope();

// 方式 2：注入 IServiceScopeFactory（更语义化）
using var scope = _scopeFactory.CreateScope();
```

（`IServiceProvider.CreateScope()` 是扩展方法，内部就是调 factory，两者等价。）

### 10. 小结


| 概念              | 一句话                                              |
| ------------------- | ----------------------------------------------------- |
| DI 容器           | 注册表 + 自动工厂                                   |
| 解析              | 递归 new 依赖链                                     |
| 依赖分析          | 反射读构造函数（非 Java 注解扫描）                  |
| 循环依赖          | 直接抛异常，不支持                                  |
| 底层组件          | ServiceDescriptor + CallSite 指令树                 |
| 实例生命周期      | 对象 new 几次、活多久（Singleton/Scoped/Transient） |
| Scope             | 一次工作单元                                        |
| CaptiveDependency | 长命（Singleton）不能持有短命（Scoped）             |
| `CreateScope`     | Singleton 里手动开 Scope 拿 Scoped                  |
