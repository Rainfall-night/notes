# 15 部署

> **系列**：web与后台服务 专题（HostedService 专属）｜ **上一篇**：[[14-异常与崩溃监控]]

### 背景

> 后台服务（Worker）没有 HTTP 入口，**部署方式与 Web 完全不同**（Web 见 [[24-Web 部署]]）。本篇按顺序讲：环境配置（部署前先配好）→ 三大平台部署（Windows / Linux / Docker）→ 发布更新。每种方式都讲清原理和每条命令的含义。

### 1. Worker Service 模板

```bash
dotnet new worker -n MyWorker
```

- 这条命令用 dotnet CLI 的 worker 模板生成一个最小后台服务项目
- **生成了什么**：`Program.cs`（构建 Host）+ 一个 `Worker.cs`（`BackgroundService` 子类）+ `csproj`
- **为什么这么简单**：后台服务没有 UI、没有接口，就是一个"空壳进程"里塞你的循环逻辑
- **和 `dotnet new webapi` 的区别**：webapi 有 Controller、中间件、端口；worker 什么都没有，只有 Host + 循环

### 2. 跨平台宿主：AddWindowsService + AddSystemd

先理解一个背景：**一个 .NET 程序默认就是个普通进程**，双击就能跑。但"服务"（Windows Service / systemd service）有特殊待遇：

- 开机自启、由系统统一管理启停、崩溃自动重启、以特定账号运行

要让 .NET 程序"知道自己正被当服务跑"（能响应系统的停止信号、优雅关闭），就得注册下面这两个：

```csharp
builder.Services.AddWindowsService(options => {
    options.ServiceName = "DailyReportService";
});
builder.Services.AddSystemd();
```

- `AddWindowsService`：告诉 Host"如果我是被 Windows 服务管理器（SCM）拉起来的，就按服务模式工作"——能响应 SCM 的 stop 信号、触发优雅关闭
- `AddSystemd`：同理，Linux 上响应 systemd 的通知和停止

**为什么两个都注册**：运行时自动检测环境——Windows 用 Windows 服务模式，Linux 用 systemd 模式，同一份代码两个平台通用。

### 3. 环境与配置注入

- `DOTNET_ENVIRONMENT` / `ASPNETCORE_ENVIRONMENT`：切换 Production/Development，Host 会加载对应的 `appsettings.{env}.json` 覆盖基础配置
- **敏感信息**（密码、连接串）用**环境变量**注入，不写进配置文件（日报：`Database__MesPassword`、`Email__Password`；双下划线 `__` 表示配置层级分隔符）
- 注入方式：Windows 用系统环境变量，systemd 用 `Environment=` / EnvironmentFile，Docker 用 `environment:`

#### 配置优先级（重要）

.NET 的配置系统按**优先级**合并多个来源，**后者覆盖前者**：

```
appsettings.json
   → appsettings.{环境}.json      （如 appsettings.Production.json）
   → 用户机密（仅开发）
   → 环境变量
   → 命令行参数                    ← 最高
```

部署时记住这个规律：

- **默认值**放 `appsettings.json`
- **环境差异**放 `appsettings.{env}.json`
- **敏感/环境相关**用环境变量（优先级高，且不写死）
- 想临时覆盖某个值，命令行参数优先级最高

举例：`appsettings.json` 里 `Email:Password` 是默认值，生产环境用环境变量 `Email__Password=xxx` 覆盖它——环境变量优先级高，天然生效。

### 4. 部署

#### 4.1 Windows Service

**原理**：Windows 服务不是普通双击运行的 exe，它由"服务控制管理器（SCM）"统一管理——负责开机启动、响应 start/stop、崩溃恢复。

**1. 创建服务**：先告诉 SCM"有个服务叫 DailyReportService，它的 exe 在哪"：

```cmd
sc.exe create DailyReportService binPath="C:\publish\DailyReportService.exe"
sc.exe start DailyReportService
sc.exe stop DailyReportService
sc.exe delete DailyReportService
```

| 命令 | 含义 |
|---|---|
| `create ... binPath=...` | 在 SCM **注册**新服务，`binPath` 指定它运行哪个 exe（注册 ≠ 启动） |
| `start` | SCM 用注册时指定的账号把 exe 拉起来 |
| `stop` | SCM 发停止信号 → 触发程序的优雅关闭（`StopAsync`） |
| `delete` | 从 SCM 移除注册 |

**2. `sc.exe config`：修改已注册服务的配置**

`sc.exe create` 是"新建"，`sc.exe config` 是"改已有服务的属性"。语法强制：**`选项= 值` 里 `=` 后必须有个空格**：

```cmd
sc.exe config DailyReportService [option= value] ...
```

| 选项 | 配置什么 | 示例 |
|---|---|---|
| `start=` | 启动类型：`auto`（开机自启）/ `demand`（手动）/ `disabled`（禁用） | `sc.exe config DailyReportService start= auto` |
| `binPath=` | 服务运行的 exe/dll 路径 | `sc.exe config DailyReportService binPath= "C:\new\app.exe"` |
| `displayname=` | 服务显示名（服务管理器里看到的名字） | `sc.exe config DailyReportService displayname= "日报服务"` |
| `description=` | 服务描述 | `sc.exe config DailyReportService description= "每天生成生产日报"` |
| `obj=` | 服务以哪个账号运行 | `sc.exe config DailyReportService obj= ".\congang"` |
| `password=` | 上面账号的密码 | `sc.exe config DailyReportService password= "xxx"` |
| `error=` | 严重错误处理：`normal` / `severe` / `critical` / `ignore` | `sc.exe config DailyReportService error= severe` |
| `type=` | 服务类型：`own`（独立进程）/ `share`（共享进程） | `sc.exe config DailyReportService type= own` |

**坑 1：PowerShell 的 sc 是别名**

PowerShell 有个内置命令 `Set-Content`（写文件），它的简写就是 `sc`。你在 PowerShell 敲 `sc create ...`，PowerShell 优先认**自己的别名**，把 `create...` 当成"写文件的内容"——自然报"找不到参数"。解法：写全 `sc.exe`，或用 PowerShell 自带的 `Start-Service` / `Stop-Service`。

**坑 2：1069 登录权限**

`sc.exe create` / `sc.exe config` 的 `obj=` 可以指定服务以哪个账号身份运行。**普通账号默认没有"作为服务登录"（Log on as a service）这个 Windows 权限**——SCM 启动服务时验证账号权限，不通过就报 **1069**。解法：`secpol.msc` → 用户权限分配 → "作为服务登录" → 添加账号。

**坑 3：1053 工作目录（最坑）**

**为什么**：双击 exe 时，工作目录 = exe 所在目录；但服务是 SCM 拉起的，SCM 不设置工作目录，Windows 默认给服务的当前目录是 `C:\Windows\System32`。于是配置里的相对路径（`./Data/`、`Logs/`）全解析到 System32 → 无权限 → 启动崩溃。

**为什么难查**：崩溃发生在日志初始化**之前**，日志根本没写出来，事件查看器也没有 .NET 错误——只报 **1053"服务没有及时响应"**，无从查起。

```csharp
// 解法：Program.cs 最开头强制工作目录 = exe 所在目录
Directory.SetCurrentDirectory(AppContext.BaseDirectory);
```

**坑 4：CET 兼容（Windows 10）**

CET（控制流强制技术）是 CPU 硬件安全特性，.NET 10 默认启用，但 **Windows 10 内核不支持** → 运行直接报 `Fatal error. Your Windows doesn't fully support CET`。在 `.csproj` 加 `<CETCompat>false</CETCompat>`（编译期生效；环境变量 `DOTNET_EnableCET=0` 无效——因为 CET 检查发生在运行时启动之前，配置文件还没加载）。

**失败自动重启（Recovery）**

服务崩溃后，SCM 默认**什么都不做**（服务就停在那了）。配置"恢复"策略后，崩溃会自动重启——这就是 Windows 层的"看门狗"：

```cmd
sc.exe failure DailyReportService reset= 86400 actions= restart/5000/restart/5000
```

（或：服务属性 → "恢复"标签页，配置"第一次失败：重启服务"）

#### 4.2 Linux Systemd

**原理**：Linux 上管理常驻后台进程的是 **systemd**（取代老式的 init）。每个服务写一个 `.service` 文件，systemd 按它来启动、监控、重启——**systemd 就是 Linux 的"SCM"**。

`/etc/systemd/system/myworker.service`：

```ini
[Service]
Type=simple                    # 启动方式：simple = 主进程就是服务本身（启动即算成功）
WorkingDirectory=/opt/myworker # 设置工作目录（从根上避免 1053 那种相对路径问题）
ExecStart=/usr/bin/dotnet /opt/myworker/MyWorker.dll  # 启动命令
Restart=on-failure             # 崩溃自动重启（systemd 层的看门狗）
RestartSec=5                   # 重启间隔 5 秒
```

```bash
sudo systemctl daemon-reload    # 改完 .service 必须重新加载，systemd 才读到新配置
sudo systemctl enable myworker  # 开机自启（在 multi-user.target.wants 下建软链）
sudo systemctl start myworker   # 启动
sudo systemctl status myworker  # 看状态（是 running 还是 failed）
journalctl -u myworker -f       # 看日志（systemd 统一收集所有服务的输出，-f 跟随）
```

`Restart=on-failure` 就是 systemd 层的"看门狗"（对应 [[05-异常处理]] 的看门狗思想）。

#### 4.3 Docker

**原理**：**Docker 把"应用 + 运行环境"打包成镜像，跑成容器**。镜像分两阶段——用带编译器的 `sdk` 镜像编译，再用只带运行时的 `aspnet` 镜像运行（后者小得多，没有编译器）：

```dockerfile
FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build   # 阶段 1：sdk 镜像（有编译器）
WORKDIR /src
COPY . .
RUN dotnet publish -c Release -o /app/publish      # 编译产物

FROM mcr.microsoft.com/dotnet/aspnet:10.0          # 阶段 2：aspnet 镜像（只带运行时）
WORKDIR /app
COPY --from=build /app/publish .                   # 从阶段 1 拷贝产物
ENTRYPOINT ["dotnet", "MyWorker.dll"]              # 容器启动时执行的命令（前台运行）
```

- **为什么没有 `EXPOSE`**：Worker 不监听端口，是"无入口的常驻进程"
- **为什么用 `ENTRYPOINT`**：容器里的程序必须**前台运行**（阻塞住），如果写成后台会立刻退出——和 Windows 服务相反，Docker 容器"主进程退出 = 容器结束"

```yaml
services:
  worker:
    build: .
    restart: always                      # 容器退出自动重启（Docker 的看门狗）
    environment:
      - DOTNET_ENVIRONMENT=Production
```

```bash
docker logs worker -f        # 看日志（对应 journalctl / 事件查看器）
```

### 5. 发布与更新流程

通用前提：`dotnet publish -c Release -o ./publish` 编译成可部署产物。

#### 5.1 Windows

**为什么更新必须先停服务**：服务运行时 exe 被进程**占用**，Windows 不允许覆盖运行中的文件——直接复制报"文件被占用"。

```cmd
sc.exe stop DailyReportService    # ① 停（释放文件占用）
# ② 覆盖 publish 目录下的文件
sc.exe start DailyReportService   # ③ 启
```

#### 5.2 Linux

同理，systemd 运行时进程占用 dll，需先停再覆盖：

```bash
sudo systemctl stop myworker      # ① 停
# ② 覆盖 /opt/myworker 下的文件
sudo systemctl start myworker     # ③ 启
```

#### 5.3 Docker

容器化没有"文件占用"问题——直接构建新镜像、重建容器即可：

```bash
docker build -t myworker:latest .   # 构建新镜像
docker compose up -d --build        # 重建容器
```

### 6. 小结

| 知识点 | 一句话 |
|---|---|
| Worker 模板 | `dotnet new worker` |
| 跨平台宿主 | `AddWindowsService` + `AddSystemd`（运行时自动检测） |
| 配置 | 优先级：appsettings < 环境变量 < 命令行 |
| Windows | `sc.exe create` + `sc.exe config`（start/obj/displayname...）+ 四坑 |
| 自动重启 | Recovery / `Restart=on-failure` / `restart: always` |

| 更新 | Windows/Linux 停→覆盖→启；Docker 重建镜像 |
