# C# 内存与 GC

> **系列**：C# 学习笔记（内存与 GC 专题）｜ **上级**：[[02-C#高阶]] 第 8 课
> **说明**：结合 `STWebsiteBackEnd_V2` 项目实际场景讲解。

## 1. 栈 vs 堆

### 1.1 内存分两大区域


|        | 栈（Stack）                  | 堆（Heap）           |
| -------- | ------------------------------ | ---------------------- |
| 存什么 | 值类型、方法局部变量、调用帧 | 引用类型对象         |
| 大小   | 小（默认 1MB 左右）          | 大（整个可用内存）   |
| 速度   | 快（栈顶指针移动）           | 慢（要查找空闲空间） |
| 释放   | 自动（方法返回就弹栈）       | GC 管理              |

### 1.2 值类型在栈，引用类型对象在堆

```csharp
void Method() {
    int x = 10;                 // 值类型 → 直接放栈上
    var list = new List<int>(); // 引用类型：list 变量在栈，对象在堆
}
```

```
栈                    堆
┌─────────────┐     ┌──────────────────┐
│ x = 10      │     │ List<int> 对象     │
│ list ───────┼────▶│  (实际数据在堆)     │
└─────────────┘     └──────────────────┘
```

- 值类型（int/bool/DateTime/struct）：数据直接在栈上
- 引用类型（class/List 等）：变量（引用）在栈，对象本身在堆

### 1.3 栈为什么快、堆为什么慢

- 栈像"叠盘子"：方法调用压帧、返回弹帧，栈顶指针移动，极快
- 堆像"大仓库找空地"：分配时要找足够大的空闲块、记录占用，慢

### 1.4 呼应基础篇第 1 课

值类型 vs 引用类型，从内存角度看：

```
值类型   → 数据在栈（随方法结束自动消失）
引用类型 → 对象在堆（需要 GC 回收）
```

也解释了"复制行为"：值类型复制"值"（栈上拷一份），引用类型复制"地址"（栈上两个变量指向堆上同一对象）。

### 1.5 调用栈 + 栈帧（图示）

每个方法调用在栈上压一个栈帧（局部变量 + 参数 + 返回地址）：

```
方法调用链：Main() → MethodA() → MethodB()

栈顶 ↑（当前执行 MethodB）
┌───────────────────┐
│ MethodB 的栈帧      │
│  ├ 局部变量         │
│  ├ 参数             │
│  └ 返回地址         │
├───────────────────┤
│ MethodA 的栈帧      │
├───────────────────┤
│ Main 的栈帧        │
└───────────────────┘
栈底 ↓
```

压栈：方法调用压帧；弹栈：方法返回弹帧，局部变量自动消失——所以栈"不可能泄漏"。

### 1.6 栈为什么快：栈顶指针

栈分配/释放只是移动指针：

```
分配前：   ┌──────┐ ← 栈顶指针
           │ 空闲  │
分配后：   ┌──────┐
           │新数据 │ ← 栈顶指针（上移）
           │ 空闲  │
```

无碎片、无查找，一条指令搞定。

### 1.7 完整图示：值类型 vs 引用类型

```csharp
void Method() {
    int a = 10;                  // 值类型
    string name = "hello";       // 引用类型
    var list = new List<int>();  // 引用类型
}
```

```
栈（Method 的栈帧）                堆
┌────────────────┐              ┌────────────────┐
│ a = 10         │              │ "hello" 字符串   │
│ name ──────────┼─────────────▶│                │
│ list ──────────┼──┐           ├────────────────┤
└────────────────┘  │           │ List<int> 对象   │
                    └──────────▶│                │
                                └────────────────┘
```

- a = 10：值直接存在栈上
- name：栈上存字符串对象的地址，字符串本身在堆
- list：栈上存 List 对象的地址，List 本身在堆

### 1.8 struct vs class（决定内存位置）


|          | struct                   | class    |
| ---------- | -------------------------- | ---------- |
| 本质     | 值类型                   | 引用类型 |
| 内存位置 | 直接放栈（或内嵌对象里） | 对象放堆 |
| 复制     | 整体拷贝                 | 拷贝引用 |

### 1.9 装箱：值类型"跑"到堆上

```csharp
object o = 10;   // 装箱：int 值被包装成堆对象
```

```
栈                    堆
┌──────────┐        ┌───────────────┐
│ o ───────┼───────▶│ 装箱的 int（10） │
└──────────┘        └───────────────┘
```

装箱 = 值类型包成堆对象，有性能开销（分配堆内存 + 拷贝值），基础篇 1.6 说的"用泛型避免装箱"就为这个。

### 1.10 为什么"栈不泄漏、堆会泄漏"


|          | 栈                           | 堆                                                   |
| ---------- | ------------------------------ | ------------------------------------------------------ |
| 释放     | 方法返回自动弹帧，不可能泄漏 | 靠 GC 判断没人引用才回收                             |
| 泄漏条件 | 无                           | 对象一直被引用（static 字段、事件订阅）→ 永远不回收 |

堆的"内存泄漏"本质：不是"忘了删"，而是"对象没用了却还被引用指着，GC 不敢回收"。

## 2. GC 是什么（托管堆 + 自动回收 + 可达性分析）

### 2.1 一句话：GC 帮你"删"堆上的垃圾

GC = Garbage Collector（垃圾回收器），是 .NET 运行时（CLR）内置的一个组件。

```csharp
var list = new List<int>();   // 只负责 new，不负责 delete
```

- **C/C++**：`malloc` 之后必须手动 `free`，忘了就泄漏，释放早了就崩溃
- **C#**：只管 `new`，堆上的对象不用了，GC 自动判断、自动回收

你写代码时从没写过"删除对象"的代码，背后就是 GC 在干活。

### 2.2 没有 GC 的世界：C/C++ 的两大经典错误

```c
int* p = (int*)malloc(100 * sizeof(int));  // 手动申请堆内存

// 错误 1：忘记 free → 内存泄漏（内存被占着，永远回不来）
// free(p);

free(p);   // 手动释放

// 错误 2：释放后继续用 p → 悬空指针（野指针），程序崩溃
p[0] = 10;
```


| 错误          | 后果                             |
| --------------- | ---------------------------------- |
| 忘记 free     | 内存泄漏，越跑越慢，最终内存耗尽 |
| free 后继续用 | 悬空指针，访问已释放内存，崩溃   |

GC 的价值就是**同时消灭这两个错误**：不让你手动 free，也不存在"悬空指针"——因为对象只要还可能被用到，GC 就不会回收它（可达性分析保证）。

### 2.3 GC 管什么、不管什么


| 内存/资源      | 谁管                       | 举例                               |
| ---------------- | ---------------------------- | ------------------------------------ |
| 栈上的局部变量 | 运行时自动（方法返回弹栈） | `int x = 10;`                      |
| 托管堆的对象   | **GC**                     | `new List<int>()`、`new Order()`   |
| 非托管资源     | **程序员自己**（Dispose）  | 文件句柄、数据库连接、DES 加密句柄 |

关键结论：**GC 只管"托管堆"，栈它不管（自动弹栈），非托管资源它管不了（要靠 Dispose）**。

### 2.4 可达性分析：怎么判断"谁是垃圾"

GC 不是靠"猜"，而是用**可达性分析**：

1. 找出所有**根（GC Roots）**：栈上的局部变量、`static` 静态字段、CPU 寄存器
2. 从根出发，沿着引用一路标记，能标记到的对象 = **可达**（还活着）
3. 标记不到的 = **不可达**（垃圾），整片回收

```
根（GC Roots）：栈上的引用变量 + static 字段

  栈：obj1 ──▶ [对象A] ──▶ [对象B]    ✅ 可达，保留
  栈：obj2 ──▶ [对象C]                 ✅ 可达，保留
               [对象D]                  ❌ 没人指向 → 垃圾，回收
```

**呼应 1.10**：堆的"泄漏"本质 = 对象没用了，却还被根指着（比如 `static` 字段一直引用），GC 误以为它"可达"，不敢回收。

### 2.5 项目实景：`DES.Create()` 为什么必须 `using`

项目里同一段 DES 解密，新老两个版本对比：

**新版 `DecryptDes.cs`（正确）：**

```csharp
using var des = DES.Create();        // 用完自动释放
des.Key = key;
des.Mode = CipherMode.ECB;
using var dec = des.CreateDecryptor();  // 解密器也要释放
byte[] plain = dec.TransformFinalBlock(cipher, 0, cipher.Length);
```

**老版 `DESHelper.cs`（有隐患）：**

```csharp
DES dES = DES.Create();   // 没 Dispose，句柄泄漏风险
var r = dES.CreateDecryptor().TransformFinalBlock(source, 0, source.Length);
```

为什么必须 `using`：

- `DES.Create()` 底层调用**操作系统加密接口（CryptoAPI）**，返回的对象内部持有**非托管句柄**
- GC 管不了这个句柄——句柄在操作系统手里，不在托管堆上
- 如果只靠 GC：对象要等 GC 触发才回收，这期间句柄一直占着；而系统句柄是**有限资源**，大量请求下会耗尽
- 所以要用 `using`/`Dispose` **立即**释放句柄（完整机制见第 5 节）

一句话：**GC 管托管对象，`Dispose` 管非托管资源，两者分工不同**。

### 2.6 GC 什么时候回收？（预告第 3 节）

GC **不是用完立刻回收**，而是"它觉得该收才收"：

- 第 0 代内存分配满了 → 触发
- 系统内存压力大 → 触发
- 手动调 `GC.Collect()`（生产环境不建议）→ 触发

触发条件与"三代回收"机制密不可分，放在第 3 节一起讲。

## 3. GC 的三代回收（0/1/2 代 + 大对象堆 + 触发时机）

### 3.1 为什么要分代：大部分对象都很短命

统计规律（弱分代假说）：**大多数对象刚创建不久就没用了，只有少数对象长寿**。

```csharp
public ExecuteResult<Order> GetOrder(int id) {
    var dto = new OrderDto();          // 短命：方法结束就没人引用
    var query = new OrderQuery();      // 短命
    var result = _repo.Get(id);        // 短命
    return new ExecuteResult<Order>(result);  // 短命（序列化成 JSON 后也没用了）
}
```

- Web API 里，**每次请求产生的 DTO、临时字符串、局部变量**，绝大多数"英年早逝"
- 极少数长寿：注册的单例服务、静态缓存、全局配置

如果 GC 每次都扫描**整个堆**找垃圾，等于天天在大仓库里翻箱倒柜，太慢。
分代的思路：**新生对象单独放一块，优先、高频回收这一小块**，扫描范围小、速度快。

### 3.2 三代怎么划分


| 代          | 装谁                           | 特点                         |
| ------------- | -------------------------------- | ------------------------------ |
| **第 0 代** | 刚`new` 的、从没熬过一次 GC 的 | 最新，回收最频繁、最快       |
| **第 1 代** | 熬过一次 GC 幸存下来的         | 过渡层                       |
| **第 2 代** | 熬过两次以上 GC 的             | 长寿对象：单例、static、缓存 |

```
托管堆（按代分块）
┌──────────────────────────────┐
│ 第 0 代（新生对象）            │ ← 最先回收，频率最高
├──────────────────────────────┤
│ 第 1 代（熬过 1 次）           │
├──────────────────────────────┤
│ 第 2 代（长寿对象）            │ ← 最后才回收，频率最低
└──────────────────────────────┘
```

### 3.3 回收过程：幸存者"晋升"

规则：**每熬过一次 GC，对象就升一代**。

演算过程（假设只有 3 个对象 A、B、C）：

```
初始：A、B、C 都在 0 代

第 1 次 GC（回收 0 代）：
  A 没人用 → 回收 ❌
  B、C 还活着 → 晋升到 1 代

第 2 次 GC（回收 0 代和 1 代）：
  B 没人用了 → 回收 ❌
  C 还活着 → 晋升到 2 代

第 3 次 GC 起：C 属于 2 代，只有"完全回收（full GC）"才会碰它
```

关键逻辑：

1. 先回收 **0 代**，幸存者升 **1 代**
2. 0 代再次满了，回收 **0 代 + 1 代**，幸存者升 **2 代**
3. 只有 **full GC**（完全回收）才会连 2 代一起扫

**为什么不一开始就全扫？** 因为大部分垃圾都在 0 代，先扫 0 代就清掉 90% 垃圾了，又快又省。

### 3.4 大对象堆（LOH）：大块头走特殊通道

- 阈值：**85000 字节（约 83 KB）** 以上的对象，不放进 0/1/2 代，直接进 **LOH（Large Object Heap，大对象堆）**
- 典型：大数组、大字符串、大 `byte[]`（比如文件内容、Base64 图片）

```csharp
byte[] fileBytes = File.ReadAllBytes(path);   // 几 MB → 进 LOH
string bigJson = JsonSerializer.Serialize(hugeList); // 超大字符串 → 进 LOH
```

LOH 的特殊性：


| 特性            | 说明                                                       |
| ----------------- | ------------------------------------------------------------ |
| 不参与 0/1/2 代 | 独立区域，回收频率低（跟随 2 代回收）                      |
| 默认**不压缩**  | 大对象搬来搬去拷贝成本太高，只标记清除 → 容易产生**碎片** |

碎片问题：反复分配/释放大对象，LOH 会像"狗啃过的饼"，中间留下小空隙，大对象塞不进去，导致内存越用越多。

### 3.5 什么时候触发 GC（完整版）


| 触发条件            | 说明                                            |
| --------------------- | ------------------------------------------------- |
| **0 代预算耗尽**    | 最常见。0 代分配新对象达到阈值 → 触发 0 代回收 |
| 1 代 / 2 代预算耗尽 | 对应触发 1 代 / full GC                         |
| 系统内存不足        | 操作系统报告内存紧张 → CLR 主动 full GC        |
| `GC.Collect()`      | 手动强制（生产环境强烈不建议，会打断所有线程）  |
| 其他                | AppDomain 卸载、进程关闭等                      |

### 3.6 项目实景：对象寿命分布

`STWebsiteBackEnd_V2` 里，对象寿命正好对应三代：


| 对象                                     | 寿命           | 去向             |
| ------------------------------------------ | ---------------- | ------------------ |
| 每次请求的 DTO、`OrderQuery`、临时字符串 | 请求结束就没用 | 0 代，高频回收   |
| 偶尔跨请求存活的中转对象                 | 中等           | 1 代             |
| `Program.cs` 注册的单例服务、静态配置    | 进程级         | 2 代，几乎不回收 |
| Excel 导出的`byte[]`、Base64 图片        | 大对象         | LOH              |

### 3.7 代越大，回收越贵


| 回收                | 范围         | 耗时                | 影响                    |
| --------------------- | -------------- | --------------------- | ------------------------- |
| 0 代回收            | 只扫 0 代    | 极快（微秒~毫秒级） | 几乎无感                |
| 1 代回收            | 扫 0 + 1 代  | 较快                | 无感                    |
| **full GC（2 代）** | 扫全部 + LOH | 慢（可达几百毫秒）  | **暂停所有线程（STW）** |

**结论**：性能优化的一大目标就是——**让对象尽量死在 0 代，别让它活到 2 代**。这样 GC 永远只做最便宜的 0 代回收，不触发昂贵的 full GC。（具体手法见第 7 节）

## 4. GC 的类型（Workstation / Server / Background / 大对象压缩）

> 一句话建立大图景：Java 有一堆可以换的收集器，.NET 只有一套分代 GC，但可以调"模式"。

### 4.1 Java 的收集器（简单了解即可）

Java 有多个**彼此独立**的收集器，每个算法完全不同，用启动参数换整套算法：


| 收集器   | 特点                 |
| ---------- | ---------------------- |
| Serial   | 单线程，小内存客户端 |
| Parallel | 多线程，吞吐优先     |
| CMS      | 并发，已废弃         |
| G1       | 区域化，JDK 9+ 默认  |
| ZGC      | 亚毫秒暂停，超大堆   |

切换：`-XX:+UseG1GC`、`-XX:+UseZGC`。**Java 是"换发动机"**，本笔记简单带过，重点讲 .NET。

### 4.2 .NET 的模式（重点）

.NET 的 GC **核心算法固定**（分代 + 标记清除/压缩），换不了算法，但有 4 个可调维度：

#### 4.2.1 Workstation GC vs Server GC（最重要的开关）


| 模式            | 堆结构          | GC 线程   | 追求   | 适合              |
| ----------------- | ----------------- | ----------- | -------- | ------------------- |
| **Workstation** | 1 个堆          | 少量      | 低停顿 | 桌面 / 客户端     |
| **Server**      | 每逻辑核 1 个堆 | 每核 1 个 | 高吞吐 | Web 服务 / 服务器 |

底层细节：

- Server GC 给**每个逻辑核分配一个独立的堆 + 一个 GC 线程**
- 回收时各核**并行收自己的堆**，互不等待 → 吞吐量高
- 代价：单次暂停略长、整体内存占用略多（每个堆都要有各自的 0/1/2 代）

配置（二选一）：

```xml
<PropertyGroup>
  <ServerGarbageCollection>true</ServerGarbageCollection>
</PropertyGroup>
```

环境变量：`DOTNET_gcServer=1`（容器部署常用）

#### 4.2.2 Background GC（后台 GC，默认开启）

- 让 0/1 代回收跑到**后台线程**执行，与应用程序并发运行
- 效果：把"暂停所有线程（STW）"的时间大幅压缩
- 默认开启，一般不用动

#### 4.2.3 大对象堆压缩（LOH Compaction）

- 默认 LOH **不压缩**（见 3.4），反复分配/释放大对象会产生碎片
- 可设 `GCSettings.LargeObjectHeapCompactionMode` 手动要求压缩
- 代价：压缩大对象拷贝成本高，暂停变长

#### 4.2.4 .NET 8 新特性

- **DATAS**（动态适应应用大小）：根据实际内存自动调整堆大小，默认开启
- **Region GC**（实验性）：区域化回收，思想类似 Java 的 G1，仍在演进

### 4.3 小结：Java vs .NET


| 维度     | Java               | .NET                          |
| ---------- | -------------------- | ------------------------------- |
| 选型方式 | 换整个收集器       | 调模式                        |
| 算法     | 各收集器算法不同   | 分代算法固定                  |
| 配置入口 | JVM 启动参数`-XX:` | `csproj` / `DOTNET_` 环境变量 |

一句话：**Java 是"货架上有好几种发动机可以换"，C# 是"一台发动机，只能调挡位"**。

## 5. IDisposable + using（非托管资源）

### 5.1 为什么需要 IDisposable：GC 的盲区

回顾第 2 课结论：**GC 只管托管堆，非托管资源管不了**。

非托管资源 = 操作系统手里的**有限资源**：


| 资源           | 项目里的例子                        |
| ---------------- | ------------------------------------- |
| 加密句柄       | `DES.Create()`                      |
| 文件句柄       | `FileStream`、`StreamWriter`        |
| Excel/GDI 句柄 | FreeSpire.XLS 的`Workbook`          |
| 数据库连接     | `SqlConnection`（EF Core 内部持有） |
| 网络套接字     | `HttpClient`、`Socket`              |

这类资源有两个特点：

1. **在操作系统手里**，GC 看不到、管不了
2. **数量有限**（比如系统句柄表有上限），占着不还会耗尽

如果只等 GC：对象可能很久才被回收，这期间句柄一直被占着 → 高并发下句柄耗尽 → 程序崩。所以需要一种"用完立即释放"的机制，这就是 `IDisposable`。

### 5.2 IDisposable 接口：就一个方法

```csharp
namespace System {
    public interface IDisposable {
        void Dispose();
    }
}
```

- 整个接口只有一个 `Dispose()` 方法
- 约定：实现 `IDisposable` = "我持有需要手动释放的资源，用完请调 `Dispose()`"
- 谁来调：程序员（直接调），或 `using`（语法糖自动调）

### 5.3 using 的两种写法

**写法一：using 块（传统）**

```csharp
using (var des = DES.Create()) {
    des.Key = key;
    // ... 用 des
}   // 出花括号，自动 Dispose
```

**写法二：using 声明（C# 8+，项目 `DecryptDes.cs` 用的就是这种）**

```csharp
using var des = DES.Create();
des.Key = key;
byte[] plain = dec.TransformFinalBlock(cipher, 0, cipher.Length);
// 方法结束（离开作用域）自动 Dispose
```

区别：


|          | using 块             | using 声明             |
| ---------- | ---------------------- | ------------------------ |
| 释放时机 | 出花括号**立即**释放 | **方法结束**才释放     |
| 控制粒度 | 细（精确控制释放点） | 粗（跟方法作用域绑定） |

⚠️ `using` 声明的坑：方法很长时，资源会一直占到方法结束才释放。短方法用它很爽，长方法建议用 `using` 块精确控制释放点。

### 5.4 using 的本质：try-finally

`using` 不是魔法，编译器把它翻译成 `try-finally`：

```csharp
var des = DES.Create();
try {
    des.Key = key;
    // ... 用 des
} finally {
    des.Dispose();   // 无论正常还是抛异常，都执行
}
```

关键：**`finally` 保证无论是否抛异常，`Dispose` 一定执行**。这就是 `using` 比手动 Dispose 强的地方——手动写很容易漏掉异常路径的释放。

### 5.5 标准 Dispose 模式（完整模板）

自己写一个持有资源的类，要按微软官方 Dispose Pattern：

```csharp
public class MyResource : IDisposable {
    private bool _disposed = false;

    // 公开入口：程序员/using 调这里
    public void Dispose() {
        Dispose(true);
        GC.SuppressFinalize(this);
    }

    // 核心：disposing 区分"主动释放"还是"终结器兜底"
    protected virtual void Dispose(bool disposing) {
        if (_disposed) return;          // 防重复释放
        if (disposing) {
            // 释放托管资源（内部持有的 IDisposable 字段）
            _managedResource?.Dispose();
        }
        // 释放非托管资源（句柄、指针）——两种情况都必须做
        ReleaseUnmanagedResource();
        _disposed = true;
    }

    // 终结器：兜底，用户忘 Dispose 时由 GC 触发
    ~MyResource() {
        Dispose(false);
    }
}
```

模板要点：


| 要点                      | 说明                                                                           |
| --------------------------- | -------------------------------------------------------------------------------- |
| `_disposed` 标志          | 防止重复 Dispose（重复释放句柄会出问题）                                       |
| `Dispose(bool disposing)` | `true` = 人主动调；`false` = GC 终结器调                                       |
| 托管资源                  | 只在`disposing == true` 时释放（终结器阶段托管字段可能已被 GC 回收，不能再碰） |
| 非托管资源                | 两种情况**都必须**释放                                                         |

### 5.6 终结器（Finalizer）：兜底保险

```csharp
~MyResource() {   // 析构器 = 终结器
    Dispose(false);
}
```

- 作用：万一程序员忘了 Dispose，GC 回收对象前会调终结器**兜底**释放非托管资源
- 代价（重要）：
  1. 带终结器的对象回收要走**终结队列**，需要**两轮 GC** 才能真正回收 → 慢
  2. 终结器在专用线程上跑，执行顺序不确定

所以终结器是"保险"，不是"常态"——能 Dispose 就 Dispose，别指望终结器。

### 5.7 GC.SuppressFinalize：为什么必须调

```csharp
public void Dispose() {
    Dispose(true);
    GC.SuppressFinalize(this);   // 关键
}
```

- `GC.SuppressFinalize(this)` = 告诉 GC："这个对象我已经手动 Dispose 过了，**别再调它的终结器了**"
- 效果：对象从终结队列里摘出来，回收只要**一轮 GC**，快
- 不调的话：Dispose 之后 GC 还会白白再跑一遍终结器（重复释放 + 慢）

### 5.8 项目实景：三个例子

**① `DecryptDes.cs`（正确 ✅）**

```csharp
using var des = DES.Create();          // 加密对象用完自动释放
using var dec = des.CreateDecryptor(); // 解密器也要释放
```

两个资源都 `using`，正确。

**② `ExcelService.cs`（有隐患 ⚠️）**

```csharp
var workbook = new Workbook();   // FreeSpire 的 Workbook 持有 GDI 句柄
// ... 一堆操作 ...
workbook.SaveToStream(stream);   // 保存完没有 workbook.Dispose()
return stream;
```

`Workbook` 实现了 `IDisposable`，但导出完**没 Dispose** → 每次导出泄漏一个 Excel 句柄，高并发导出会累积句柄。

**③ `FileLogger.cs`（半对 ⚠️）**

`_sw`（`StreamWriter` + `FileStream`）持有文件句柄，只在日志滚动时 Dispose 旧的；`FileLogger` 自身没实现 `IDisposable`，进程结束时最后一个 `_sw` 没主动释放（进程退出时 OS 会兜底回收，但属于不规范）。

### 5.9 一句话总结

> GC 管托管对象，`Dispose` 管非托管资源。持有句柄/连接/流的类，要么 `using` 它，要么自己实现 `IDisposable`。

## 6. 常见内存问题（泄漏 / 装箱 / 大对象 / 静态引用）

### 6.1 托管内存泄漏的真相

再强调一次（呼应 1.10）：**托管堆的"泄漏"不是"忘了删"，而是"对象没用了却还被 GC Root 指着"**。

对象只要还能从根（静态字段、栈变量、事件订阅）找到，GC 就认为它"可达"，永远不会回收。所以泄漏排查的思路不是"找 delete"，而是**找多余的引用链**。

### 6.2 泄漏场景 1：无界静态缓存

```csharp
static Dictionary<int, Order> _cache = new();   // 只 Add 不 Remove → 无限增长
```

- `static` 字段是**进程级 GC Root**，永远可达 → 里面的对象**永远不回收**
- 只要这个字典一直往里塞，内存就一直涨

**项目对照**：

- ✅ `EnumTool.cs` 的 `_enumCache` 是"合理缓存"：键是枚举类型，**种类有限**，每个类型只缓存一次，总量有上限，不会无限增长
- ⚠️ `Logger.cs` 的 `LogQueues`（静态 `Queue<string>`）是"风险缓存"：日志**生产速度 > 写盘消费速度**时，队列无限增长 → 内存持续上涨

**判据**：静态集合是否安全，看它**有没有增长上限**。有上限 = 缓存；无上限 = 定时炸弹。

### 6.3 泄漏场景 2：事件订阅没退订

```csharp
publisher.Event += handler;   // 订阅了
// 之后从不 -= ，publisher 一直引用 handler
```

- 事件订阅 = publisher 持有一条指向订阅者的**隐式引用链**
- 只要 publisher 还活着（尤其 publisher 是长命对象），订阅者对象就**永远可达**，回收不了

**项目对照**：`Seed.cs` 里 `SeedOffset_GetIDWithDate += AddOffset;` 这类委托链订阅——若这些静态委托没在合适的时机 `-=` 退订，被订阅的方法所在对象就跟着常驻。

**规则**：长命对象（static/单例）订阅了短命对象的方法，短命对象用完后必须退订，否则泄漏。

### 6.4 泄漏场景 3：单例持有作用域对象（DI 陷阱）

```csharp
// 反例：单例服务注入 Scoped 的 DbContext
public class MySingletonService {          // 单例，进程级常驻（2 代）
    private readonly AppDbContext _db;      // Scoped，本该每个请求一个
    public MySingletonService(AppDbContext db) => _db = db;   // ❌
}
```

- 单例是**进程级**对象，`DbContext` 是 **Scoped**（每请求一个）
- 单例把 `DbContext` 当字段存着 → 第一个请求的 `DbContext` 被单例永久引用 → **所有请求的实体都堆在一个 DbContext 里**，越滚越大
- ASP.NET Core 默认会报 **CaptiveDependency**（捕获依赖）验证警告

**规则**：**长寿命对象不能持有短寿命对象**。单例只能注入单例；Scoped 只能注入 Scoped/单例；Transient 随便。

### 6.5 问题 4：装箱过多

回顾 1.9：**装箱 = 值类型包成堆对象**（分配堆内存 + 拷贝值）。

```csharp
object o = 10;           // 一次装箱：int → 堆对象
List<object> list = new();
for (int i = 0; i < 100000; i++)
    list.Add(i);         // 10 万次装箱：10 万个堆对象 + GC 压力
```

- 大量装箱 → 堆对象暴增 → GC 回收压力大 → full GC 变频繁
- 解法：用泛型 `List<int>` 避免装箱

**项目对照**：`ExcelService.cs` 优化前用反射 `GetValue` 取值，每格都装箱成 `object`；后来优化成 `CompileGetter` 编译委托（见 `ExcelService代码备份.md`），本质就是为了消除反射 + 减少装箱。

### 6.6 问题 5：大对象堆（LOH）碎片

回顾 3.4：**LOH 默认不压缩**，只标记清除 → 反复分配/释放大对象会留下碎片。

```csharp
// 反复分配、释放大 byte[]（几 MB），LOH 被"狗啃"得支离破碎
for (...) {
    byte[] big = new byte[10 * 1024 * 1024];   // 10 MB → LOH
    // ... 用完 big 失去引用，但 LOH 的空洞补不回
}
```

- 后果：**总内存够，但连续空间不够** → 大对象分配失败 → OOM
- 项目对照：Excel 导出的 `MemoryStream`/`byte[]`、文件读写缓冲，都属于大对象

**对策**（详见第 7 节）：大对象池化复用（`ArrayPool<byte>`），避免反复分配释放。

### 6.7 问题 6：循环里字符串拼接

`string` 是**不可变**的，每次 `+=` 都生成一个新字符串：

```csharp
string s = "";
for (int i = 0; i < 10000; i++)
    s += i + ",";          // 每次都复制整个旧串 + 新内容 → O(n²) 分配
```

- n 次拼接产生 n 个中间字符串，总复制量 O(n²)，大量垃圾进 0 代
- 解法：`StringBuilder`

**项目对照**：`ReportService.cs` 里大量 `returnString += ...`、`result.Content += ...` 循环拼接，就是典型场景，可用 `StringBuilder` 优化。

### 6.8 排查工具速查


| 工具                 | 用途                             |
| ---------------------- | ---------------------------------- |
| `dotnet-counters`    | 实时看 GC 次数、堆大小、各代大小 |
| `dotnet-dump`        | 抓内存快照，分析对象图           |
| `dotnet-trace`       | 追踪 GC / 分配事件               |
| dotMemory / PerfView | 可视化分析（IDE / 独立工具）     |

### 6.9 小结对照表


| 问题            | 本质                 | 解法                |
| ----------------- | ---------------------- | --------------------- |
| 无界静态缓存    | 静态根永远可达       | 加淘汰策略 / 设上限 |
| 事件没退订      | 长命对象引用短命对象 | 用完`-=` 退订       |
| 单例持有 Scoped | 长寿命捕获短寿命     | 遵守 DI 寿命规则    |
| 装箱过多        | 值类型反复包成堆对象 | 用泛型              |
| LOH 碎片        | 大对象不压缩         | 大对象池化复用      |
| 字符串拼接      | 不可变串反复复制     | `StringBuilder`     |

## 7. 性能优化建议

### 7.1 总原则：先测量，再优化

> 过早优化是万恶之源。别凭感觉改代码，先用工具定位真正的瓶颈。

- 先用 `dotnet-counters` / `dotnet-trace` 看 GC 数据，确认问题再动手
- 优化总目标回顾（3.7 节）：**让对象尽量死在 0 代，别让它活到 2 代，避免 full GC**

### 7.2 手段 1：减少分配，能复用就复用

对象分配得越少，GC 压力越小。

```csharp
// ❌ 循环里反复 new 大数组（LOH 碎片 + GC 压力）
for (...) {
    byte[] buffer = new byte[1024 * 1024];
    Process(buffer);
}

// ✅ 池化复用（ArrayPool 借、用完还）
byte[] buffer = ArrayPool<byte>.Shared.Rent(1024 * 1024);
try {
    Process(buffer);
} finally {
    ArrayPool<byte>.Shared.Return(buffer);   // 归还，供下次复用
}
```

- `ArrayPool<byte>`：大对象反复分配释放的最佳解，避免 LOH 碎片
- 项目对照：Excel 导出的 `MemoryStream`/`byte[]`，高频场景可考虑池化

### 7.3 手段 2：避免装箱，用泛型

```csharp
// ❌ 装箱：10 万个堆对象
List<object> list = new();
for (int i = 0; i < 100000; i++) list.Add(i);

// ✅ 泛型：0 装箱
List<int> list = new();
for (int i = 0; i < 100000; i++) list.Add(i);
```

- 项目对照：`ExcelService.cs` 用 `CompileGetter` 编译委托替代反射 `GetValue`，消除装箱

### 7.4 手段 3：循环拼接字符串用 StringBuilder

```csharp
// ❌ O(n²) 分配
string s = "";
for (int i = 0; i < 10000; i++) s += i + ",";

// ✅ O(n)
var sb = new StringBuilder();
for (int i = 0; i < 10000; i++) sb.Append(i).Append(',');
string s = sb.ToString();
```

- 项目对照：`ReportService.cs` 里 `returnString += ...`、`result.Content += ...` 循环拼接可优化

### 7.5 手段 4：及时释放非托管资源（using）

```csharp
// ✅ 用完立即释放，不等 GC
using var des = DES.Create();
using var workbook = new Workbook();
```

- 项目对照：`ExcelService.cs` 的 `workbook` 已加 `using var`（本次修复）

### 7.6 手段 5：静态缓存设上限 + 事件退订

- 缓存要有**淘汰策略**（LRU / 定期清理 / 容量上限），不能只进不出
- 长命对象订阅短命对象的事件，用完必须 `-=` 退订
- 项目对照：`EnumTool._enumCache` 有上限 ✅；`Logger.LogQueues` 无界 ⚠️

### 7.7 手段 6：遵守 DI 寿命规则

- 长寿命对象不持有短寿命对象：单例只注入单例，Scoped 不注入单例持有
- 避免 CaptiveDependency

### 7.8 手段 7：生产环境开启 Server GC

```xml
<PropertyGroup>
  <ServerGarbageCollection>true</ServerGarbageCollection>
</PropertyGroup>
```

- 高并发 Web 服务建议开 Server GC（详见第 4 节）

### 7.9 最终优化清单（收尾汇总）

| 手段 | 一句话 | 项目落地点 |
|---|---|---|
| 减少分配 | 大对象池化 `ArrayPool<byte>` | Excel 导出缓冲 |
| 避免装箱 | 用泛型 | `CompileGetter` 委托 |
| 字符串 | `StringBuilder` 替代 `+=` | `ReportService` 拼接 |
| 非托管资源 | `using` 及时释放 | `workbook` 已修 |
| 静态缓存 | 设上限/淘汰 | `EnumTool` 正确 |
| DI 寿命 | 长命不持短命 | 服务注册 |
| GC 配置 | 生产开 Server GC | `csproj` |

> 本专题完。所有优化都回到一个原点：**少分配、早释放、让对象死在 0 代**。
