## 一、DbContext 与 ChangeTracker

### 1. DbContext 内部有什么

```
DbContext
├── Model（模型）
│     实体 <-> 表/列的映射元数据，启动时构建一次，之后只读
├── ChangeTracker（变更跟踪器）
│     一张表：实体实例 -> 状态 + 原始值快照
├── Database（数据库门面）
│     BeginTransaction / ExecuteSqlRaw / 连接管理
└── DbSet<T>
│     查询入口（IQueryable 工厂）
```

**最容易忽略的是"原始值快照"**：EF Core 不只是记住实体对象，还记下了**它从数据库读出来时每一列的值**。`SaveChanges` 时就是靠"当前值 vs 原始值"的差异来生成 UPDATE 的。

### 2. 实体是怎么"进"跟踪器的

```
查询（跟踪查询）
  -> 执行 SQL
  -> 拿到结果行
  -> 对每一行：查跟踪器里有没有同主键的实例
        有  -> 复用（把行数据丢掉）
        没有 -> new 一个实体，塞进跟踪器，状态 = Unchanged，并记录原始值快照
```

```
Add / Update / Attach 一个游离实体
  -> 直接塞进跟踪器（不查库）
  -> 状态 = Added / Modified / Unchanged
```

### 3. 状态机怎么驱动 SQL

`SaveChanges()` 做的事：

```
1. 遍历 ChangeTracker 里的所有实体
2. 按状态分组：
     Added    -> 生成 INSERT（所有列）
     Modified -> 生成 UPDATE（被标记为 Modified 的列）
     Deleted  -> 生成 DELETE
3. 排序（受主键/外键依赖影响，保证先插父表再插子表）
4. 开事务（隐式）
5. 逐条执行
6. 处理返回值（自增主键回填、并发令牌校验）
7. 把 Added 改成 Unchanged，把快照更新为当前值
```

**关键推论**：

- `SaveChanges` 会保存**跟踪器里所有的变更**，不能只保存某一个实体
- 一个 `Modified` 实体如果**所有属性**都被标了 Modified，生成的 UPDATE 就是全列更新（这就是 `db.Update(游离实体)` 的行为）
- 快照在 `SaveChanges` 之后会刷新，所以连续两次改同一实体、两次 `SaveChanges` 是可行的

### 4. 为什么 DbContext 不是线程安全的

因为 `ChangeTracker` 是**普通字典 + 可变状态**，没有任何锁：

```
两个线程同时 SaveChanges
  -> 同时在遍历、修改同一张状态表
  -> 轻则生成重复 SQL，重则字典被改坏
```

**推论**：**永远不要**把 DbContext 注册成 Singleton，也不要用 `Task.Run` 在里面并发操作同一个上下文。

### 5. 为什么 DbContext 要"短命"（Scoped）

两个原因：

1. **跟踪器会越来越大**：查得越多，跟踪的实体越多，`SaveChanges` 时越慢，内存也一直涨
2. **数据会越来越陈旧**：跟踪查询复用实例 -> 你拿到的一直是"第一次读进来"的那份，看不到别人后来的改动

```
Scoped（一个请求一个）：请求结束 -> Dispose -> 跟踪器清空 -> 干净
Singleton：跟踪器永远不清 -> 内存泄漏 + 数据陈旧
```

**排查线索**：如果某个接口随着运行时间推移越跑越慢，怀疑是不是有人把 DbContext 弄成长生命周期的了。

## 二、标识解析（Identity Resolution）

### 1. 是什么

**一句话**：**同一个数据库行，在同一个 DbContext 里只会对应一个实体对象。**

```csharp
var a = db.Blogs.First(x => x.Id == 1);
var b = db.Blogs.First(x => x.Id == 1);

Console.WriteLine(ReferenceEquals(a, b));   // True —— 同一个对象
```

注意是**同一个引用**，不是"内容相同"。这是 EF Core 的硬保证。

### 2. 为什么需要它

假设没有标识解析：

```csharp
var a = db.Blogs.First(x => x.Id == 1);
a.Name = "AAA";

var b = db.Blogs.First(x => x.Id == 1);   // 新对象，Name = 数据库里的旧值
b.Name = "BBB";

db.SaveChanges();
// 两个对象都在跟踪器里，都要写同一个主键 -> 到底写哪个？顺序不同结果不同
```

**乱套**。有了标识解析，`b` 就是 `a`，永远只有一个对象要写。

### 3. 查询时怎么工作（关键机制）

**每次跟踪查询，实际发生两件事**：

```
① 数据库那边：执行 SQL（用 WHERE 条件）-> 拿到结果行的原始数据
② 客户端这边：对每一行做标识解析
      跟踪器里有同主键实例  -> 丢弃行数据（重要！），返回已有实例
      没有                  -> 用行数据新建实体
```

**第 ② 步"丢弃行数据"是关键**。这就解释了一个看起来反直觉的现象：

```csharp
var a = db.Blogs.First(x => x.Id == 1);   // 数据库 Name = "A"
a.Name = "B";                              // 只改内存

// 再查一次
var b = db.Blogs.Where(x => x.Id == 1).First();
Console.WriteLine(b.Name);                 // "B"，不是 "A"
```

SQL 明明返回了 `Name = "A"`，但因为跟踪器里已经有 ID=1 的实例，行数据被丢掉，返回的是内存里那个 `"B"`。

### 4. 未提交修改的两层行为（原理版）

把上面两步拆开看，"筛不到但取得到"就很好理解了：

| 步骤 | 在哪儿执行 | 看得到未提交的修改吗 |
| --- | --- | --- |
| ① WHERE 条件 | **数据库** | **看不到**（数据库只有已提交数据） |
| ② 实例数据 | **客户端跟踪器** | **看得到**（内存里就是改过的） |

**所以**：

- 按"被改的字段"筛 -> 第 ① 步就筛不出来 -> **查不到**
- 按主键查 -> 第 ① 步能查到行 -> 第 ② 步返回内存实例 -> **读到新值**

**一句话**：**筛条件看数据库（已提交），取实例看内存（含未提交）。**

### 5. AsNoTracking 为什么打破它

`AsNoTracking()` 就是**关掉第 ② 步**：

```
跟踪查询：  执行 SQL -> 标识解析 -> 返回跟踪器实例（可能是内存里改过的）
NoTracking：执行 SQL -> 直接用行数据造新对象 -> 返回
```

结果：

- 同一个实体查两次得到**两个不同对象**
- 属性值永远是**数据库里的**（看不到内存里的未提交修改）
- 省掉了"查跟踪器 + 建快照"的开销，所以更快

**`AsNoTrackingWithIdentityResolution()`** = 关掉跟踪，但**保留第 ② 步的"同一主键返回同一实例"**，只是这些实例不进跟踪器（不建快照、不参与 SaveChanges）。

**副作用**：因为这批实例不进跟踪器，你**改了它们 `SaveChanges` 也不会写库**。

## 三、LINQ -> SQL 的翻译管道

### 1. 管道概览

```
db.Blogs.Where(...).OrderBy(...).Select(...)
   |
   | ① 表达式树（Expression Tree）
   v
Expression<Func<Blog, bool>>
   |
   | ② Provider 解析
   v
关系代数 / 查询模型
   |
   | ③ SQL 生成器
   v
SELECT ... FROM ... WHERE ...
   |
   | ④ 执行 + 物化
   v
List<Blog>
```

### 2. 表达式树（Expression Tree）

**这是整个机制的地基**。

```csharp
Func<Blog, bool> del = x => x.Id > 1;               // 委托：编译成 IL，一个黑盒
Expression<Func<Blog, bool>> expr = x => x.Id > 1;  // 表达式树：一棵可读的树
```

表达式树长这样：

```
GreaterThan
├── MemberAccess (x.Id)
└── Constant (1)
```

**委托只能执行，表达式树能被"读"** —— Provider 就是读这棵树，把它翻译成 SQL 的。

```csharp
// 可以手动看这棵树
Expression<Func<Blog, bool>> expr = x => x.Id > 1;
Console.WriteLine(expr.ToString());   // x => (x.Id > 1)
Console.WriteLine(expr.Body.NodeType); // GreaterThan
```

### 3. 为什么 IQueryable 能翻译、IEnumerable 不能

`IQueryable<T>` 内部持有的是 **`Expression`（表达式树）**：

```csharp
public interface IQueryable<out T> : IEnumerable<T>, IQueryable { }

public interface IQueryable : IEnumerable
{
    Expression Expression { get; }      // <- 关键：表达式树
    Type ElementType { get; }
    IQueryProvider Provider { get; }    // <- 关键：翻译器 + 执行器
}
```

- **`IQueryable.Where(...)`** -> 不改数据，只**接手并包装表达式树**（`Expression.Call(...)`），返回新的 `IQueryable`
- **`IEnumerable.Where(...)`** -> 是个**委托**，必须能执行；调用时就真的跑代码

所以：

```csharp
db.Blogs.Where(x => MyMethod(x.Name))          // IQueryable -> Provider 翻译 MyMethod -> 不会翻 -> 抛异常
db.Blogs.ToList().Where(x => MyMethod(x.Name)) // IEnumerable -> 就是在内存里跑 C# 代码 -> 正常运行
```

**这就是"ToList 的位置决定一切"的根因。**

### 4. 翻译不了为什么抛异常（而不是偷偷跑内存）

EF Core 2.x 时代是"翻译不了就拉到内存算"，结果：

- 一个看起来正常的 LINQ，在数据库上跑个全表扫描
- 生产环境悄悄变成性能事故
- 因为"能跑"，没人发现

EF Core 3.0 起改成**直接抛异常**，逼你显式处理。**这是好事**。

**要"退回内存"就显式写**：

```csharp
var rows = db.Blogs.Select(x => new { x.Id, x.Name }).ToList();   // 先缩小结果集！
var result = rows.Where(x => MyMethod(x.Name));                   // 再在内存里处理
```

**注意顺序**：**先 `Select` 缩小，再 `ToList`，再内存处理**。反过来（先 `ToList` 全表）就是性能事故。

### 5. 怎么看翻译结果

```csharp
optionsBuilder.LogTo(Console.WriteLine, LogLevel.Information);
```

或者：

```csharp
var sql = db.Blogs.Where(x => x.Id > 1).ToQueryString();
Console.WriteLine(sql);
```

`ToQueryString()` **只生成 SQL 不执行**，调试时很方便。

## 四、IQueryable 的本质

### 1. 三个组成部分

```
IQueryable<T>
├── Expression        表达式树（"我要查什么"）
├── ElementType       元素类型
└── Provider          IQueryProvider（"怎么查"：翻译 + 执行）
```

**`IQueryable` 不等于"数据"，它等于"一个待执行查询的描述"。**

### 2. 延迟执行是怎么实现的

```csharp
var query = db.Blogs.Where(x => x.Id > 1);
```

这行什么都没查。真正发生的是：

```
db.Blogs              -> 一个 IQueryable（Provider = EF 的，Expression = 空）
.Where(...)           -> 返回新的 IQueryable，Expression = Expression.Call(Where, 旧的Expression, 谓词)
```

**只是不断包装表达式树**。

只有当你**遍历它**（`foreach` / `ToList` / `Count` / `First`）时，`GetEnumerator()` 被调用 -> Provider 才去翻译 + 执行。

### 3. 为什么多次遍历会多次查库

因为 `IQueryable` 是**描述**，不是**结果**。每次从头遍历都是"重新执行这个查询描述"：

```csharp
var q = db.Blogs.Where(x => x.Id > 1);

q.Count();       // SELECT COUNT(*)   -> 1 次
q.ToList();      // SELECT *          -> 2 次
foreach (var x in q) { }   // SELECT *  -> 3 次
```

**要复用就落地**：`var list = q.ToList();` 之后随便遍历，内存里跑，不再查库。

### 4. 闭包捕获的坑

```csharp
int minId = 1;
var q = db.Blogs.Where(x => x.Id > minId);   // 这里捕获的是"变量"，不是"当前值"

minId = 100;      // 改一下
var list = q.ToList();   // SQL 里用的是 minId = 100
```

**因为查询是延迟执行的，表达式树里的 `minId` 是在执行那一刻求值的。**

**两个后果**：

1. 逻辑上容易写错（以为是 1，实际是 100）
2. 循环里拼查询要小心：

```csharp
// 危险：所有查询最终都用循环结束时的 i
var queries = new List<IQueryable<Blog>>();
for (int i = 0; i < 3; i++) { queries.Add(db.Blogs.Where(x => x.Id > i)); }

// 安全：循环体内立即执行
for (int i = 0; i < 3; i++) { lists.Add(db.Blogs.Where(x => x.Id > i).ToList()); }
```

## 五、事务与隔离级别

### 1. ACID 简述

| 特性 | 含义 | 谁保证 |
| --- | --- | --- |
| **A** 原子性 | 要么全成功要么全失败 | 事务 |
| **C** 一致性 | 约束不被破坏 | 约束 + 业务代码 |
| **I** 隔离性 | 并发事务互不干扰 | **隔离级别** |
| **D** 持久性 | 提交了就不丢 | 数据库 |

**"隔离性"是并发问题的根源** —— 隔离得越少，性能越好，但异常现象越多。

### 2. 四种隔离级别与三种读现象

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
| --- | --- | --- | --- |
| READ UNCOMMITTED | 可能 | 可能 | 可能 |
| **READ COMMITTED**（SQL Server 默认） | 不会 | 可能 | 可能 |
| REPEATABLE READ | 不会 | 不会 | 可能 |
| SERIALIZABLE | 不会 | 不会 | 不会 |

**三种现象**：

- **脏读**：读到了别人**未提交**的数据（别人一回滚就完蛋）
- **不可重复读**：同一事务内，两次读同一行，值不一样（中间别人改了并提交）
- **幻读**：同一事务内，两次按同样条件查，**行数**不一样（中间别人插入/删除了）

### 3. SQL Server 默认：READ COMMITTED

```csharp
db.Database.BeginTransaction();   // 无参 -> 用数据库默认
```

**这个级别保证**：只能读到**已提交**的数据（防脏读）。
**它不保证**：两次读结果相同（防不住不可重复读和幻读）。

**改隔离级别**：

```csharp
db.Database.BeginTransaction(IsolationLevel.RepeatableRead);
```

或者 SQL Server 的 `SNAPSHOT`（要数据库先开 `ALLOW_SNAPSHOT_ISOLATION`）。

### 4. 为什么 READ COMMITTED 挡不住"先查后写"

这是最重要的一个推论：

```
请求A                                  请求B
① SELECT Status -> Free（已提交值）    ① SELECT Status -> Free（已提交值）
② UPDATE Status = Used                ② UPDATE Status = Used
COMMIT                                 COMMIT
```

**第 ① 步读到的都是"已提交的旧值" —— 完全合法，`READ COMMITTED` 不会拦。**

所以 **`READ COMMITTED` 只防"脏读"，不防"并发下双方基于同一个旧值各写各的"**。

这个现象叫 **TOCTOU**，要防它得靠：

- **数据库约束**（唯一索引）—— 最省事
- **锁**（`UPDLOCK` / `SERIALIZABLE`）—— 最重
- **乐观并发**（`rowversion`）—— 折中

### 5. SNAPSHOT 隔离

SQL Server 的 `SNAPSHOT`：事务内所有读都走**事务开始时的行版本**（读不阻塞写、写不阻塞读）。

**优点**：读一致性 + 高并发。
**代价**：要开数据库选项、tempdb 压力大。
**注意**：它解决的是"读到一半数据被别人改了"，**不解决** TOCTOU。

### 6. 幻读与 `SELECT ... FOR UPDATE`

要"读到就锁住"，标准做法是读的时候加锁：

```sql
select * from tbl_Board with (updlock, rowlock) where ID = 1;
```

后到的事务会**阻塞等待**，直到前一个事务结束 -> 拿到的是最新值 -> 避免 TOCTOU。

**EF Core 没有原生 API**，要 `FromSqlRaw` 写。**代价**：阻塞、可能死锁、要调优。

## 六、把四篇串起来

```
01-基础      实体 + DbContext + 映射           "是什么"
02-查询与跟踪  IQueryable / 后缀 / 跟踪行为      "怎么查"
03-高阶      状态机 / 事务 / 并发 / 性能         "怎么改、怎么快、怎么不踩坑"
04-原理      跟踪器 / 标识解析 / 翻译管道 / 事务   "为什么"
```

**遇到问题时按这个顺序想**：

1. 先看**生成的 SQL**（`LogTo` / `ToQueryString`）—— 90% 的问题看一眼 SQL 就清楚了
2. 再看**跟踪行为**（这个实体在跟踪器里吗？状态是什么？）
3. 然后看**翻译**（我写的 LINQ 它翻得出来吗？翻成什么了？）
4. 最后看**并发**（这里有可能两个请求同时进来吗？）
