## 一、EF Core 是什么

### 1. 一句话

**EF Core 是 .NET 的 ORM**：让你用 C# 对象 + LINQ 操作数据库，SQL 由它替你生成。

代价是 —— **SQL 是它生成的，所以你必须知道它生成了什么**。本系列后面大半篇幅都在讲这件事。

### 2. 和别的方案对比

| 方案 | SQL 谁写 | 特点 |
| --- | --- | --- |
| ADO.NET | 全手写 | 最快、码量最大、最容易写错 |
| Dapper | 手写，映射帮你做 | 性能接近手写 SQL |
| **EF Core** | **它生成** | 开发快；有变更跟踪、迁移、LINQ |
| EF6 | 它生成 | 上一代，绑死 .NET Framework |

### 3. 最小可运行的例子

```csharp
// ① 实体
public class Blog
{
    public int Id { get; set; }
    public string Name { get; set; }
}

// ② DbContext
public class AppDbContext : DbContext
{
    public DbSet<Blog> Blogs { get; set; }

    protected override void OnConfiguring(DbContextOptionsBuilder optionsBuilder)
    {
        optionsBuilder.UseSqlServer("Server=.;Database=Demo;Trusted_Connection=True;");
    }
}

// ③ 用
using var db = new AppDbContext();

db.Blogs.Add(new Blog { Name = "hello" });
db.SaveChanges();                                    // 写库

var list = db.Blogs.Where(x => x.Name.Contains("hello")).ToList();   // 查库
```

**核心就三样：实体、DbContext、LINQ 查询。** 剩下的都是这三样的变体和坑。

### 4. 一段完整流程长什么样

```
实体类  --(映射)-->  表
DbSet<T>  --(LINQ)-->  SQL  --(Provider)-->  数据库
        <--(物化)---  结果行  <--(结果集)--
```

- **映射**：谁来定义实体和表的对应关系（`OnModelCreating` / 特性 / 约定）
- **Provider**：`UseSqlServer` / `UseNpgsql` / `UseSqlite` —— 决定 LINQ 翻译成哪家的 SQL
- **物化（materialize）**：把结果行变成 C# 对象

## 三、DbContext 与生命周期

### 1. DbContext 管三件事

| 职责 | 说明 |
| --- | --- |
| **连接** | 连接字符串、连接池、Provider |
| **映射** | 实体 <-> 表/列（写在 `OnModelCreating`） |
| **变更跟踪** | 记住你改过哪些实体，`SaveChanges` 时统一生成 UPDATE |

第三件事是 EF Core 的"魔法"来源，也是**大部分坑的来源**（详见 `03-高阶`、`04-原理`）。

### 2. 注册进 DI

```csharp
// Program.cs / Startup.cs
builder.Services.AddDbContext<AppDbContext>(options =>
{
    options.UseSqlServer(connectionString);
}, ServiceLifetime.Scoped);
```

### 3. 为什么生命周期必须是 Scoped

| 生命周期 | 能不能用 | 原因 |
| --- | --- | --- |
| `Singleton` | **不能** | DbContext **不是线程安全的**，多线程共用一个实例会出各种诡异问题 |
| `Scoped` | **可以（推荐）** | 一个请求一个实例：变更跟踪、事务的边界正好和请求对齐 |
| `Transient` | **不推荐** | 同一请求里多个实例 -> 跟踪互相看不见、事务不覆盖同一批操作 |

**记忆点**：DbContext 就是一个"数据库会话"，会话当然应该跟请求同生命周期。

### 4. 常见配置项

```csharp
services.AddDbContext<AppDbContext>(options =>
{
    options.UseSqlServer(connectionString)
           .EnableSensitiveDataLogging(false)                    // 日志里带参数值（生产别开！）
           .UseQueryTrackingBehavior(QueryTrackingBehavior.NoTracking);   // 全局默认不跟踪
}, ServiceLifetime.Scoped);
```

三个配置项都值得单独记：

- `EnableSensitiveDataLogging`：**开了会把参数值写进日志**（可能含隐私数据），生产环境务必 `false`
- `UseQueryTrackingBehavior`：改的是**全局默认**，影响面极大，详见 `02-查询与跟踪`
- `LogTo`：把生成的 SQL 打到控制台

### 5. 看生成的 SQL（排查必备）

```csharp
optionsBuilder.LogTo(Console.WriteLine, LogLevel.Information);
```

**这是排查 EF 问题最直接的手段** —— 不管出什么问题，先看它到底发了什么 SQL。

> 本项目实测就是靠它确认：`("," + col + ",").Contains("," + v + ",")` 被翻译成
> `CHARINDEX(@p, N',' + COALESCE(col, N'') + N',') > 0` —— **用的是 `CHARINDEX` 字面查找，不是 `LIKE`**。

### 6. 连接字符串一般是加密的

生产项目里连接串通常不明文放在 `appsettings.json`，而是加密后运行期解密：

```csharp
var conn = DESHelper.Decode(Configuration.GetSection("ConnectionStrings:DefaultConnection").Value, key);
options.UseSqlServer(conn);
```

**排查时注意**：配置文件里读出来的可能是密文，别直接拿去连数据库。

## 四、模型映射与约定

### 1. 约定优于配置

什么都不配时，EF Core 按这些约定办事：

| 项 | 约定 |
| --- | --- |
| 表名 | 实体类名（会复数化，可关掉：`RemovePluralizingTableNameConvention`） |
| 主键 | `Id` 或 `类名Id`（int / long / Guid） |
| 列名 | 属性名 |
| 可空 | C# `int?` -> SQL 允许 NULL；`string` 默认允许 NULL |
| 关系 | 导航属性 + 外键命名规律（`WorkOrderId` 对应 `WorkOrder`） |

**小项目可以直接吃约定**（表名和类名对得上就行）。

**老系统基本吃不了**：表名是 `tbl_xxx` / `r_xxx` / `dic_xxx` 这种，跟类名完全对不上，只能一个个显式映射。

> 本项目就是后者：几乎每个实体都手写一行 `ToTable`。

### 2. Fluent API（推荐）

写在 `OnModelCreating` 里：

```csharp
protected override void OnModelCreating(ModelBuilder modelBuilder)
{
    modelBuilder.Entity<Blog>(entity =>
    {
        entity.ToTable("tbl_Blog");                        // 表名
        entity.HasKey(x => x.Id);                          // 主键
        entity.Property(x => x.Name)
              .HasMaxLength(50)
              .IsRequired();                               // 列配置
        entity.HasIndex(x => x.Name).IsUnique();           // 索引
        entity.HasQueryFilter(x => !x.IsDelete);           // 全局过滤（软删）
    });
}
```

### 3. 常用映射 API 速查

| API | 作用 |
| --- | --- |
| `ToTable("名")` | 表名 |
| `HasKey(x => x.Id)` | 主键 |
| `Property(x => x.Name)` | 进入列级配置 |
| `.HasMaxLength(n)` / `.IsRequired()` / `.HasDefaultValue(...)` | 列属性 |
| `.HasConversion<T>()` | 值转换（枚举 <-> int、JSON <-> string） |
| `.HasColumnName("列名")` | 列名 |
| `HasIndex(x => x.Code).IsUnique()` | 唯一索引 |
| `HasQueryFilter(x => !x.IsDelete)` | 全局过滤（软删） |
| `HasOne() / HasMany() / WithOne() / WithMany()` | 关系 |
| `HasDbFunction(...)` | 把数据库函数注册进来给 LINQ 用 |

### 4. 数据注解 vs Fluent API

```csharp
// 数据注解：直接标在实体上
[Table("tbl_Blog")]
public class Blog
{
    [Key]
    public int Id { get; set; }

    [MaxLength(50)]
    public string Name { get; set; }
}
```

| 方式 | 优点 | 缺点 |
| --- | --- | --- |
| 数据注解 | 直观、就近 | 要动实体类；能配的东西少 |
| **Fluent API** | 全能、集中在 DbContext | 要跳文件看 |

**建议**：小项目随你；**中大型项目一律 Fluent API** —— 实体类应该保持"纯 POCO"，配置集中在 DbContext 里，改配置不用动被到处引用的实体项目。

### 5. 把配置拆出去（大项目必备）

实体多起来之后 `OnModelCreating` 会变成几千行。两种拆法：

**（a）partial + 分部方法**

```csharp
public partial class AppDbContext : DbContext
{
    protected override void OnModelCreating(ModelBuilder modelBuilder)
    {
        // ... 主文件里一部分
        OnModelCreatingPartial(modelBuilder);
    }

    partial void OnModelCreatingPartial(ModelBuilder modelBuilder);   // 另一个文件里实现
}
```

**（b）每个实体一个配置类**

```csharp
public class BlogConfig : IEntityTypeConfiguration<Blog>
{
    public void Configure(EntityTypeBuilder<Blog> builder)
    {
        builder.ToTable("tbl_Blog");
        builder.HasKey(x => x.Id);
    }
}

// 注册
protected override void OnModelCreating(ModelBuilder modelBuilder)
{
    modelBuilder.ApplyConfiguration(new BlogConfig());
    // 或者一次性扫描程序集里所有 IEntityTypeConfiguration
    modelBuilder.ApplyConfigurationsFromAssembly(typeof(AppDbContext).Assembly);
}
```

**（c）本项目用的偏门写法：反射 + 自定义特性**

标了 `[AutoApplyConfiguration]` 的配置类会被反射自动应用，不用在 `OnModelCreating` 里写一行：

```csharp
var types = thisAssembly.GetTypes()
    .Where(t => t.GetInterface(typeof(IEntityTypeConfiguration<>).FullName) != null);
foreach (var type in types)
{
    if (type.CustomAttributes.Any(a => a.AttributeType.FullName == typeof(AutoApplyConfigurationAttribute).FullName))
    {
        dynamic instance = Activator.CreateInstance(type);
        modelBuilder.ApplyConfiguration(instance);
    }
}
```

**效果**：加了配置类就自动生效。**代价**：新人看到配置类会疑惑"它为什么生效"，得知道有这套反射。

### 6. 本项目不吃约定的后果

因为表名对不上，本项目 `OnModelCreating` 里就是**一长串 `ToTable`**：

```csharp
modelBuilder.Entity<R_TestBoard_Product>(entity => entity.ToTable("r_TestBoard_Product"));
modelBuilder.Entity<TestBoardEntity>(entity => entity.ToTable("tbl_TestBoard"));
modelBuilder.Entity<TestBoardCategoryEntity>(entity => entity.ToTable("tbl_TestBoardCategory"));
// ... 几十个
```

**要留意**：这种写法**很容易漏配**。漏了 `ToTable` 的实体，EF Core 会按约定去找一张**复数化的表名**，然后报"表不存在"。

**另一个后果**：因为只写了 `ToTable`，**没有加任何索引和并发令牌**。这在排查并发问题时是重要事实（详见 `03-高阶`）。
