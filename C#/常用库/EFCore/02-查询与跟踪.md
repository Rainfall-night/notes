## 一、查询基础

### 1. 查询的三段式

```csharp
var list = db.Blogs                                  // ① 数据源（IQueryable）
             .Where(x => x.Name.Contains("a"))       // ② 拼条件（还是 IQueryable）
             .OrderBy(x => x.Id)                     // ② 排序
             .Skip(0).Take(20)                       // ② 分页
             .ToList();                              // ③ 触发执行 -> 真发 SQL
```

| 阶段 | 类型 | 发 SQL 了吗 |
| --- | --- | --- |
| ① 数据源 | `IQueryable<T>` | 没有 |
| ② 拼条件 / 排序 / 分页 / 投影 | `IQueryable<T>` | 没有 |
| ③ `ToList()` / `FirstOrDefault()` / `Count()` / `foreach` | 具体结果 | **这时候才发** |

**记住这个分界**：`IQueryable` 只是"查询计划"，不是数据。

### 2. 延迟执行（Deferred Execution）

```csharp
var query = db.Blogs.Where(x => x.Id > 0);   // 没查库

foreach (var x in query) { }    // 查一次
var count = query.Count();      // 又查一次
var list  = query.ToList();     // 再查一次 —— 一共三次
```

**两个后果**：

1. 同一个 `IQueryable` 被消费多次 -> **多次查库**。要复用先 `ToList()` 落地
2. 它读到的是**执行那一刻**的数据。先拼好查询、中间数据被别人改了，最后执行时读到的是新数据

**什么时候是"坑"**：把 `IQueryable` 当参数传来传去，以为查过一次就缓存了 —— 其实每消费一次都查一次。

### 3. IQueryable vs IEnumerable（最容易写错的地方）

```csharp
// 对：条件在数据库执行，只把符合条件的行拉回来
db.Blogs.Where(x => x.Id > 100).Take(20).ToList();

// 错：Where 作用在 IEnumerable 上 -> 全表拉进内存再过滤
db.Blogs.ToList().Where(x => x.Id > 100);
```

**一眼判别法**：看 `.ToList()` / `.AsEnumerable()` 出现在 `Where` 的**前面**还是**后面**。

- **前面** -> 内存过滤（危险）
- **后面** -> SQL 过滤（正确）

**为什么危险**：数据量小的时候看不出区别；数据量一上来，内存和耗时都是数量级的差距。

### 4. 客户端 vs 服务端求值

EF Core 3.0 之后：**表达式翻译不了就直接抛异常**（不再像 2.x 那样偷偷拉到内存算）。

**翻译不了的典型**：

```csharp
// 自定义方法
db.Blogs.Where(x => MyHelper.IsValid(x.Name))

// 带 StringComparison 的字符串比较
db.Blogs.Where(x => x.Name.Equals("a", StringComparison.OrdinalIgnoreCase))
```

**怎么办**：

1. 能改成 EF 支持的写法就改（比如上面的用 `x.Name.ToLower() == "a"`，或者 `EF.Functions.Like`）
2. 实在不行，**先 `Select` 缩小结果集**，再 `AsEnumerable()` 明确切到内存处理：

```csharp
var rows = db.Blogs.Select(x => new { x.Id, x.Name }).ToList();   // SQL 只查这两列
var filtered = rows.Where(x => MyHelper.IsValid(x.Name));         // 内存里过滤
```

**关键**：切内存的时候，**先缩小再切**，不要全表切。

### 5. 分页

```csharp
var page = db.Blogs
            .Where(x => x.Id > 0)
            .OrderBy(x => x.Id)          // 必须排序
            .Skip((pageIndex - 1) * pageSize)
            .Take(pageSize)
            .ToList();
```

**必须 `OrderBy`**：SQL Server 上不排序直接分页，返回的行顺序是**不确定的** —— 翻页时可能看到重复或漏掉的行。

**深分页问题**：`Skip(100000)` 性能很差（数据库还是要扫过去）。大数据量要用"游标分页"（`Where(x => x.Id > lastId).Take(n)`）。

## 二、LINQ 翻译成什么 SQL

### 1. 常用翻译对照表

| C# 写法 | 生成的 SQL | 备注 |
| --- | --- | --- |
| `x.Id == 1` | `[Id] = 1` | |
| `list.Contains(x.Id)` | `[Id] IN (1,2,3)` | 集合可以是常量或变量 |
| `x.Name.Contains("a")` | `CHARINDEX('a', [Name]) > 0` | **字面查找** |
| `x.Name.StartsWith("a")` | `[Name] LIKE 'a%'` | **走 LIKE** |
| `x.Name.EndsWith("a")` | `[Name] LIKE '%a'` | **走 LIKE** |
| `EF.Functions.Like(x.Name, "a%")` | `[Name] LIKE 'a%'` | 显式 LIKE |
| `x.Name.Length` | `LEN([Name])` | |
| `x.CreateTime.Date` | `CONVERT(date, [CreateTime])` | |
| `x.CreateTime.Year` | `DATEPART(year, [CreateTime])` | |
| `x.Children.Any(y => ...)` | `EXISTS (...)` | |
| `x.Children.Count()` | `(SELECT COUNT(*) ...)` | |
| `x.Name ?? "无"` | `ISNULL([Name], N'无')` | |

**怎么自己验证**：开 `LogTo` 抓日志，看一眼就知道。

### 2. 重点坑：LIKE 的通配符

`StartsWith` / `EndsWith` / `EF.Functions.Like` 都会生成 `LIKE`。**如果模式串里含 `%` `_` `[`，会被当成 SQL 通配符**：

```csharp
// 想找 "AB_01"，但 "_" 在 LIKE 里表示"任意一个字符"
db.Items.Where(x => x.Code.StartsWith("AB_01"))
// -> WHERE [Code] LIKE N'AB_01%'  -> 会误命中 "ABX01..."、"AB901..."
```

**注意不对称**：`Contains` **没有这个问题**（它翻译成 `CHARINDEX`，是字面查找）；**有问题的是 `StartsWith` / `EndsWith` / `Like`**。

**三种规避手段**：

**（1）用 `Contains` 拼出等效语义**（最省事）

```csharp
// 想要"按分隔符精确匹配某一段"，而不是 LIKE 前缀匹配
db.Items.Where(x => ("," + x.Code + ",").Contains("," + value + ","))
// -> CHARINDEX(@p, N',' + COALESCE([Code], N'') + N',') > 0   <- 字面查找
```

**（2）用 `EF.Functions.Like` 显式指定转义字符**

```csharp
db.Items.Where(x => EF.Functions.Like(x.Code, pattern, "\\"))
```

**（3）输入侧做白名单校验**

只要输入被限制成"纯字母数字"，通配符问题自然消失。**这是最省心的做法**。

> **本项目佐证**：
> - 基板类型字段值里含 `_`（如 `TF09_XC3532低高度`），所以筛选改成了「字段两端补逗号 + `Contains`」，靠 `CHARINDEX` 避开 `LIKE`
> - 短脉冲驱动板 PN 用的是 `EndsWith`（走 LIKE），但那个输入是纯字母数字，实际安全

### 3. 其他"看着一样、SQL 差很多"的地方

| 写法 | 差异 |
| --- | --- |
| `x.Name == "abc"` | `=` 精确匹配 |
| `x.Name.Contains("abc")` | `CHARINDEX` 子串匹配 |
| 先 `Select` 再 `Where` | 先 `Where` 再 `Select` 更好（少拉列） |
| `query.Count()` 和 `query.ToList().Count` | 前者 `SELECT COUNT(*)`；后者全拉回来数 |

## 三、查询后缀与跟踪行为（本章重点）

> 这一章是排查 EF 问题最常用的一章。

### 1. 什么是"查询后缀"

那些**只影响查询行为、不改变结果集内容**的链式方法：

```csharp
db.Blogs.Where(x => x.Id > 0)
        .AsNoTracking()        // <- 后缀：不跟踪
        .TagWith("查博客")      // <- 后缀：给 SQL 加注释
        .IgnoreQueryFilters()  // <- 后缀：忽略全局过滤
        .ToList();
```

**共同点**：必须写在**触发查询的那个调用之前**。

### 2. AsNoTracking / AsTracking（最常用的一对）

| 后缀 | 效果 | 什么时候用 |
| --- | --- | --- |
| `AsNoTracking()` | 查出来的实体**不进** ChangeTracker | 只读展示 |
| `AsTracking()` | 查出来的实体**进** ChangeTracker，之后改属性才可能被 `SaveChanges` 写库 | 要改数据 |
| （不写） | 跟随**全局设置** | |

```csharp
// 只读：不跟踪，省内存省时间
var list = db.Blogs.AsNoTracking().ToList();

// 要改：跟踪，改完 SaveChanges 就写库
var blog = db.Blogs.First(x => x.Id == 1);
blog.Name = "new";
db.SaveChanges();
```

**为什么要有 NoTracking**：跟踪是有成本的 —— 要维护实体状态机、存原始值快照、占内存、`SaveChanges` 时要逐个体检。**纯查询场景关掉能明显省资源**。

### 3. 全局默认 NoTracking 意味着什么

可以在注册时改全局默认：

```csharp
options.UseQueryTrackingBehavior(QueryTrackingBehavior.NoTracking);
```

**开了这个之后，三个后果必须记住**：

1. 所有查询出来的实体都是**游离（Detached）**的，除非显式 `AsTracking()`
2. 游离实体**改属性不会被 `SaveChanges` 感知** —— 光改不动库
3. 要改数据，必须显式让实体"进跟踪器"（`AsTracking()` 查询，或者 `db.Update(entity)` 附加）

**同一段代码，全局设置不同，行为完全不同**：

```csharp
var blog = db.Blogs.First(x => x.Id == 1);
blog.Name = "new";
db.SaveChanges();
// 全局跟踪（默认）：写库成功
// 全局 NoTracking ：什么都不发生（而且不报错！）
```

**这是最容易踩的"静默失败"** —— 没有异常、没有警告，就是不生效。

> **本项目佐证**：三个 DbContext 全部设了 `NoTracking`，同时自建的 `Repository.GetAll()` 默认参数也是不跟踪 —— **两层默认都不跟踪**。所以要改数据必须走 `GetEntity(..., TrackAll)` 或 `Update(entity)`。

### 4. 最实用的一个知识点：未提交的修改，到底查得到查不到

**先给结论**：

| 问题 | 答案 |
| --- | --- |
| 同一事务内，改过但**没提交**的实体，**按被改的字段筛**，筛得到吗？ | **筛不到** |
| 同一事务内，改过但**没提交**的实体，**按主键/其他条件查**出来后，拿到的属性值是新的还是旧的？ | **新的**（内存里那份） |

**为什么？——**因为这两件事走的**不是同一个地方**：

**（a）查询条件（WHERE）走数据库 -> 读不到未提交的修改**

`WHERE` 会被翻译成 SQL 发给数据库。数据库里只有**已提交**的数据。

```csharp
var blog = db.Blogs.First(x => x.Id == 1);
blog.Name = "changed";        // 只在内存里改了，没有 SaveChanges

// 下面这条的 WHERE 在数据库上执行 —— 数据库根本不知道内存里改过什么
db.Blogs.Where(x => x.Name == "changed").ToList();     // 查不到
db.Blogs.Where(x => x.Name == "original").ToList();    // 反而能查到这行
```

**（b）返回的实体实例 -> 给的是内存里那个（identity resolution）**

EF Core 执行完 SQL 拿到行之后，对每一行做**标识解析（identity resolution）**：

- **ChangeTracker 里已经有同主键的实例** -> **丢弃数据库返回的值，直接返回已有的那个实例**
- 没有 -> 新建实例并附加

所以拿到手的属性值是**你刚在内存里改过的那份**。

**前提是跟踪查询**（`AsTracking()`，或全局开了跟踪）。如果查询用了 `AsNoTracking()`，就会老老实实用数据库里的值。

**一个完整例子**：

```csharp
// ① 查出来（跟踪）
var a = db.Blogs.First(x => x.Id == 1);        // 数据库里 Name = "A"
a.Name = "B";                                  // 只改内存

// ② 再查一次
var b = db.Blogs.First(x => x.Id == 1);

// b 和 a 是同一个对象（引用相等）
Console.WriteLine(object.ReferenceEquals(a, b));   // True
Console.WriteLine(b.Name);                          // "B" —— 读到的是内存值，不是数据库的 "A"
```

**换成 `AsNoTracking()` 就不同了**：

```csharp
var c = db.Blogs.AsNoTracking().First(x => x.Id == 1);
Console.WriteLine(c.Name);            // "A" —— 数据库里的值
Console.WriteLine(ReferenceEquals(a, c));   // False —— 新对象
```

**"筛不到"的另一个后果**：如果你按"内存里的新值"去查，会得到空结果，很容易误判成"数据没保存成功"。

**一句话记法**：

> **筛条件看数据库（已提交），取实例看内存（含未提交）。**

> **本项目佐证**：`BatchAvailable` 里先把选中的通道改成 `Unused`（只改内存），随后整板联动用 `.AsTracking()` 按**板号**（不是按状态）查同板通道 -> 被改过的通道返回内存实例（`Unused`），没改过的返回数据库真值。**如果那里写成 `AsNoTracking()`，整板联动就会基于陈旧状态判断，行为就错了。**

### 5. AsNoTrackingWithIdentityResolution

`AsNoTracking()` 有个副作用：**同一个实体在结果里出现多次，会生成多个不同的对象**（不跟踪就没有身份解析）。

```csharp
// 3 个订单都属于同一个客户 -> 内存里有 3 个独立的 Customer 对象
var orders = db.Orders.Include(x => x.Customer).AsNoTracking().ToList();
```

`AsNoTrackingWithIdentityResolution()` -> **不跟踪，但保证同一主键返回同一实例**。

**什么时候用**：只读 + 有关联数据 + 关心对象引用一致（比如后面要按 Customer 分组、或者要比较引用）。

### 6. Include 家族

| 后缀 | 作用 |
| --- | --- |
| `Include(x => x.Nav)` | 预加载一级导航属性 |
| `ThenInclude(x => x.Nav.Sub)` | 预加载二级 |
| `AsSplitQuery()` | 拆成多条 SQL |
| `AsSingleQuery()` | 合并成一条（默认） |

**`Include` 的坑**：一对多 `Include` 会生成**笛卡尔积**，父行被复制 N 遍。

```csharp
// 一个博客 100 篇文章，SQL 返回 100 行，博客字段重复 100 次
db.Blogs.Include(x => x.Posts).ToList();
```

**修法**：

- `AsSplitQuery()`（拆成 2 条 SQL）
- 或者干脆分两次查（先查博客，再 `Where(x => blogIds.Contains(x.BlogId))` 查文章）

### 7. 其他常用后缀速查

| 后缀 | 作用 |
| --- | --- |
| `AsTracking()` | 强制跟踪 |
| `AsNoTracking()` | 强制不跟踪 |
| `AsNoTrackingWithIdentityResolution()` | 不跟踪 + 身份解析 |
| `IgnoreQueryFilters()` | 忽略 `HasQueryFilter` 的全局过滤（查软删数据时用） |
| `TagWith("备注")` | 给生成的 SQL 加注释，抓日志时定位方便 |
| `AsSplitQuery()` | 一条拆多条（避免笛卡尔积） |
| `AsEnumerable()` | 切到内存（后续是 LINQ to Objects） |
| `AsAsyncEnumerable()` | 异步流式读取（超大结果集） |
| `FromSqlRaw(...)` | 原生 SQL 查询（可再混 LINQ） |
| `ExecuteUpdate()` / `ExecuteDelete()` | **不走跟踪器**的批量更新/删除 |
| `IgnoreAutoInclude()` | 忽略模型上配的自动 Include |

**版本提醒**：`ExecuteUpdate` / `ExecuteDelete` 是 **EF Core 7** 才有的。EF Core 6 只能用「查出来 -> 循环改 -> `SaveChanges`」。

### 8. 后缀的书写顺序

```csharp
// 对
db.Blogs.Where(x => x.Id > 0).AsNoTracking().ToList();

// 错：ToList() 之后已经是 List，再挂后缀没有意义
db.Blogs.Where(x => x.Id > 0).ToList().AsNoTracking();
```

多个后缀可以链式叠加，但**后面的会覆盖前面**（`AsTracking()` 后又写 `AsNoTracking()`，最终是不跟踪）。

## 四、关系与导航属性

### 1. 三种关系

| 关系 | 例子 | 外键放哪 |
| --- | --- | --- |
| 一对多 | 博客 -> 文章 | 多方（文章）持 `BlogId` |
| 一对一 | 订单 -> 订单详情 | 任一方 |
| 多对多 | 学生 <-> 课程 | 需要中间表（EF Core 5+ 可隐式建） |

### 2. 导航属性 vs 裸 ID

```csharp
// 用导航属性
public class Post
{
    public int Id { get; set; }
    public int BlogId { get; set; }      // 外键
    public Blog Blog { get; set; }       // 导航属性
}

// 只用裸 ID
public class R_Order_Item
{
    public long OrderId { get; set; }    // 裸 ID，没有导航属性
    public long ItemId { get; set; }
}
```

| 方式 | 优点 | 缺点 |
| --- | --- | --- |
| 导航属性 | 查询方便（`Include`）、语义清晰 | 对象图可能很复杂、容易 N+1 或笛卡尔积 |
| 裸 ID | 简单、可控、SQL 好预测 | 查询要手写 join 或分两步 |

**两种都可以**，取决于团队习惯。

> **本项目佐证**：实体里大部分是**裸 ID**（如关系表 `R_TestBoard_Product` 只有 `TestBoardID` / `ProductID`），查询靠手写 `join` 或"先查 ID 再 `Contains`"。

### 3. 手写 join 的两种写法

**（a）LINQ 查询表达式（左连接）**

```csharp
var query = from o in db.Orders
            join c in db.Customers on o.CustomerId equals c.Id into oc
            from c in oc.DefaultIfEmpty()          // <- DefaultIfEmpty = 左连接
            select new OrderDto
            {
                Id = o.Id,
                CustomerName = c.Name              // 左连接时可能为 null
            };
```

**（b）先查一批 ID 再 `Contains`（多步查）**

```csharp
var blogIds = db.Posts.Where(x => x.IsPublished).Select(x => x.BlogId).Distinct().ToList();
var blogs = db.Blogs.Where(x => blogIds.Contains(x.Id)).ToList();
```

| 写法 | 优点 | 缺点 |
| --- | --- | --- |
| 手写 join | 一条 SQL 搞定 | 复杂，分页时要小心 |
| 多步查 + `Contains` | 清晰好读 | 中间那个 `ToList()` 把**所有 ID 拉进内存** |

**多步查的坑**：IDs 太多时拼出来的 `IN (...)` 会非常长，SQL Server 对参数个数有上限（约 2100）。
