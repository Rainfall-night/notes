## 一、变更跟踪与保存

### 1. 实体的 5 种状态

`ChangeTracker` 给每个它认识的实体记一个状态：

| 状态 | 含义 | `SaveChanges` 时会怎样 |
| --- | --- | --- |
| `Detached` | 游离，跟踪器不认识它 | 什么都不做 |
| `Unchanged` | 从库里查出来，没改过 | 什么都不做 |
| `Added` | 新增 | 生成 `INSERT` |
| `Modified` | 改过 | 生成 `UPDATE` |
| `Deleted` | 标记删除 | 生成 `DELETE` |

```csharp
// 看某个实体的状态
var entry = db.Entry(blog);
Console.WriteLine(entry.State);
```

**关键**：只有**在跟踪器里**的实体，状态才有意义。全局 NoTracking 时，查出来的实体全是 `Detached`（详见 `02-查询与跟踪`）。

### 2. Add / Update / Remove 对游离实体做了什么

```csharp
db.Add(entity);        // 游离实体 -> Added      -> INSERT 全部列
db.Update(entity);     // 游离实体 -> Attach + 所有属性标为 Modified -> UPDATE 全部列
db.Remove(entity);     // 游离实体 -> Attach + Deleted -> DELETE
```

**`Update` 的重点**：对游离实体，它的语义是「**Attach（附加）+ 把*所有属性*标记为 `Modified`**」。

后果：`SaveChanges` 生成的 `UPDATE` 会**更新所有列**，而不只是你改过的那一列。

```csharp
var blog = db.Blogs.AsNoTracking().First(x => x.Id == 1);   // 游离
blog.Name = "new";                                          // 只改了一个属性
db.Update(blog);                                            // 所有列都被标成 Modified
db.SaveChanges();
// -> UPDATE [Blogs] SET [Name] = 'new', [Url] = '...', [Remark] = '...', ... WHERE [Id] = 1
```

**三种"附加进跟踪器"的方式**（全局 NoTracking 时经常要用）：

```csharp
// ① 查询时就跟踪（最推荐）
var e = db.Blogs.AsTracking().First(x => x.Id == 1);

// ② 游离实体手动附加
db.Attach(e);                                   // Unchanged
db.Entry(e).Property(x => x.Name).IsModified = true;   // 只标记改过的列 -> 生成最小 UPDATE

// ③ db.Update(e)（最省事，但写全列）
db.Update(e);
```

**方式 ② 是最精确的**：只标记你真正改过的列，生成的 UPDATE 最小，也不会覆盖别人的改动。代价是麻烦。

### 3. 丢失更新（Update 写全列的后果）

```
时刻 T1：你查出实体（拿到的是"T1 时刻"的快照，所有列都是 T1 的值）
时刻 T2：别人改了同一行的 [Remark] 列，并提交
时刻 T3：你改了 [Name]，db.Update(e)，SaveChanges
         -> UPDATE 写"所有列"，[Remark] 被写回 T1 的旧值 -> 别人的改动没了
```

**这就是丢失更新（Lost Update）**。窗口越大越容易发生。

**规避**：

1. 缩小"查出 -> 保存"的窗口
2. 用方式 ② 只标记改过的列
3. 上并发令牌（见下一章）

### 4. SaveChanges vs SaveChangesAsync

```csharp
db.SaveChanges();             // 同步
await db.SaveChangesAsync();  // 异步
```

**Web 请求里必须用 Async**：同步版本会**阻塞线程**，高并发下把线程池耗光。

**返回的是受影响行数**，但一般不用管。

**注意**：`SaveChanges` 会把**当前跟踪器里所有变更**一次性发出（EF Core 6 里包在一个事务里）。所以"只想保存这一个实体"是做不到的 —— 要么全保存，要么先清理跟踪器。

### 5. 事务

**隐式事务**：`SaveChanges` 自己就会开一个事务，里面的多条 SQL 要么全成功要么全失败。

**显式事务**：一批操作要跨多个 `SaveChanges` 时用。

```csharp
using var transaction = db.Database.BeginTransaction();
try
{
    db.Blogs.Add(new Blog { Name = "a" });
    await db.SaveChangesAsync();

    db.Posts.Add(new Post { BlogId = 1, Title = "b" });
    await db.SaveChangesAsync();

    await transaction.CommitAsync();            // 提交
}
catch (Exception)
{
    transaction.Rollback();                     // 回滚
    throw;
}
```

**三个要点**：

1. `BeginTransaction()` **无参 -> 用数据库默认隔离级别**（SQL Server = `READ COMMITTED`）
2. **`using` + 没 Commit 就 Dispose -> 自动回滚**
3. **`SaveChanges` 不等于提交**：它只是把 SQL 发出去；在显式事务里还得 `Commit` 才生效

**跨库事务**（同一个 DbContext 连多个库）要用 `TransactionScope`，麻烦且性能差，能避就避。

### 6. 靠"不提交"实现原子性（一种脆弱的写法）

```csharp
using var transaction = db.Database.BeginTransaction();
try
{
    foreach (var item in items)
    {
        item.Status = 1;
        db.Update(item);

        if (item.IsInvalid)                     // 校验不通过
        {
            return Fail("有非法数据");            // 直接返回 -> 事务 Dispose -> 回滚
        }
    }

    await db.SaveChangesAsync();
    await transaction.CommitAsync();
}
catch (Exception ex)
{
    transaction.Rollback();
    return Fail(ex);
}
```

**能工作**：中途 `return` -> 没有 `SaveChanges` + `Commit` -> `using` 结束时自动回滚。

**为什么说脆弱**：

- 一旦循环中间有人插了一句 `SaveChanges()`，就会**部分落库**
- 报错信息也没有"哪几条已经写了"的概念，排查困难
- 后来的人看不出这是"故意的"

**更稳的写法**：**先全量校验一遍，再全量写入**。

```csharp
// 第一遍：只校验，不写
var invalid = items.Where(x => x.IsInvalid).ToList();
if (invalid.Count > 0) return Fail($"有 {invalid.Count} 条非法数据");

// 第二遍：写入
foreach (var item in items) { item.Status = 1; db.Update(item); }
await db.SaveChangesAsync();
await transaction.CommitAsync();
```

> **本项目佐证**：`BatchAvailable` / 焊接绑定时段用的是前一种（循环里 `return` 不提交）的写法，所以那段逻辑特别怕别人在中间加 `SaveChanges`。

## 二、并发

### 1. 先查后写（TOCTOU）

```csharp
var board = db.Boards.First(x => x.Id == id);
if (board.Status == Status.Free)          // ① 先查
{
    board.Status = Status.Used;            // ② 后写
}
db.SaveChanges();
```

**两个请求同时执行**：

```
请求A                            请求B
① 读到 Free                      ① 读到 Free      <- 彼此不可见（都未提交）
② 置为 Used                      ② 置为 Used
提交                              提交
```

**结果**：两个都以为成功，后提交的覆盖先提交的。

这就是 **TOCTOU（Time-of-Check to Time-of-Use）**，也叫"检查与使用之间的时间差"。

### 2. 为什么 `READ COMMITTED` 挡不住它

`READ COMMITTED` 保证的是"**读不到别人未提交的数据**"。但这里两边读的都是**已提交的旧值** —— 完全合法。所以它**天然挡不住 TOCTOU**。

**记忆点**：

> **`if (状态 == 可用)` 只能防"顺序执行"下的冲突，防不住并发。**
> 真要防并发，靠的是**数据库约束**（唯一索引）或**锁**，不是 if。

### 3. 乐观并发（并发令牌）

**思路**：不锁，但**更新时校验这行有没有被动过**。

```csharp
// ① 表上加一列 rowversion（SQL Server 的 timestamp 类型，每次更新自动变）
// ② 模型里声明
entity.Property(x => x.RowVersion).IsRowVersion();
```

之后 EF Core 生成的 UPDATE 会自动带条件：

```sql
UPDATE [Boards] SET [Status] = 2
WHERE [Id] = 1 AND [RowVersion] = 0x0000000000001234;
```

**别人先改过 -> `RowVersion` 变了 -> 影响 0 行 -> EF Core 抛 `DbUpdateConcurrencyException`**。

```csharp
try
{
    await db.SaveChangesAsync();
}
catch (DbUpdateConcurrencyException)
{
    return Fail("数据已被他人修改，请刷新后重试");
}
```

**优点**：不改 SQL 逻辑，EF Core 自动处理。
**缺点**：要加列（DDL），且要在所有 SaveChanges 处处理异常。

### 4. 悲观锁（UPDLOCK）

**思路**：读的时候就把行锁住，别人读不了（或只能等）。

```csharp
// EF Core 没有原生 API，要写原生 SQL
var board = await db.Boards
    .FromSqlRaw("select * from tbl_Board with (updlock, rowlock) where ID = {0}", id)
    .FirstOrDefaultAsync();
```

**优点**：简单直接，锁住就没人抢。
**缺点**：**必须写原生 SQL**；锁的粒度/时长要小心，容易造成死锁或阻塞。

### 5. 唯一索引（最省事、最可靠）

**思路**：把"业务上不能重复"这件事交给数据库。

```sql
create unique index ux_r_TestBoard_Product_TestBoardID
on r_TestBoard_Product (TestBoardID)
where IsDelete = 0;                          -- 过滤索引：软删的历史记录不算
```

**效果**：并发时第二个请求的 INSERT 直接被数据库拒掉（抛异常）-> 业务层捕获后提示"已被占用"。

**优点**：**C# 一行代码都不用改**；约束是"永远有效"的，不依赖各自的代码路径。
**缺点**：加索引前要确认**存量数据没有重复**，否则建不上。

```sql
-- 建之前先查有没有脏数据
select TestBoardID, count(*) from r_TestBoard_Product
where IsDelete = 0 group by TestBoardID having count(*) > 1;
```

### 6. 三种方案怎么选

| 方案 | 改动量 | 适用 |
| --- | --- | --- |
| **唯一索引** | DDL 一句 | **首选**（业务本来就"不允许重复"时） |
| 乐观并发 | 加列 + 异常处理 | 需要在"多列竞态"上做保护 |
| 悲观锁 | 写原生 SQL + 调优 | 冲突概率极高、且能接受阻塞 |

## 三、性能

### 1. N+1 查询

**现象**：查 N 条主表数据，然后循环里对每条再查一次子表 -> 一共 N+1 条 SQL。

```csharp
// 反面例子
var blogs = db.Blogs.ToList();                        // 1 条
foreach (var b in blogs)
{
    var posts = db.Posts.Where(x => x.BlogId == b.Id).ToList();   // N 条
}
```

**三种修法**：

```csharp
// ① Include 预加载（一次查完，但可能笛卡尔积）
db.Blogs.Include(x => x.Posts).ToList();

// ② 先收集 ID 再一次性查
var blogIds = blogs.Select(x => x.Id).ToList();
var allPosts = db.Posts.Where(x => blogIds.Contains(x.BlogId)).ToList();

// ③ 直接在 SQL 端做（投影 + join，最优）
var rows = db.Blogs.Select(b => new { b.Id, PostCount = b.Posts.Count() }).ToList();
```

**怎么发现**：抓 SQL 日志，看有没有大量"结构相同、只有参数不同"的 SQL 连续出现。

### 2. 投影到 DTO（最有效的优化）

```csharp
// 差：查出整个实体，却只用两个字段
var list = db.Blogs.ToList();

// 好：只查需要的列
var list = db.Blogs.Select(x => new BlogDto
{
    Id = x.Id,
    Name = x.Name
}).ToList();
```

**三重好处**：

1. SQL 只查这两列（**少 IO**）
2. 不建跟踪实体（**少内存、少 CPU**）
3. 结果集小（**少网络传输**）

**只读接口的首选写法**。

### 3. 批量操作

```csharp
// EF Core 7+：
await db.Blogs.Where(x => x.Status == 1).ExecuteUpdateAsync(s => s.SetProperty(x => x.Status, 2));

// EF Core 6 及以前：只能查出来循环改
var list = db.Blogs.Where(x => x.Status == 1).ToList();
foreach (var b in list) { b.Status = 2; }
await db.SaveChangesAsync();
```

**差别**：前者发**一条** UPDATE，压根不把数据拉回来；后者要**全量拉回内存 + 逐行生成 UPDATE**。

**EF Core 6 想快**：写原生 SQL（`ExecuteSqlRaw`）或者 `SqlBulkCopy`。

### 4. 原生 SQL

```csharp
// 查询
var list = db.Blogs.FromSqlRaw("select * from Blogs where Status = {0}", 1).ToList();

// 执行命令
await db.Database.ExecuteSqlRawAsync("update Blogs set Status = 1 where Id = {0}", id);
```

**安全要点**：**永远不要拼字符串**（SQL 注入）。用 `{0}` 占位符，或用 `FromSqlInterpolated`（它是参数化的，安全）。

```csharp
// 安全（会参数化）
db.Blogs.FromSqlInterpolated($"select * from Blogs where Status = {status}");

// 危险（字符串拼接，注入风险）
db.Blogs.FromSqlRaw("select * from Blogs where Status = " + status);
```

### 5. 长事务

- **事务要短**：长事务持锁、占连接，可能把连接池耗尽
- **别在事务里做 HTTP 调用 / 文件 IO / 大量计算**：锁一直被持着
- 需要"先算再写"时，把计算挪到事务外

### 6. 反模式清单（自查用）

| 反模式 | 症状 | 改法 |
| --- | --- | --- |
| `ToList()` 写在 `Where` 前面 | 全表进内存 | 把 `Where` 提到 `ToList` 前 |
| 循环里查库 | N+1 | `Include` / 批量 `Contains` / SQL 端聚合 |
| 只读却用跟踪查询 | 内存占用高 | `AsNoTracking()` |
| 查出全程实体只用一两列 | 拉多余的列 | `Select` 投影到 DTO |
| 全量拉内存做统计/去重/Split | 随数据量线性恶化 | 尽量在 SQL 端算（`Sum` / `Count` / `Distinct`） |
| `Update(游离实体)` 前跨了长逻辑 | 丢失更新 | 缩小窗口 / 只标记改过的列 |
| `if (状态 == 可用) { 改状态 }` | 并发下双写 | 唯一索引 / 并发令牌 |
| 同一个 `IQueryable` 被遍历多次 | 重复查库 | 先 `ToList()` 落地 |

## 四、实战踩坑清单

> 以下都是实际项目里遇到过的，排查时优先看这里。

### 1. 全局 NoTracking 下拿到游离实例再 Update，可能撞主键冲突

**现象**：抛 `The instance of entity type 'X' cannot be tracked because another instance with the same key value for {'ID'} is already being tracked.`

**原因**：跟踪器里已经有一个同主键的实例了，你又 Attach 了一个新实例。

**规避**：**用跟踪查询**（`AsTracking()` / `First()` 默认跟踪）—— 跟踪查询遇到已在跟踪的行会**返回同一个实例**，不会产生第二个对象。

### 2. `Update` 写全列导致丢失更新

见 `一.3`。要精确更新就 `Entry(e).Property(x => x.Name).IsModified = true`。

### 3. 事务内未提交的修改，查询读不读得到

见 `02` 的「四.4」。一句话：**筛条件看数据库，取实例看内存**。

### 4. 投影表达式里调用"会抛异常"的代码 -> 一条脏数据炸掉整个查询

**现象**：列表接口整个报 500，而不是只让某一行显示为空。

**原因**：`Select` 投影（以及 AutoMapper 的 `MapFrom`）是在**枚举行结果时逐行求值**的，任意一行抛异常都会中断整个查询。

**例子**：某个字段存的是残缺 JSON，投影里做 `JsonConvert.DeserializeObject` 就炸了。

**教训**：列表接口里对"可能脏"的字段做解析，**必须 `try/catch` 并降级**（返回默认值），不能让单行数据拖垮整页。

### 5. LIKE 通配符（详见 `02` 的二.2）

`StartsWith` / `EndsWith` 走 `LIKE`，值里的 `_` `%` `[` 会被当通配符。`Contains` 不受影响（走 `CHARINDEX`）。

### 6. 全量拉内存做统计

```csharp
// 因为要 Split 字符串，SQL 端做不了，所以把全表拉进内存算
var rows = query.Select(x => new { x.Id, x.Code }).ToList();
var count = rows.Select(x => x.Code.Split('-')[0]).Distinct().Count();
```

**为什么**：字符串 `Split` 在 SQL 端确实做不了。
**代价**：每次（包括每次翻页）都全量拉一遍。
**如果非要这么做**：注释里写明原因；或者用 `LEFT(Code, CHARINDEX('-', Code + '-') - 1)` 在 SQL 端算。

### 7. 枚举值复用要小心旧数据

给枚举加值时，如果**复用了已废弃的旧值**，数据库里的历史行会被按**新语义**解读。

**动手前先查库**：

```sql
select [Status], count(*) from 表名 group by [Status];
```

### 8. 数据库层零保护 = 全靠代码自觉

如果一个项目里**没有唯一索引、没有 rowversion、没有锁**，那所有的"防重复""防并发"都只在应用层的一个 `if` 里。

**单人操作、低频场景**下可能一直不出问题；**一旦并发上来**就会暴露，而且很难复现。

**要不要补**：看业务。补的话**优先唯一索引**（成本最低、最可靠）。
