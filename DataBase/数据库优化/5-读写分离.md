# 读写分离

> **所属**：[[0-数据库优化总览]] ｜ **上一篇**：[[4-归档与冷热分离]] ｜ **下一篇**：[[6-分库分表]]

## 1. 核心思想

**主库负责写，从库负责读**——把读压力从主库分流到从库：

```
应用
 ├─ 写操作 → 主库（master，唯一可写）
 └─ 读操作 → 从库（replica，只读，可多个分摊）
```

## 2. 概念澄清：读写分离 ≠ 分库分表


|      | 读写分离                             | 分库分表                      |
| ------ | -------------------------------------- | ------------------------------- |
| 本质 | **多副本**（同一份数据 N 份）        | **数据分片**（数据拆成 N 份） |
| 解决 | 读压力                               | 数据量 / 写压力               |
| 数据 | 每份都是全量                         | 每片是部分                    |
| 关系 | 可以和分库分表**叠加**（每片再主从） |                               |

## 3. 适用场景与顺序

- **读多写少**（报表、监控、流水查询——老化机台概览/详情是典型）
- 主库读压力成瓶颈（CPU/IO 高）
- **顺序**：先做方案①②③④（索引/优化/分区/归档），读还顶不住才上读写分离

## 4. 搭建方案

### sqlserver

#### Always On 可用性组（AG）—— 推荐

**组件**：主副本 + 从副本 + 可用性组 + **AG 监听器**

**要点**：

1. 至少 2 台 SQL Server 实例（1 主 1 从）
2. 依赖 WSFC 集群（Windows）/ Pacemaker（Linux）
3. `create availability group` 加入从库
4. 从库设 **Readable Secondary = Yes**
5. 配置**只读路由列表**（读连接自动重定向到从库）
6. 可用性模式：**同步提交**（强一致、写慢）/ **异步提交**（快、有延迟）

**应用连接**：

```csharp
// 写/默认 → 主库（连监听器，不带 intent）
Server=ag-listener;Database=TestDB;User Id=...;Password=...;

// 读 → 从库（加 ApplicationIntent=ReadOnly，自动路由到只读副本）
Server=ag-listener;Database=TestDB;User Id=...;Password=...;ApplicationIntent=ReadOnly;
```

⚠️ **Standard 版不支持完整 AG**（只读路由需 Enterprise）。

#### 事务日志传送（Log Shipping）

- 定时传主库日志备份到从库恢复（standby）
- 只读可用，但**延迟分钟级**，不适合实时读

### mysql

#### 主从复制（基于 binlog）

**原理**：主库写 binlog → 从库拉取 → relay log → 重放。

**配置步骤**：

1. 主库 `my.cnf`：

```ini
server-id = 1
log-bin = mysql-bin
```

2. 从库 `my.cnf`：

```ini
server-id = 2
relay-log = relay-bin
read_only = 1          # 从库只读
```

3. 主库建复制账号：

```sql
create user 'repl'@'%' identified by 'xxx';
grant replication slave on *.* to 'repl'@'%';
```

4. 主库查看 binlog 位点（记下 file + position）：

```sql
show master status;
```

5. 从库指定主库并启动（8.0 新语法；老版本用 `change master to` / `start slave`）：

```sql
change replication source to
  source_host = '192.168.1.10',
  source_user = 'repl',
  source_password = 'xxx',
  source_log_file = 'mysql-bin.000001',
  source_log_pos = 154;
start replica;
```

6. 验证延迟：

```sql
show replica status;   -- 看 seconds_behind_master 字段
```

**复制模式**：statement（语句）/ **row（行，推荐，8.0 默认）** / mixed
**半同步**：装 semi-sync 插件，`rpl_semi_sync_master_enabled=1`（主库等从库确认），减小延迟

### 其他（postgresql / oracle）

- **PostgreSQL**：流复制，`wal_level = replica`，主库 `pg_basebackup` 生成从库，配置 `primary_conninfo`
- **Oracle**：Data Guard，日志应用模式：最大保护 / 最大可用 / 最大性能

## 5. 路由层细节（EF Core）

### 方式 1：双连接串 / 双 Context（最简单，推荐起步）

```csharp
// 写：AppDbContext 用主库连接
builder.Services.AddDbContext<AppDbContext>(o => o.UseSqlServer(writeConn));
// 读：单独只读 context 用从库连接
builder.Services.AddDbContext<ReadDbContext>(o => o.UseSqlServer(readConn));
```

### 方式 2：自定义 DbCommandInterceptor 动态切连接

```csharp
public class ReadWriteInterceptor : DbCommandInterceptor
{
    private readonly string _readConn;
    private readonly string _writeConn;
    private readonly bool _forceReadMaster; // 本次请求必须读主（写过数据）

    public override InterceptionResult<DbDataReader> ReaderExecuting(
        DbCommand command, CommandEventData eventData, InterceptionResult<DbDataReader> result)
    {
        // SELECT 且无事务且允许走从 → 切从库；否则主库
        var isRead = command.CommandText.TrimStart()
                         .StartsWith("select", StringComparison.OrdinalIgnoreCase)
                     && eventData.Context!.Database.CurrentTransaction == null;
        if (isRead && !_forceReadMaster)
            ((SqlConnection)command.Connection).ConnectionString = _readConn;
        return result;
    }
}
```

**核心规则**：`SELECT 且无事务 → 从库；否则 → 主库`；**事务内的读强制主库**。

### 方式 3：中间件/代理

- ProxySQL / MyCat 等；应用无感知，但引入新组件，.NET 生态不优先

## 6. 主从延迟解决方案（实施细节）

### ① 写后立即读 → 走主库（最关键）

```csharp
// 中间件：请求开始时允许读从库
app.Use(async (ctx, next) => {
    ctx.Items["canReadReplica"] = true;   // 默认允许
    await next();
});
// 任何写操作（SaveChanges 写主库）后置 false
// → 本次请求后续读也强制走主库
```

### ② 业务分类

- 可容忍延迟（列表/报表/概览）→ 从库
- 必须实时（工单当前状态、自己刚操作的数据）→ 主库

### ③ 半同步 / 同步提交（数据库层）

- SQL Server AG：可用性模式设**同步提交**（延迟≈0，写变慢）
- MySQL：启用 semi-sync 插件
- 只对强一致的表/场景开，其余异步

### ④ 延迟监控 + 自动降级（进阶）

- 监控从库延迟（SQL Server `last_commit_time`；MySQL `seconds_behind_master`）
- 延迟超阈值（如 5s）→ 读自动切回主库，稳定后再切回

### ⑤ 加缓存（治本之一）

- 热点读加 Redis，命中缓存不落库 → 减读压力 + 降低对延迟敏感

## 7. 落地优先级（针对本场景）

```
① 双连接串/双 context 起步（最简单）
② 写后本次请求强制读主（延迟坑）→ 请求标记
③ 可容忍延迟的读走从库（业务分类）
④ 再上：半同步 + 延迟监控自动降级
```

⚠️ **现在单库就够**：这套是"读 QPS 真顶不住"才上，别在没到瓶颈时引入（副本+路由+一致性是新增复杂度）。
