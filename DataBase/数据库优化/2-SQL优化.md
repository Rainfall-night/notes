## 1. 核心思想：两条主线

```
主线一：减少"读取量"  —— 走索引、只取需要的列、覆盖索引（少读页、少回表）
主线二：减少"处理量"  —— 避免全表扫描、大排序、临时表、深分页（少 CPU/内存/IO）
```

索引是"硬件"，SQL 写法是"怎么用硬件"——索引建得再好，写法不对照样白搭。

## 2. 只取需要的列

- 别 `select *`——尤其日志表的 `Content`（大 JSON 字段），取它必回表、多读大字段
- `select WorkOrderID, ModifyTime ...` 能走覆盖索引，直接省掉回表

## 3. WHERE 写法与索引（最容易栽的坑）


| 写法                                                  | 后果                          |
| ------------------------------------------------------- | ------------------------------- |
| `where YEAR(ModifyTime)=2026`（函数包裹索引列）       | ❌ 索引失效                   |
| `where WorkOrderID='123'`（字符串 vs 数字，隐式转换） | ❌ 索引失效                   |
| `like '%xx%'`（前导通配符）                           | ❌ 索引失效（`'xx%'` 才走）   |
| `between` / `>` / `<`（范围）                         | ✅ 走索引，但范围列后的列失效 |
| `or` / `not in`                                       | ⚠️ 可能全表扫描，看执行计划 |
| `where 列 is null`                                    | ⚠️ 一般不走普通索引（除非筛选索引或特意处理） |

## 4. 分页优化（大数据量最重要的一环）

### 4.1 分页语法：各数据库对比（重点）

**偏移分页（OFFSET/LIMIT）**——"跳过 N 行再取"：


| 数据库                     | 语法                                                                 | 备注                                   |
| ---------------------------- | ---------------------------------------------------------------------- | ---------------------------------------- |
| **MySQL**                  | `... limit 20, 10`（跳过20取10）`... limit 10 offset 20`（等价）     | 最常见                                 |
| **PostgreSQL**             | `... limit 10 offset 20``... offset 20 rows fetch next 10 rows only` | 支持 SQL:2008                          |
| **SQL Server 2012+**       | `... order by ID offset 20 rows fetch next 10 rows only`             | ⚠️**必须带 order by**，SQL:2008 标准 |
| **SQL Server 2008 及更早** | `top n` + `row_number()` 子查询                                      | 见下方示例                             |
| **Oracle 12c+**            | `... order by ID offset 20 rows fetch next 10 rows only`             | 老版本用`rownum`                       |
| **SQLite**                 | `... limit 20, 10`                                                   | 同 MySQL                               |

**SQL Server 偏移分页两种写法**（你没用过，重点看）：

```sql
-- ① 推荐（2012+）：OFFSET/FETCH，必须带 ORDER BY
select * from tbl_WorkOrder
order by ID
offset 20 rows fetch next 10 rows only;     -- 跳过 20 行，取 10 行

-- ② 老版本（2008/2005）：TOP + ROW_NUMBER() 子查询
select * from (
    select *, ROW_NUMBER() over (order by ID) as rn
    from tbl_WorkOrder
) t where rn between 21 and 30;
```

**游标分页（Keyset/Seek）**——"从某条已知记录之后取"，**是查询思路不是语法，所有库通用**：

```sql
-- MySQL
select * from tbl_WorkOrder where ID > 1234567 order by ID limit 10;
-- SQL Server
select top 10 * from tbl_WorkOrder where ID > 1234567 order by ID;
-- 或（2012+）
select * from tbl_WorkOrder where ID > 1234567 order by ID offset 0 rows fetch next 10 rows only;
```

### 4.2 数据库执行分页的本质（关键认知）

**不是"先把所有符合条件的行查出来再取一页"**，而是**流式迭代**：

```
用索引从起始位置扫 → 逐行判断筛选 → 符合的计数 → 数够目标行数立即停止
```

- **证明**：如果先物化全部符合行，那 OFFSET 深页和浅页性能应该一样；但实际"越深越慢"→ 说明是从头扫到目标位置
- **物化中间结果 + Sort** 只在"排序不走索引"时发生——那是性能陷阱，**分页的排序列必须有索引**

### 4.3 OFFSET 偏移分页的问题

- 每翻一页，从头扫到该页位置再丢弃前面所有行 → **页码越深越慢**（深分页灾难）
- 性能与"页码深度"成正比：`O(跳过行数)`

### 4.4 Keyset（游标/Seek）分页——顺序翻页正解

**原理**：不跳行，记住"上一页最后一条的排序键值"，从那里继续取。

```sql
-- 上一页最后一条 ID = 1234567，取下一页：
select * from tbl_WorkOrder where ID > 1234567 order by ID ...取 N 条;
```

**要求**：

- **排序键必须唯一**（否则漏行/重行）——不唯一的列要加唯一兜底：
  ```sql
  -- 复合键：order by ModifyTime desc, ID desc
  where (ModifyTime < '2026-08-13 10:00')
     or (ModifyTime = '2026-08-13 10:00' and ID < 999999)
  ```
- 升序用 `> 上次值`，降序用 `< 上次值`
- **性能恒定**：永远只扫一页，与页码深度无关

**实现方式**：后端每次返回 `{ items, nextCursor }`，前端原样透传游标，下一页带回。

**代价**：不能页码跳转（只能顺序/加载更多）；要存游标。

### 4.5 下界裁剪跳页（单调 ID 排序时的方案）

**前提**：排序键 = **单调自增 ID**。跳 N 页可用**物理位置估算**裁剪扫描下界：

```sql
-- 当前页最后 ID=1000，一页 50，跳 3 页（第 4 页）：
where ID >= 1000 + 3*50  and 筛选条件  order by ID  取 50 条
```

- **下界安全**：第 N 页之前有 `N×pageSize` 条符合筛选的行，至少占 `N×pageSize` 个物理 ID → 估算下界**永远不会超过真实起始**，不漏数据
- **结果精确**：从估算下界扫，凑够的 50 条正是第 N 页
- **性能**：省掉"表头~估算下界"的扫描；但还要扫"估算下界~真实起始"的间隙，**间隙大小取决于筛选过滤率**（过滤率高间隙大，但最差也不比 OFFSET 差）
- **前提**：必须单调 ID（能用数值公式）；`ModifyTime` 等不均匀列无法估算

### 4.6 分页方案决策


| 场景                                 | 方案                                   |
| -------------------------------------- | ---------------------------------------- |
| 数据量小（万级内）                   | `LIMIT/OFFSET` 够用，简单              |
| 数据量大 +**顺序翻页/加载更多**      | **Keyset**（游标）                     |
| 数据量大 +**页码跳转** + 单调自增 ID | **下界裁剪**（`lastId + N×pageSize`） |
| 必须精确页码 + 非单调排序键          | OFFSET（接受深页慢）                   |
| **一切分页的前提**                   | **排序列必须有索引**，否则先补索引     |

## 5. 统计信息 & 参数嗅探

- 统计信息过期 → 优化器选错执行计划（表大改后要更新统计）
- 同一查询不同参数执行计划不同（参数嗅探）→ 必要时 `OPTION(RECOMPILE)`

## 6. ORM / 查询写法

- **避免 N+1**：循环里逐条查 = N 次查询 → 用 JOIN / Include / 批量
- **判断"存在"用 `EXISTS`**（短路）通常比 `IN` 子查询高效
- **JOIN 注意去重**：一对多 join 会产生重复行

## 7. 针对本场景建议

- `tbl_WorkOrderLog` 流水分页（时间倒序）→ **Keyset**，排序键 `(ModifyTime, ID)`
- `tbl_WorkOrder` GetList 深分页（自增 ID）→ **下界裁剪**或 OFFSET，排序键 `ID`
- 条件 COUNT（分页总数）→ 能走索引即可接受；无筛选全表 COUNT 亿级会慢
