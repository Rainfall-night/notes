# 归档与冷热分离

> **所属**：[[0-数据库优化总览]] ｜ **上一篇**：[[3-表分区]] ｜ **下一篇**：[[5-读写分离]]

## 1. 核心思想：冷热分离

数据天生分冷热：
- **热数据**：近期（如近 1 年日志），高频访问
- **冷数据**：历史（1 年前日志），几乎没人查

**把冷数据从在线表挪走** → 在线表体量骤减 → **所有在线查询自动变快**。

## 2. 为什么是"性价比之王"

- 日志/流水表**天然冷热分明**，归档逻辑天然成立
- 在线表从**十亿 → 几百万**，索引、扫描、缓存全部受益
- **零复杂度、零风险**（不涉及分库分表那套）

> 一句话：**在线表只要保持"小"，什么都快。** 归档就是让在线表保持小的最省事办法。

## 3. 三种实现方式

### 方式 A：后台任务迁移（未分区时）

```sql
-- ① 把一年前的日志 insert 到归档表
insert into log_archive (id, workorderid, modifytime, content)
select id, workorderid, modifytime, content
from tbl_workorderlog
where modifytime < '2025-01-01';

-- ② 再分批 delete 在线表（⚠️ 不能一次删亿行，见第 5 节坑）
```

### 方式 B：分区切换（已分区时，最优）——衔接 [[3-表分区]]

```sql
-- 秒级把旧分区整段切到归档表，不用 delete
alter table tbl_workorderlog switch partition 2 to log_archive;
```

### 方式 C：归档库 / 只读库

- 冷数据放**另一个库**（甚至另一台机器/对象存储）
- 归档库**只读**，历史查询走它
- 在线表更轻，归档库也不影响在线性能

## 4. 归档策略设计

| 设计点 | 建议 |
|--------|------|
| 保留窗口 | 在线保留多久（如 1 年），其余归档 |
| 归档表结构 | 可和在线表相同，也可**精简**（冷数据不需要全字段/全索引） |
| 归档查询 | 历史查询走归档（只读接口/直接查归档库） |
| 执行频率 | 每月/每日定时任务跑一次 |

## 5. 两个关键坑

### 坑 1：🔴 别直接 DELETE 亿级数据

一次 `delete` 1 亿行：
- 慢到死
- 事务日志膨胀（每行都记日志）
- 锁表（期间在线写入全堵）

**正确姿势（分批删）**：

```sql
while 1 = 1 begin
    delete top (50000) from tbl_workorderlog
    where modifytime < '2025-01-01';
    if @@rowcount = 0 break;
end
```

或直接用**分区切换**（方式 B）——秒级正道。

### 坑 2：归档 ≠ 删除

冷数据**不是不要了，是"挪走"**：
- 要能查历史（归档表/库只读可查）
- 归档是"**转移**"，不是"丢弃"

## 6. 与分区的最佳组合

```
① 表按时间分区（方案③）
② 定时把"N 个月前"的分区 switch 到归档表（秒级）
③ 在线表永远只保留最近 N 个月 → 体量恒定
```

**分区 + 归档 = 大日志表的终极运维方案**：秒级归档、在线表恒小。

## 7. 针对本场景

- `tbl_workorderlog` 在线保留 **1 年**，1 年前 → 归档表/归档库（只读）
- 已分区 → 用 `switch` 秒级归档；未分区 → 分批 insert+delete 后台任务
- 归档表按历史查询模式建少量索引即可
