# 分库分表

> **所属**：[[0-数据库优化总览]] ｜ **上一篇**：[[5-读写分离]] ｜ **下一篇**：（系列最后一篇）

## 1. 核心思想

**单库单表有物理极限，分库分表是把数据从"一个库/一张表"物理拆到"多个库/多张表"。**

前面 5 个方案（索引/SQL/分区/归档/读写分离）都是在**单库单表内部**做优化，解决的是**读**的问题；而分库分表是**横向扩容**，解决的是另外两类问题：


| 瓶颈               | 现象                                                                           | 单库内优化能救吗                           |
| -------------------- | -------------------------------------------------------------------------------- | -------------------------------------------- |
| **单表数据量过大** | 表几亿~几十亿行，索引再优化也扛不住（索引大、内存缓存命中率低、B+ 树层数增加） | 分区/归档能缓解一部分，但有上限            |
| **写入成为瓶颈**   | 单库写 QPS 到几千就顶不住（磁盘 IO、锁竞争、事务日志）                         | **救不了**——读写分离只分摊读，写仍是单点 |

```
单库单表  →  索引/SQL/分区/归档/读写分离  →  都是"原地优化"
分库分表  →  物理拆成多份              →  是"扩容"
```

## 2. 什么时候才需要（触发条件）

分库分表**成本极高**，必须满足"硬指标"才值得考虑，缺一个都不要碰：


| 触发条件         | 大致阈值                              | 说明                                   |
| ------------------ | --------------------------------------- | ---------------------------------------- |
| 单表行数         | 千万 ~ 亿级以上                       | 且索引优化、分区、归档都做过了仍扛不住 |
| 写入 QPS         | 单库几千 QPS 持续打满                 | 写是硬瓶颈，读多写少用不上它           |
| 存储容量         | 单实例磁盘/IOPS 到顶                  | 扩容无非加磁盘还是加机器的问题         |
| 架构复杂度承受力 | 团队能维护分布式事务/全局 ID/跨库查询 | 没有运维能力 = 埋雷                    |

**核心判断：前面方案全部做完仍然不够，才轮到它。** 如果连索引都还没建、查询几十毫秒到几百毫秒，分库分表是杀鸡用牛刀。

## 3. 四种拆分方式（先分清术语）

"分库分表"其实是四个维度，很多人混为一谈：


| 方式         | 做法                        | 例子                                | 解决                           |
| -------------- | ----------------------------- | ------------------------------------- | -------------------------------- |
| **垂直分库** | 按业务模块拆到不同库        | 订单库 / 用户库 / 库存库            | 模块间相互拖累（IO/锁/连接数） |
| **垂直分表** | 一张宽表按字段拆            | 大字段、不常查字段挪到附属表        | 行宽过大、冷热字段混杂         |
| **水平分表** | 同一张表按分片键拆成多张表  | `user_0 / user_1 / user_2 / user_3` | 单表行数爆炸                   |
| **水平分库** | 同一张表拆到多个**实例/库** | 每库放一部分行，路由定位            | 单实例存储/写入/IO 瓶颈        |

> **垂直拆**解决的是"表太宽/模块耦合"，**水平拆**解决的是"行太多/单点容量"。
> 数据量大到亿级，方向基本都是**水平拆分**——垂直拆不减少行数。

## 4. 分片键（Sharding Key）—— 最重要的一步

**分片键 = 决定一条数据去哪个分片的那一列。** 选错全盘皆输，且后期几乎无法改。

### 4.1 选择原则

1. **选查询最常用的字段**——保证 80% 以上查询能带上它
2. **基数大、分布均匀**——避免某一片成为热点
3. **不可变/少变**——分片键改了 = 数据要搬片
4. **能覆盖核心业务路径**——比如按用户 ID 拆，则"查某用户的所有订单"天然单片查询

### 4.2 好与坏


|    | 分片键                           | 结果                 |
| ---- | ---------------------------------- | ---------------------- |
| ✅ | `user_id`（查某用户的订单）      | 单片查询，快         |
| ❌ | `order_id`（却常按 user 查订单） | 每次要广播全片，白拆 |
| ❌ | `status`（只有少数几个值）       | 热点片，等于没拆     |

### 4.3 残酷现实

**为了一个高频查询方便，你把其它所有查询都变难了：**

```
按分片键查   →  路由到 1 片，单片查，快
不带分片键查 →  广播到所有片，各自查再合并，慢（甚至比不分片还慢）
```

所以在决定分片键之前，要统计**所有查询里有多少比例能带上它**——这是分库分表前必做的评估。

## 5. 路由算法：数据怎么定位

### 5.1 取模（hash mod n）

```
片号 = hash(分片键) mod n        // n = 分片数
```

- ✅ 实现最简单、分布均匀
- ❌ **扩容灾难**：n 变了，几乎所有数据要重算、迁移

### 5.2 一致性哈希（Consistent Hashing）

**哈希环原理**：

```
把 hash 值域组织成一个环（0 ~ 2^32-1）
1. 每个分片节点（node）hash 后放到环上
2. 每条数据 hash(分片键) 后，沿环顺时针找第一个节点 = 归属片
```

**虚拟节点**：给每个物理节点复制 N 个虚拟位置散布在环上，解决真实节点少导致的分布不均。

- ✅ **扩容只迁移少量数据**（只影响新节点顺时针区间内的数据）
- ❌ 实现复杂，均匀性要靠虚拟节点调

### 5.3 范围分片（Range）

按分片键的区间切，如 `id 1~1亿 → 片0`、`1亿~2亿 → 片1`、按时间按月切。

- ✅ 扩容友好（加一段区间即可）、天然支持范围查询
- ❌ **热点**：新数据全写到最后一段（如按时间拆，最新数据永远打爆最后一片）

### 5.4 对比


| 算法       | 均匀性           | 扩容           | 实现 | 典型场景                 |
| ------------ | ------------------ | ---------------- | ------ | -------------------------- |
| 取模       | 好               | 差（要重分布） | 简单 | 数据量稳定、很少扩       |
| 一致性哈希 | 中（靠虚拟节点） | 好（少量迁移） | 复杂 | 经常扩容、节点动态增减   |
| 范围分片   | 差（热点）       | 好             | 简单 | 按时间归档类、能接受热点 |

## 6. 全局唯一 ID —— 拆完之后第一个坑

**自增主键每片各自独立，会撞号**（片0 和片1 都生成 id=100）。必须有全局唯一 ID 方案：

### 6.1 雪花算法（Snowflake）—— 最主流

一个 64 位 long，拆成三段：

```
 41 bit 时间戳（毫秒） | 10 bit 机器 ID | 12 bit 序列号
 ──────────────────── ─────────────── ────────────────
      约 69 年          1024 台机器      每毫秒 4096 个
```

- ✅ 趋势递增（对索引友好）、本地生成零依赖、高性能
- ❌ 依赖**机器时钟**——时钟回拨会撞号（需做回拨保护）

### 6.2 号段模式（Segment）

数据库维护一张号段表，应用一次性取一段（如 `[1001, 2000]`）内存里发号，用完再取。

- ✅ 性能好、无时钟依赖
- ❌ 段用尽时要多一次 DB 访问；依赖中心 DB（本身又要防单点）

### 6.3 UUID 对比


| 方案 | 趋势 | 索引友好度                            | 长度 | 依赖     |
| ------ | ------ | --------------------------------------- | ------ | ---------- |
| 雪花 | 递增 | 好                                    | 8B   | 机器时钟 |
| 号段 | 递增 | 好                                    | 8B   | 中心 DB  |
| UUID | 随机 | **差**（随机插入 → B+ 树页分裂频繁） | 16B  | 无       |

> 随机主键导致页分裂的机制：见 [[1-索引优化#8. 页分裂 & 索引碎片|页分裂与索引碎片]]

## 7. 拆完带来的新问题（最劝退的部分）

分库分表把一个单点问题，换成了一堆**分布式问题**——代价远大于收益时别碰：


| 问题             | 说明                                | 常见应对                           |
| ------------------ | ------------------------------------- | ------------------------------------ |
| **跨库 join**    | 分片键不同的两张表没法在一个库 join | 数据冗余 / 应用层多次查询组装      |
| **全局排序分页** | `order by` 要每片排序再合并         | 深分页几乎不可行，只能靠分片键收敛 |
| **分布式事务**   | 一次业务改多库，要么全成要么全败    | 见下节（2PC/TCC/本地消息表）       |
| **扩容**         | 取模路由扩片要重分布                | 停机迁移 / 双写过渡                |
| **跨片聚合**     | count/sum 要全片汇总再合并          | 结果不准（多片并发读）             |

### 7.1 分布式事务详解

单库事务靠 `begin`/`commit`/`rollback` 就能保证 ACID；拆库后跨库无法用数据库原生事务，只能靠下面几种：

**① 两阶段提交（2PC）**

```
协调者 → 问所有参与者"能提交吗？"（prepare 阶段）
       → 全部说 yes → 让所有人 commit（commit 阶段）
       → 有一个人说 no → 让所有人 rollback
```

- ✅ 强一致
- ❌ 协调者是单点；prepare 后参与者要**长时间持有锁**（阻塞），故障时可能卡死

**② TCC（Try / Confirm / Cancel）**

```
try       → 先冻结资源（不真正扣减）
confirm   → 确认扣减（try 全部成功才执行）
cancel    → 回滚释放（try 有失败就全 cancel）
```

- ✅ 性能比 2PC 好、不长期持锁
- ❌ 每个操作都要写三段逻辑，**开发量大**；且 confirm/cancel 要支持重试、幂等

**③ 本地消息表 / 最终一致**

```
业务库里多写一张"待发消息表"，和业务操作同库事务提交
后台异步把消息发出去，消费者幂等处理
```

- ✅ 实现相对简单、不阻塞主流程
- ❌ 只保证**最终一致**（不是强一致），有延迟窗口

> **结论**：分布式事务没有免费的，无论哪种都让简单业务变复杂、变慢。这也是分库分表"杀敌一千自损八百"的根本原因。

## 8. 中间件生态：Java 成熟，.NET 几乎空白


| 生态 | 中间件                   | 成熟度                                              |
| ------ | -------------------------- | ----------------------------------------------------- |
| Java | ShardingSphere / MyCat   | 生产级，JDBC 代理透明接入，分片路由/ID/读写分离全包 |
| .NET | ShardingCore（社区项目） | 功能不全、更新慢、生产案例少                        |
| .NET | 自己封装路由层           | 分片路由 + 全局 ID + 分布式事务全要自己写           |

**中间件成熟 = 复杂度被框架吸收**，所以 Java 上分库分表是常规操作；.NET 没有这层吸收，等于所有复杂度都得团队自己扛——成本不是一个量级。

## 9. 决策路线图

```
数据量大 / 写入瓶颈？
 ├─ 还没建索引 → 先建索引（最便宜，收益最高）→ [[1-索引优化]]
 ├─ 旧数据多   → 归档 / 分区 → [[4-归档与冷热分离]] [[3-表分区]]
 ├─ 读压力大   → 读写分离 → [[5-读写分离]]
 ├─ 上面都做完了还不够，且写确实是硬瓶颈？
 │    ├─ 是 → 评估分片键 + 路由 + 全局 ID + 分布式事务（成本很高）
 │    └─ 否 → 停在原地，别为不存在的问题付钱
 └─ 有成熟中间件（Java）？没有（.NET）→ 慎重再慎重
```
