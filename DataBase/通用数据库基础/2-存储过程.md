# 存储过程

> **所属**：通用数据库基础 ｜ **主题**：存储过程 Stored Procedure

## 1. 存储过程是什么

- **本质**：一组**预先定义并保存在数据库里**的 SQL 语句 + 过程化逻辑，有名字、有参数、可被反复调用
- 三个核心特征：
  1. **可参数化**（`IN` / `OUT` / `INOUT`）
  2. **有过程化控制流**（变量、`IF`、循环、游标、异常处理）
  3. **在服务端执行**（离数据最近）
- 它属于"**数据库里的程序**"，和视图（一条查询）、函数（可嵌入表达式的计算单元）是并列的三类对象
- 所谓"**预编译**"：多数数据库在**首次执行**时生成执行计划并缓存；这个概念被神话了，见第 6 节

## 2. 与其他数据库对象的边界

| 对象 | 有参数 | 有控制流 | 返回值 | 能返回结果集 | 能嵌在 `SELECT` 里 | 能修改数据 |
|---|---|---|---|---|---|---|
| **视图** | 无 | 无 | - | 有（当表查） | 有 | 受限 |
| **标量函数** | 有 | 视库 | 单个值 | 无 | **有** | 通常不能 |
| **表值函数** | 有 | 视库 | 一张表 | 有 | **有** | 通常不能 |
| **存储过程** | 有 | 有 | 返回码 / `OUT` 参数 | 有（可多个） | **不能** | 能 |
| **触发器** | 无 | 有 | - | 通常无 | 不能 | 能（被动触发） |
| **匿名块** | 视库 | 有 | - | 视库 | 不能 | 能 |

三条最实用的结论：

1. **存储过程不能被 `SELECT` 调用**，只能用 `EXEC` / `CALL`
2. **函数必须"能在表达式里用"**，所以被限制得很死（多数库不允许函数内改数据、开事务、用动态 SQL）
3. **触发器不能传参数**，它是被动的 —— 想复用同一段逻辑，用过程，不要用触发器

## 3. 分类

| 维度 | 类别 |
|---|---|
| 归属 | **系统存储过程**（SQL Server `sp_*`、Oracle `DBMS_*` 包）/ **用户存储过程** |
| 返回形态 | 返回结果集 / 只返回 `OUT` 参数 / 只返回状态码 |
| 实现语言 | T-SQL / PL/pgSQL / PL/SQL / SQL PL / 甚至外部语言（PostgreSQL 支持 `plpython`、`plv8` 等） |
| 组织方式 | **裸过程** / **包 Package**（Oracle 特有，把过程和函数打包成命名空间） |
| 生命周期 | 永久 / 临时（SQL Server 支持 `CREATE PROCEDURE #temp_proc`） |

## 4. 语法要素（跨库对照）

### 4.1 参数

| 库 | 声明 | 调用 | 默认值 |
|---|---|---|---|
| SQL Server | `@p int`、`@p int OUT` | `EXEC p @p = 1` | **支持** `@p int = 1` |
| MySQL | `IN p INT`、`OUT p INT`、`INOUT p INT` | `CALL p(1, @out)` | **不支持** |
| PostgreSQL | `p int`、`p int`（OUT 用 `OUT` / `INOUT`） | `CALL p(1)`；命名参数 `p => 1` | 支持 `DEFAULT` |
| Oracle | `p IN NUMBER`、`p OUT NUMBER` | `BEGIN p(1); END;` | 支持 `:=` 默认值 |

### 4.2 变量与控制流

```sql
-- SQL Server
create procedure dbo.p_demo @n int
as
begin
    set nocount on;
    declare @i int = 0;
    while @i < @n
    begin
        set @i = @i + 1;
    end;
end;
```

```sql
-- PostgreSQL (PL/pgSQL)
create or replace procedure p_demo(n int)
language plpgsql
as $$
declare
    i int := 0;
begin
    while i < n loop
        i := i + 1;
    end loop;
    raise notice 'done %', i;
end;
$$;
```

```sql
-- MySQL（命令行里必须先改分隔符）
delimiter $$
create procedure p_demo(in n int)
begin
    declare i int default 0;
    while i < n do
        set i = i + 1;
    end while;
end$$
delimiter ;
```

```sql
-- Oracle (PL/SQL)
create or replace procedure p_demo(n in number) is
    i number := 0;
begin
    while i < n loop
        i := i + 1;
    end loop;
    dbms_output.put_line('done ' || i);
end;
/
```

### 4.3 游标（逐行处理）

| 库 | 写法 |
|---|---|
| SQL Server | `declare c cursor for select ...; open c; fetch next from c into @a; ... close c; deallocate c;` |
| PostgreSQL | `for rec in select ... loop ... end loop;`（隐式游标，最省事） |
| MySQL | `declare c cursor for select ...;` + `declare continue handler for not found` 判断结束 |
| Oracle | `cursor c is select ...; open c; loop fetch c into v; exit when c%notfound; end loop; close c;` |

> **警告**：游标是**反模式**，见第 9 节。能用集合运算就别逐行。

### 4.4 异常处理

| 库 | 写法 |
|---|---|
| SQL Server | `begin try ... end try  begin catch ... end catch`；`ERROR_MESSAGE()`、`XACT_STATE()` |
| PostgreSQL | `begin ... exception when others then ... end;`；`get stacked diagnostics` |
| MySQL | `declare continue handler for sqlexception ...`；`declare exit handler for sqlstate '23000' ...` |
| Oracle | `exception when no_data_found then ... when others then ...;`；`sqlcode` / `sqlerrm` |

### 4.5 事务

- 过程内可以开/提交/回滚事务；**事务范围要尽量小**（锁范围 = 事务范围）
- 嵌套事务不是真嵌套：SQL Server 用 `@@TRANCOUNT` 计数，`ROLLBACK` 会整体回滚；`SAVE TRANSACTION` 才能部分回滚
- Oracle 的 **自治事务** `pragma autonomous_transaction`：过程内独立提交，脱离调用方事务（适合写日志）
- PostgreSQL 11+ 的过程内**可以** `COMMIT` / `ROLLBACK`；**函数内不可以**

### 4.6 动态 SQL 与 SQL 注入

| 库 | 不安全的拼串 | 正确的参数化 |
|---|---|---|
| SQL Server | `exec(@s)` | `exec sp_executesql N'... where a = @p', N'@p int', @p = 1` |
| PostgreSQL | `execute 'select ... where a = ' \|\| v` | `execute format('... where a = %L', v) using ...`（`%I` 标识符、`%L` 字面量） |
| MySQL | `set @s = concat('...', v); prepare s from @s` | `prepare s from '... where a = ?'; execute s using @v` |
| Oracle | `execute immediate '... ' \|\| v` | `execute immediate '... where a = :1' using v`；标识符用 `dbms_assert` 校验 |

**唯一原则：能参数化就不要拼字符串。** 动态 SQL 是存储过程里最常见的漏洞来源。

### 4.7 返回

| 形态 | 说明 |
|---|---|
| **结果集** | 过程里直接 `select`，调用方拿到结果集（可多个） |
| **返回码** | SQL Server `return 0`；调用方 `exec @rc = p` |
| **`OUT` 参数** | 最通用的"返回单值"方式，跨库语义一致 |
| **两种混用** | 可以同时 `select` 结果集 + 赋值 `OUT` 参数 |

## 5. 调用与集成

### 5.1 数据库客户端

```sql
exec dbo.p_demo @n = 5;                 -- SQL Server
call p_demo(5);                          -- MySQL / PostgreSQL(procedure)
select p_demo(5);                        -- PostgreSQL(函数)
begin p_demo(5); end;                    -- Oracle
```

### 5.2 应用层调用

| 技术 | 方式 |
|---|---|
| ADO.NET | `command.CommandType = CommandType.StoredProcedure;` + `Parameters.Add("@p", ...)` |
| EF Core | 不直接映射存储过程；用 `FromSqlRaw` / `SqlQueryRaw` / `ExecuteSqlRaw` 调用；或 ADO.NET 接口绕过 |
| JDBC | `CallableStatement` + `registerOutParameter` |
| MyBatis | `<select statementType="CALLABLE">` |

### 5.3 权限

- 最小授权：`GRANT EXECUTE ON dbo.p_demo TO app_user;`（而不是给底表 `SELECT`）
- SQL Server **所有权链**：底表与过程同属一个 owner 时，只授 `EXECUTE` 就够，不必授表权限
- SQL Server `EXECUTE AS` / Oracle `AUTHID` / PostgreSQL `SECURITY DEFINER`：让过程"以定义者身份运行"，但要小心**提权风险**

## 6. 性能真相（破除"预编译所以快"的神话）

### 6.1 "预编译"基本不成立

- 现代数据库对**参数化查询**同样会缓存执行计划；只要 SQL 是参数化的（而不是拼串），ad-hoc 查询的性能与存储过程**基本相当**
- 所以"存储过程比 SQL 快"这条**不成立**，至少不是主要理由

### 6.2 唯一真实的性能优势：**减少往返 + 减少传输量**

- 数据在服务端，过程在**数据旁边**把几百万行明细算成几百行结果，只把结果传回来
- 这才是存储过程无可替代的场景：**远端库 + 海量明细 + 只想要聚合结果**
- 反过来说：如果数据在**本地文件库**、或明细量本来就小，这条优势就不存在

### 6.3 常见的性能坑

| 坑 | 说明 | 对策 |
|---|---|---|
| **参数嗅探 Parameter Sniffing** | SQL Server 用**首次编译时的参数值**生成计划，后续分布不同的参数复用错计划 | `OPTION (RECOMPILE)` / `OPTIMIZE FOR` / `WITH RECOMPILE`；或把参数赋给局部变量 |
| **计划缓存污染 / 频繁重编译** | 大过程里任一语句变化都会重编译整批 | 拆小过程；避免用临时表做大量中间结果 |
| **隐式类型转换** | 参数类型与列类型不一致（如 `nvarchar` 参比 `varchar` 列）-> **索引失效** -> 全表扫描 | 参数类型与列严格一致 |
| **逐行处理** | 游标/循环把集合操作退化成 N 次单行操作 | 改成集合运算（`UPDATE ... FROM`、`MERGE`） |
| **过程的临时表统计信息缺失** | 临时表/表变量让优化器估算不准 | 加 `OPTION (RECOMPILE)` 或改用临时表 + 显式统计 |
| **长事务** | 过程内事务太长 -> 锁等待、阻塞、死锁 | 缩小事务范围，先算后写 |

## 7. 优点

| 优点 | 说明 |
|---|---|
| **可参数化** | 视图做不到 |
| **过程化能力** | 变量、分支、循环、游标、异常处理、事务 |
| **减少网络往返与传输量** | 在数据旁算完，只回传结果（**最真实的优势**） |
| **安全性** | 只授 `EXECUTE` 不授表权限；参数化天然防注入 |
| **复用与一致性** | 一段逻辑一处维护，多个调用方共享 |
| **变更管控** | 生产环境可做到"只有 DBA 能改"，过程体变更是受控事件 |
| **一次调用完成多步** | 多语句 + 事务打包，避免中间状态外泄 |

## 8. 缺点与风险

| 风险 | 说明 |
|---|---|
| **逻辑藏进数据库** | 代码仓库里搜不到，`git log` 追不到，评审看不见 |
| **版本管理差** | 必须额外维护迁移脚本，极易与代码库脱节 |
| **调试与测试困难** | 打不了断点、不能重构、不能单元测试（要连真库） |
| **可移植性差** | T-SQL / PL/pgSQL / PL/SQL 各写一套，换库等于重写 |
| **组织/职责问题** | 业务逻辑一半在应用、一半在 DB；两人各改一半，冲突难查 |
| **参数嗅探等执行计划陷阱** | 见第 6.3 节，排查成本高 |
| **权限过大风险** | `EXECUTE AS` / `SECURITY DEFINER` 配错 -> 提权 |
| **技术人才依赖** | 复杂过程只有原作者看得懂，人走代码废 |
| **与 CI/CD 不适配** | 应用能自动化测试/灰度，过程通常只能"改完就看" |

## 9. 常见反模式

| 反模式 | 为什么坏 | 替代 |
|---|---|---|
| **游标/循环逐行处理** | 100 万次单行操作 vs 一次集合操作，差几个数量级 | `UPDATE ... FROM`、`MERGE`、`INSERT ... SELECT` |
| **把业务规则写进过程** | 规则进库后无法评审、无法回滚、无法灰度 | 留在应用层，库里只做数据搬运和聚合 |
| **万能巨型过程** | 几百行、参数十几个、分支套分支 | 拆成多个小过程 + 一个编排过程 |
| **拿存储过程当 API 层** | 每次接口变更都要动数据库 schema | 用应用层 API，库只做数据 |
| **过程内拼动态 SQL** | 注入 + 计划缓存爆炸 | 参数化（`sp_executesql` / `format ... using`） |
| **过程内开长事务** | 锁等待、阻塞、死锁 | 先算完再写，事务只包写 |
| **用过程做"定时批量"却无幂等** | 重跑一次数据翻倍 | 加幂等条件（`NOT EXISTS` / 状态位） |

## 10. 选型判据（什么时候用 / 不用）

**适合用存储过程**

- 数据在**远端数据库**上，且**明细量巨大**，而只需要**聚合结果**（最大价值场景）
- 需要**原子地**完成多步写入 + 事务
- 需要**严格的执行权限收敛**（只让调用方 `EXECUTE`，看不到底表）
- 极高频的简单操作，且参数化后能显著减少往返
- 组织的 DBA/开发职责本身就要求"逻辑在库里"（这是组织决策，不是技术决策）

**不适合用存储过程**

- 逻辑**还在快速迭代**（应用层改一行 vs 改库对象 + 迁移脚本）
- 数据在**本地/嵌入式库**（SQLite 之类，本身不支持）
- 明细量不大，**网络往返不是瓶颈**
- 需要**单元测试、评审、灰度、回滚**（库对象都很难做）
- 需要**跨数据库移植**

## 12. 调试、运维与版本管理

### 12.1 调试手段

- **打印/日志**：`PRINT`(SQL Server) / `RAISE NOTICE`(PG) / `DBMS_OUTPUT.PUT_LINE`(Oracle) / `SELECT` 临时输出
- **分步执行**：把过程体拆分，逐段单独跑，比对中间结果
- **执行计划**：SQL Server `SET STATISTICS IO/TIME ON` + 实际执行计划；PG `EXPLAIN (ANALYZE, BUFFERS)`；MySQL `EXPLAIN ANALYZE`
- **执行历史**：见 11 节末尾的执行统计视图，找"最耗时/最频繁"的过程

### 12.2 运维注意

- **变更要走迁移脚本**，不要"连上生产库改一下"——否则环境之间永久漂移
- **过程体变更要考虑计划缓存**：SQL Server 可用 `sp_recompile` 强制下次重编译
- **上线顺序**：先加 `OUT` 参数/新结果集（向后兼容），再让调用方使用，最后清理旧逻辑
- **删对象前查依赖**：SQL Server `sys.sql_expression_dependencies`、PG `pg_depend`、Oracle `user_dependencies`

### 12.3 版本管理建议

1. 把过程/函数定义**和表结构放在同一套迁移里**，按序号执行
2. 迁移脚本写成**幂等**（`CREATE OR ALTER` / `DROP + CREATE` / `IF NOT EXISTS`）
3. 过程定义**进代码仓库**，评审走 PR —— 哪怕它最终是"贴进数据库执行的"
4. 复杂过程配一份**调用契约说明**（参数、返回、异常、幂等性、事务范围）

## 13. 常见误区

| 误区 | 纠正 |
|---|---|
| 存储过程比直接写 SQL 快 | "预编译"优势已被参数化查询削弱；真实优势是**减少往返和传输量** |
| 存储过程能防 SQL 注入 | 只有在**过程内部也参数化**时才成立；过程内拼动态 SQL 照样能被注入 |
| 过程可以放在 `SELECT` 里用 | 不能；函数才可以 |
| 参数类型随便写，反正会转换 | 类型不匹配会**隐式转换 -> 索引失效**，是最常见的性能事故 |
| 事务越多越安全 | 事务范围 = 锁范围；长事务会导致阻塞和死锁 |
| 触发器可以替代存储过程 | 触发器不能传参、不能显式调用、难以调试，只适合审计类旁路逻辑 |
| 存储过程适合放业务规则 | 业务规则进库后无法评审/灰度/回滚；库只该做数据搬运与聚合 |

## 14. 附：SQLite 为什么没有存储过程

**SQLite 完全不支持存储过程** —— 没有 `CREATE PROCEDURE`，没有 `CREATE FUNCTION`（SQL 层的），没有包。这是它"精简/嵌入式"定位的一部分：**它不打算承载服务端程序逻辑**。

需要"可参数化的服务端逻辑"时的替代方案（按实用性排）：

| 替代 | 能带参数 | 说明 |
|---|---|---|
| **视图** | 无 | 参数靠外层 `WHERE`；适合固定口径的聚合 |
| **CTE（`WITH ...`）** | 有 | 只活在当前语句里，不可跨语句复用；可递归 |
| **注册自定义函数** | 有 | 通过驱动把宿主语言的方法注册成 SQL 函数（C 层的 `sqlite3_create_function`；各语言驱动都有包装，如 .NET 的 `Microsoft.Data.Sqlite` 提供 `CreateFunction` 类 API —— **具体签名以所用驱动版本文档为准**）。限制：只能返回标量，不能返回多行结果集；**每条连接都要注册**；逻辑实际在宿主语言里，不在数据库里 |
| **应用层 SQL + 参数化** | 有 | 最通用；SQL 常量放在代码仓库里，可评审、可测试、可版本管理 |
| **把逻辑放在宿主应用** | 有 | 逻辑还在代码里，只是数据在 SQLite 里 |

**实践结论**：在 SQLite 场景下，"存储过程"这个角色通常由 **视图（固定口径）+ 应用层参数化 SQL（动态逻辑）** 共同承担。这也让逻辑留在代码仓库里，反而是优点。
