# 视图

> **所属**：通用数据库基础 ｜ **主题**：视图 View

## 1. 视图是什么

- **本质**：一段**起了名字、存在数据库里的 SELECT**。它是"查询的定义"，不是数据副本
- 属于 **DDL 对象**（`CREATE VIEW` 是 DDL），但表现像表，所以俗称**虚表**
- 查视图时，数据库把视图定义**展开/重写**成对底表的查询再执行
- **最重要的一条推论**：普通视图**不存数据、不加速**（详见第 7 节，这是最大的误解来源）

## 2. 理论基础：三级模式与外模式

- 数据库三级模式：**外模式（用户视图）/ 概念模式（逻辑结构）/ 内模式（物理存储）**
- **视图是"外模式"的标准化实现**，它的理论价值是**逻辑数据独立性**
- 两个独立性要分清：

| 独立性 | 含义 | 靠什么实现 |
|---|---|---|
| **逻辑数据独立性** | 概念模式（表结构）变化，外模式（视图/应用）不变 | **视图** |
| **物理数据独立性** | 内模式（索引、存储、分区）变化，表结构不变 | 索引/分区等物理对象 |

## 3. 视图的分类

| 类型 | 说明 |
|---|---|
| **普通视图** | 只存定义不存数据，每次查询实时展开 |
| **物化视图** Materialized View | **存数据**，需刷新；Oracle / PostgreSQL 原生支持 |
| **索引视图** Indexed View | SQL Server 专属，物化 + 可建索引（需 `WITH SCHEMABINDING`） |
| **可更新视图** | 满足条件时可直接 `INSERT/UPDATE/DELETE` |
| **只读视图** | 含聚合、多表连接等，不可直接写 |
| **递归视图** | 定义中引用自身（SQL:1999 特性，PostgreSQL 支持） |
| **系统视图 / 信息模式** | `information_schema.*`、`pg_catalog.*`、`sys.*`、`sqlite_master` |

## 4. 建 / 改 / 删

### 4.1 基本语法

```sql
create view v_demo as
select col_a, col_b, sum(col_c) as total
from t_demo
where col_a is not null
group by col_a, col_b;

-- 指定列名（覆盖 select 里的列名）
create view v_demo2 (a, b, c) as select x, y, z from t_demo;

-- 幂等创建（SQLite / PostgreSQL / MySQL 8.0.19+ / SQL Server 2016 SP1+）
create view if not exists v_demo as select ...;
```

### 4.2 各库语法差异

| 能力 | SQL Server | MySQL | PostgreSQL | Oracle | SQLite |
|---|---|---|---|---|---|
| 创建 | `CREATE VIEW` | `CREATE VIEW` | `CREATE VIEW` | `CREATE VIEW` | `CREATE VIEW` |
| 幂等建 | 无（用 `IF OBJECT_ID...` 判断） | `IF NOT EXISTS`(8.0.19+) | `IF NOT EXISTS` | 无 | `IF NOT EXISTS` |
| 改定义 | `ALTER VIEW`（须已存在）/ `CREATE OR ALTER VIEW`(2016 SP1+) | `ALTER VIEW`（等价 OR REPLACE） | `CREATE OR REPLACE VIEW` | `CREATE OR REPLACE VIEW` | **无**，只能 DROP + CREATE |
| 删除 | `DROP VIEW` | `DROP VIEW` | `DROP VIEW [CASCADE]` | `DROP VIEW` | `DROP VIEW IF EXISTS` |

> 注：SQL 标准只定义了 `CREATE VIEW`；`CREATE OR REPLACE VIEW` 是各厂商扩展（Oracle / PostgreSQL / MySQL 有，SQL Server 用 `CREATE OR ALTER`）。

### 4.3 常用选项

| 选项 | 库 | 作用 |
|---|---|---|
| `WITH CHECK OPTION` | 多库 | 经视图写入的行必须满足视图的 `WHERE` 条件 |
| `WITH CASCADED / LOCAL CHECK OPTION` | MySQL、PostgreSQL | 嵌套视图时检查哪几层 |
| `ALGORITHM = MERGE / TEMPTABLE / UNDEFINED` | MySQL | 指定视图合并还是先物化 |
| `DEFINER = 'user'`、`SQL SECURITY {DEFINER\|INVOKER}` | MySQL | 以谁的身份执行（决定权限检查对象） |
| `WITH SCHEMABINDING` | SQL Server | 绑定底表结构；**索引视图必需** |
| `security_barrier` | PostgreSQL | 阻止谓词下推，防止行级安全视图泄漏数据 |
| `WITH ENCRYPTION` | SQL Server | 加密视图定义文本 |

## 5. 可更新视图

### 5.1 通用条件（各库略有差异，但核心一致）

可 `INSERT/UPDATE/DELETE` 的视图通常必须：

- 只来自**一张底表**（不能含 `JOIN`）
- 不含 `DISTINCT`、`GROUP BY`、`HAVING`、聚合函数
- 不含 `UNION / UNION ALL`
- `SELECT` 列表中不含子查询、不含计算表达式列（视库而定）
- 不含窗口函数、`LIMIT`（视库而定）

**只要有一个不满足，视图就变成只读。**

### 5.2 不可更新时的替代手段

| 手段 | 支持者 | 说明 |
|---|---|---|
| **INSTEAD OF 触发器** | SQL Server、PostgreSQL、Oracle、SQLite | 在视图上挂触发器，自己写"怎么映射到底表" |
| **规则 RULE** | PostgreSQL（旧机制） | 已不推荐，语义容易踩坑 |
| 拆成"基础视图 + 应用层写底表" | 通用 | 最土但最可控 |

> MySQL **没有** `INSTEAD OF` 触发器，所以 MySQL 里复杂视图基本就是只读。

### 5.3 WITH CHECK OPTION 的作用

```sql
create view v_active as
select * from t_user where status = 1
with check option;

insert into v_active (id, status) values (100, 0);   -- 被拒绝：插入的行不满足 status = 1
```

- 用途：防止"**通过视图插进去的行，在视图里看不见**"这种诡异现象
- `LOCAL` vs `CASCADED`：嵌套视图时，`CASCADED` 逐层检查（默认），`LOCAL` 只检查当前层

## 6. 物化视图

### 6.1 与普通视图的本质区别

| | 普通视图 | 物化视图 |
|---|---|---|
| 存数据 | 否 | **是**（本质是"表 + 刷新机制"） |
| 查询时 | 展开重写 | 直接读已存结果 |
| 能建索引 | 否 | **能** |
| 数据新鲜度 | 实时 | **取决于刷新策略** |
| 写入成本 | 无 | 刷新时集中付出 |

### 6.2 刷新策略

| 策略 | 说明 |
|---|---|
| `REFRESH ON COMMIT` | 底表事务提交即刷新，实时性最好、写入开销最大 |
| `REFRESH ON DEMAND` | 手动/定时调用刷新 |
| 定时刷新 | 用 job / 调度器（如 Oracle `DBMS_SCHEDULER`） |
| **全量刷新** | 重算整张视图 |
| **增量刷新**（fast refresh） | 只应用变化量；**前提是底表建了"物化视图日志"**（Oracle `CREATE MATERIALIZED VIEW LOG`） |

### 6.3 注意事项

- **刷新期间可能阻塞查询或被锁**（取决库与选项）
- PostgreSQL 的 `REFRESH MATERIALIZED VIEW CONCURRENTLY` 可以不长时间阻塞，但**要求物化视图上有唯一索引**
- 物化视图**不保证与底表一致**，业务要能接受"数据是 N 分钟前的"
- 增量刷新对底表有硬性要求（主键、日志表），不是所有查询都能增量

## 7. 性能真相（最重要的一节）

### 7.1 普通视图**不加速**

- 优化器把视图当"**宏**"处理：能等价展开就展开（**视图合并 View Merging**），执行计划与手写 SQL 几乎一样
- 所以"封装成视图让查询变快"是**错的**

### 7.2 反而可能变慢的两种情况

| 情况 | 原因 |
|---|---|
| **视图物化 View Materialization** | 视图含 `DISTINCT` / `GROUP BY` / `UNION` / `LIMIT` / 窗口函数时，优化器可能选择"先算出整个视图结果存临时结构"，再套外层条件 -> 白算一大堆 |
| **谓词下推失败** | 外层 `WHERE` 无法推进视图内部（被 `DISTINCT`、`LIMIT`、`UNION` 挡住）-> 全量算完再过滤 |

**嵌套视图会放大这个问题**（每层都是一次展开机会）。

### 7.3 那"视图能减少内存/传输量"对吗？

**对，但功劳不在"视图"这个机制，而在"查询形态"。**

- 把 `GROUP BY` 聚合封进视图 —— 调用端 `select * from v where ...` 拿到的是**几百行聚合结果**
- 如果不封视图，直接 `select * from 底表` 再在应用里聚合 —— 拿到的是**几万到几百万行明细**

两者差别在于"**聚合在哪一侧执行**"，跟写不写成视图无关。视图只是让这段 SQL 有个稳定的名字。

### 7.4 想真正加速怎么办

1. 改成 **物化视图 / 索引视图**
2. 或者直接**改写 SQL / 加索引 / 加汇总表**（见"数据库优化"系列）

## 8. 优点

| 优点 | 说明 |
|---|---|
| **逻辑封装与复用** | 复杂查询只定义一处，多处使用 |
| **简化调用端** | 上层只面对 `select * from v where ...` |
| **逻辑数据独立性** | 底表改名、拆表、加列 -> 只改视图定义 |
| **口径统一** | 计算口径（如日均、达成率）集中定义，防止多处各写一遍导致漂移 |
| **安全性** | 只授视图权限不授底表权限，可隐藏敏感列/敏感行 |
| **向后兼容** | 重构表结构时保留旧视图名，老代码零改动 |
| **稳定接口** | 把派生列、计算列包装成有稳定列名的"虚拟字段" |

## 9. 缺点与风险

| 风险 | 说明 |
|---|---|
| **不提升性能** | 见第 7 节 |
| **不能带参数** | 定义里无法声明参数；过滤只能靠外层 `WHERE` |
| **普通视图不能建索引** | 只有物化/索引视图可以 |
| **定义漂移** | 定义存在数据库里，代码仓库看不见；换了环境没建就报"对象不存在" |
| **依赖链脆弱** | 底表列改名/改类型 -> 视图可能失效或**语义悄悄改变**而不报错 |
| **嵌套难维护** | 出问题要一层层展开人工排查 |
| **迁移与版本管理麻烦** | 必须进迁移脚本；`CREATE OR REPLACE` 通常**不能**改列名或列类型 |
| **权限陷阱** | SQL Server 所有权链、MySQL `DEFINER` / `SQL SECURITY` 语义与直觉不符 |
| **性能问题被藏起来** | "为什么这条简单查询这么慢" —— 八成是视图里藏着重逻辑 |

## 10. 依赖管理与运维

### 10.1 查看定义

| 库 | 方式 |
|---|---|
| SQL Server | `sp_helptext 'v_name'`；`sys.sql_modules.definition` |
| MySQL | `SHOW CREATE VIEW v_name`；`information_schema.views` |
| PostgreSQL | `pg_get_viewdef('v_name'::regclass, true)`；`\d+ v_name` |
| Oracle | `user_views.text`；`dbms_metadata.get_ddl('VIEW','V_NAME')` |
| SQLite | `select sql from sqlite_master where type='view' and name='v_name'` |

### 10.2 查看依赖

| 库 | 方式 |
|---|---|
| SQL Server | `sys.sql_expression_dependencies`；`sys.dm_sql_referenced_entities('v_name','OBJECT')` |
| MySQL | `information_schema.view_table_usage`、`view_routine_usage` |
| PostgreSQL | `pg_depend`、`pg_rewrite` |
| Oracle | `user_dependencies` |
| SQLite | **无系统依赖表**，只能靠文本解析或自己的元数据维护 |

### 10.3 重建与迁移要点

- **幂等**：迁移脚本里写成 `DROP VIEW IF EXISTS` + `CREATE VIEW`，或 `CREATE OR REPLACE`
- **顺序**：先建底表/底视图，再建上层视图；删的时候反过来
- **所有环境都要建**：测试库、生产库、容器里的临时库；漏了就运行时报错
- SQL Server 底表改列后可用 `sp_refreshview` / `sp_refreshsqlmodule` 刷新元数据

## 11. 各数据库支持速查

| 能力 | SQL Server | MySQL | PostgreSQL | Oracle | SQLite |
|---|---|---|---|---|---|
| 普通视图 | 有 | 有 | 有 | 有 | 有 |
| `CREATE OR REPLACE` | `CREATE OR ALTER`(2016 SP1+) | 有 | 有 | 有 | **无** |
| `ALTER VIEW` 改定义 | 有（须已存在） | 有 | 无（用 OR REPLACE） | 无（用 OR REPLACE） | **无** |
| 物化视图 | 索引视图（受限） | **无** | 有 | 有（最强，支持增量） | **无** |
| 物化结果可建索引 | 有 | - | 有 | 有 | - |
| `WITH CHECK OPTION` | 有 | 有 | 有（9.4+） | 有 | **无** |
| 可更新视图 | 受限 | 受限 | 受限 | 受限 | **无**（需 INSTEAD OF） |
| `INSTEAD OF` 触发器 | 有 | **无** | 有 | 有 | 有 |
| 递归视图 | 无（用递归 CTE） | 无 | **有** | 无（用递归 CTE） | 无（用递归 CTE） |
| `DEFINER` / `SQL SECURITY` | 无（用 `EXECUTE AS` / 所有权链） | **有** | 无（用 `SECURITY DEFINER` 函数） | 无（用 `AUTHID`） | 无 |
| 定义存放处 | `sys.sql_modules` | `information_schema.views` | `pg_views` / `pg_get_viewdef` | `user_views` | `sqlite_master` |

## 12. 最佳实践

1. **命名**：统一前缀（`v_` / `vw_`），和表一眼能区分
2. **只在"≥2 个消费者"时才抽象成视图**；只有一个调用点，直接写 SQL 更省事
3. **嵌套不超过 2 层**：基础视图（清洗/关联）+ 应用视图（业务口径）
4. **视图里不要写 `ORDER BY`**：外层排序才有意义，部分库直接报错
5. **避免 `SELECT *`**：底表加列会静默传播到所有消费方
6. **重逻辑不要藏进视图**：性能问题会被掩盖，排查成本极高
7. **口径类计算优先收敛到视图**（如"日均 = 总量 / 有效天数"），防止多处实现漂移
8. **视图定义必须进版本控制/迁移脚本**，且写成幂等
9. **授权前先搞清语义**：MySQL 的 `DEFINER`、SQL Server 的所有权链都会改变实际权限判定
10. **性能排查时记得问一句**："这个东西是视图吗？里面有什么？"

## 13. 常见误区

| 误区 | 纠正 |
|---|---|
| 视图能提升性能 | 普通视图不能；只有物化视图/索引视图可能 |
| 视图会把结果缓存起来 | 不缓存（物化视图除外） |
| 视图是只读的 | 简单视图可读写；复杂视图可用 `INSTEAD OF` 触发器变可写 |
| 视图能带参数 | 不能；要么外层 `WHERE`，要么改用函数/存储过程 |
| 建好视图，底表怎么改都不影响 | 会影响；需要重建/刷新，语义可能悄悄变化 |
| 视图能给列建索引 | 普通视图不能建任何索引 |

## 14. 附：SQLite 的视图要点

SQLite 是最"精简"的实现，用之前必须知道这几条：

- **语法**：`CREATE VIEW [IF NOT EXISTS] v AS SELECT ...`
- **没有 `CREATE OR REPLACE`，没有 `ALTER VIEW`** -> 改定义只能：
  ```sql
  drop view if exists v_demo;
  create view v_demo as select ...;
  ```
- **没有物化视图** -> 要"物化"只能自己建表 + 定时任务 / 触发器维护
- **视图只读** -> 要写只能挂 `INSTEAD OF` 触发器（`INSTEAD OF INSERT` 等）
- **不支持 `WITH CHECK OPTION`**
- **不能带参数** -> 过滤条件写在外层 `WHERE`
- **定义存在 `sqlite_master.sql`**；**没有系统依赖表**，视图与底表的关系无人维护，改表时要自己记得哪些视图受影响
- 因为缺迁移机制（很多项目直接用 `EnsureCreated()` 建表），**视图的创建脚本要显式执行**，且测试库/生产库都要执行 —— 这是最常见的上线事故点
