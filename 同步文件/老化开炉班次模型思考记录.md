## 一、问题背景

### 1.1 业务场景

老化机台页面上，每台机器（ConsoleCode）上有一批正在老化的工单。每张工单有**下老化时间**（`NextStepStartTime`，即老化时长到达、可以下老化的时刻）。

页面卡片需要展示每台机器**下一次该在什么时候下老化**（`NextStepStartTime` + `TodayFinish` + `Status` 五态）。

### 1.2 新增需求（2026-08-21 沟通确认）

1. **时间窗口**：从原来的"自然日（0-24点）"改为 **24h 开炉窗口 = 当天 07:00 ~ 次日 07:00**
2. **班次划分**：
   - 白班 = `07:00 ~ 19:00`
   - 晚班 = `19:00 ~ 次日 07:00`
   - 一个窗口 = 一个白班 + 一个晚班
3. **核心规则**：**不能连续两个班次开炉**（隔一个班次才能再开一次炉）

### 1.3 两条硬性约束（业务/环境限制）

| # | 约束 | 后果 |
|---|---|---|
| ① | 工单下老化后，它的数据在本接口中就**消失**了 | 算法**看不到已经输出的历史段**，只能依赖"当前及未来"的在炉工单 |
| ② | **不能**依赖数据库存储开炉日志 | 算法**无法记录"哪些班次已经开过炉"** |

> 这两条约束是模型设计的核心前提，所有后续思考都围绕"如何在不存历史、数据会消失的前提下，正确判断下一次开炉时间"。

## 二、需求确认的细节（与用户逐条对齐）

| 项 | 结论 |
|---|---|
| `NextStepStartTime` 返回什么 | **原始工单时间**（不是顺延后的时间），只决定"选哪个工单的时间作为下次下老化时间" |
| 判定依据 | **只看未来下老化工单**，不查开炉日志 |
| 顺延方向 | 白班禁 → 晚班；晚班禁 → 明日白班；**跨窗口允许顺延** |
| 开炉补偿 | 已有人实现过，**不重复设计**，本次只做下老化时间窗口/班次判断 |

## 三、模型思考演进全过程

> 这一节是重点。完整记录每一步的思考、发现的问题、如何修正。

### 3.1 起点：原始代码（自然日窗口）

现有代码逻辑：

```csharp
nextStepStartTime = validOrderNextTime.Count < 1 ? null
    : validOrderNextTime.GroupBy(x => x.Value.Date)          // 按自然日分组
    .Where(g => g.Key >= DateTime.Today)                     // 只看今天及以后
    .OrderBy(g => g.Key)
    .FirstOrDefault()
    ?.Max(x => x.Value);

isOverdue1day = validOrderNextTime.Any(x => x.Value < DateTime.Today);
```

问题：按自然日（0-24点）分组，不符合"7点-次日7点"的班次业务。

### 3.2 第一次修正：窗口分组（纯窗口部分）

把分组键从"自然日"改为"7点-次日7点窗口"：

```csharp
DateTime WindowKey(DateTime t) => (t - TimeSpan.FromHours(7)).Date;   // 7点前归前一天

var curWindowKey  = WindowKey(now);
var curWindowStart = curWindowKey.AddHours(7);

nextStepStartTime = validOrderNextTime.Count < 1 ? null
    : validOrderNextTime.GroupBy(x => WindowKey(x.Value))
    .Where(g => g.Key >= curWindowKey)
    .OrderBy(g => g.Key)
    .FirstOrDefault()
    ?.Max(x => x.Value);

TodayFinish = nextStepStartTime.HasValue && WindowKey(nextStepStartTime.Value) == curWindowKey;
```

⚠️ 此时发现：**只改窗口分组解决不了"不能连续两个班次开炉"**，因为它需要知道"上一班次是否开过"。

### 3.3 第二个模型：数组 + 指针（区间覆盖模型）

**用户提出**：把班次看成数组，模拟"每天两个班组（一个 24h 窗口）"：

```
数组对齐（窗口固定从"今天早班"开始）：
  索引0 = 今天早班（窗口0）
  索引1 = 今天晚班（窗口0）
  索引2 = 明天早班（窗口1）
  索引3 = 明天晚班（窗口1）
  ...

窗口 = {索引, 索引+1}（24h = 一个早班 + 一个晚班）
指针 +2 = 处理完一个窗口跳到下一个窗口（每天）
决策单元 = 窗口内两个班次 {i, i+1} 中选一个输出
```

**输出规则**：输出索引 i = 开炉班次，它覆盖区间 `{i-1, i}`（开炉时把"前一个被禁班次顺延来的工单 + 本班次工单"一起下掉）。

**核心约束的数学表达**：

> "一个位置不能被输出两次" = 覆盖区间不能重叠 → 相邻输出索引必须相差 ≥2
> → 窗口0选晚班(1) 后，窗口1的早班(2) 与 1 相邻 → 自动被禁
> → 这就是"不能连续两个班次开炉"的数学形式，模型内建、不需查历史

**验证例子**（当前 08-21 19:30 晚班）：

| 窗口 | 候选 | 决策 |
|---|---|---|
| 窗口0 {0,1} | 1(W2) | 选1，区间{0,1} |
| 窗口1 {2,3} | 2(W3)、3(W4) | lastOpen=1 → 2被禁，只能选3 |
| 窗口2 {4,5} | 4(W5) | lastOpen=3 → 4被禁，5无值 → **W5 漏覆盖 ❌** |

**发现问题**：这个模型依赖"整个数组都可见"（能规划全覆盖），但约束①（数据消失）意味着**只能看到未输出的一段**，无法依赖整体规划。

### 3.4 关键转折：承认两条约束的本质后果

**用户指出**（正确）：

> 下老化后工单数据消失 → 每次输出后数据被抹除 → 没法依赖数组整体设计算法，只能依赖"没被输出过的一段数组"
> 不能存 log → 算法也不能记录已输出的位置

**结论**：系统在每轮决策时**根本不知道"上一班次是否开过炉"**。而"不能连续开炉"恰恰依赖这个锚点。

**追问**：那这个信息从哪来？→ 唯一还能携带历史信息的载体 = **仍然留在炉里的工单本身**。

### 3.5 第三个模型：隐式残留信号法（方向1/2/3 备选）

提出三个方向：

| 方向 | 做法 | 代价 |
|---|---|---|
| **方向1 工单标记法** | 工单被顺延时打标记（Deferred） | 要给工单加字段（可能涉及表结构变更） |
| **方向2 隐式过期信号法** | 不存任何东西，靠"过期未下工单"推断 | 零存储，但有模糊性 |
| **方向3 放弃严格保证** | 当前班次固定可开 | 最简，但"不连续"无法系统保证 |

**用户倾向方向2**，并自己推导出一个关键洞察（见 3.6）。

### 3.6 关键洞察 ①：残留信号的方向（重要，曾被搞反）

**用户修正（正确）**：

> 只要发生"顺延"，无论原因是"被规则禁"还是"忙不过来"，前提都是"上一个可开班次已经开过炉了"？
> —— 不对，反了！
> **存在过期工单 → 该工单所属班次【没有开炉】**（开了就会下掉、消失）

**正确推导**：

```
某个班次如果开了炉 → 它到期的工单会被下掉、数据消失
⇒ 如果某个班次还残留"该下没下"的工单
   ⇒ 恰恰说明那个班次【没有开炉】

判断"本班次 C 能否开"：
  上一班次 B 有残留工单（下老化时间落在 B 区间且已过、仍在炉）
    → B 没开 → C 可开 ✓（无论 B 为什么没开，都不需要区分原因）
```

| B 的情况 | 信号 | C 能否开 |
|---|---|---|
| B 有到期工单、B 开了下完了 | 无残留 | 禁（B、C 连续） |
| B 有到期工单、B 没开 | **有残留** | ✅ 可开 |
| B 本无到期工单 | 无残留 | 可开 |

### 3.7 兜底策略：只有"激进"不自锁

**发现**：真正的盲区在"无残留"一边（无法区分"B开了下干净" vs "B本无到期工单"）。

| 兜底 | 结果 |
|---|---|
| 无残留 → **默认可开**（激进） | 不产生死锁；只在"B开了且下得很干净"时偶尔违反"不连续" |
| 无残留 → 默认禁开（保守） | **会死锁**：若每班次都能正常下完（永远无残留）→ 永远禁开 → 工单积压 ❌ |

**结论**：激进兜底（无残留默认可开）是唯一自洽选择——系统在信息不足时默认放行，"不连续"最终由现场人工把关。

### 3.8 关键洞察 ②：同班次多工单的"假残留"边界（用户提出）

**场景**（晚班 19:00 ~ 次日 07:00）：

| 工单 | 下老化时间 |
|---|---|
| A | 当晚 19:01（班次开始就到期） |
| B | 次日 06:59（班次快结束才到期） |

假设 19:01 开一次炉（下 A），B 在开炉时还没到期 → 留在炉里等下次。

**问题**：次日 07:00 早班轮询，B 已过期 → 残留信号 → 误判"晚班没开 → 早班可开"。
但实际晚班 19:01 开过炉 → 早班**应该禁开**。❌

**本质**：残留工单有两种来源，信号只对一种成立：

| 残留来源 | 含义 | 模型推断 | 是否正确 |
|---|---|---|---|
| (a) 上一班次**完全没开** | 工单一直在炉里 | 残留→上一班次没开→可开 | ✅ 正确 |
| (b) 上一班次**开了但没下完** | 同班次只开一次，末尾工单没赶上 | 残留→上一班次没开→可开 | ❌ 误判 |

**能否在模型层根治？** 数据层面系统只能看到"B 残留"，看不到已被下掉的 A。启发式（按残留时间在班次内的位置判断）是概率性的、不可靠，不推荐。

**真正解法**：靠**操作规范**保证信号纯净：

> 开炉时，一次下掉"本班次内所有已到期工单"（以班次内最晚到期时间为参考，统一开一次，不留尾巴）。

这样 6:59 的工单会在晚班末尾一起下 → 残留只来自"真的没开的班次" → 信号 (a) 纯净 → 模型成立。

## 四、最终模型（当前状态）

```
本班次 C 的开炉决策（每台机器、每轮轮询）：

输入：当前在炉工单（Moving 且有 NextStepStartTime）
      now、当前班次 C（班次开始时间 shiftStart）

① 检测残留（过期）信号：
   上一班次 B 是否有残留工单？
   （下老化时间落在 B 的班次区间、且已过当前时刻、仍留在炉里）
   ├─ 有 → B 没开 → C 【可开】        ← 信号明确、正确
   └─ 无 → 信息不足 → C 【默认可开】    ← 激进兜底，现场把关"不连续"

② 确定下次开炉班次：
   C 可开 → 下次开炉 = 本班次 C
   （禁开场景在当前模型下不直接产生，由现场按规则执行）

③ 输出（沿用既有语义）：
   NextStepStartTime = 下次开炉班次内所有工单的【最晚原始时间】
   TodayFinish        = 下次开炉班次是否落在当前 24h 窗口
   Status             = 按下次开炉班次位置 + 剩余时间判定
```

**模型成立的必要前提**（待业务确认）：

1. 现场开炉**一次下掉班次内所有已到期工单**（消除 (b) 假残留）
2. 接受激进兜底（无残留默认可开），"不连续"最终由现场把关
